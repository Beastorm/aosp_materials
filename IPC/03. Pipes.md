# Pipe IPC in Android

## What is a Pipe?

A Pipe is the simplest form of IPC — it's like a one-way water pipe where data flows from one end to another.

```
┌──────────┐                        ┌──────────┐
│          │   ════════════════►     │          │
│ Process A│       PIPE (Data)      │ Process B│
│ (Writer) │   ════════════════►     │ (Reader) │
│          │                        │          │
└──────────┘                        └──────────┘
     ▲                                    ▲
  Write End                           Read End
  (fd[1])                             (fd[0])
```

## 1. Anonymous (Unnamed) Pipe

### How It Works — Step by Step

```
Step 1: Process creates a pipe
  Process A (Parent)
  fd[0] = Read End
  fd[1] = Write End
  fd[0]═══════fd[1]

Step 2: fork() creates child process
  Parent Process              Child Process
  fd[0] (read)               fd[0] (read)
  fd[1] (write)              fd[1] (write)
         └──────────┬───────────────┘
                    │  Shared Pipe

Step 3: Close unused ends
  Parent Process              Child Process
  fd[0] ✗ CLOSED             fd[0] ✓ READ
  fd[1] ✓ WRITE              fd[1] ✗ CLOSED
       │    ══════════════►        │
            Data flows one direction
```

### Native Code Example (C/C++)

```c
#include <unistd.h>
#include <stdio.h>
#include <string.h>
#include <sys/wait.h>

int main() {
    int fd[2];      // fd[0] = read end, fd[1] = write end
    pid_t pid;
    char buffer[100];

    if (pipe(fd) == -1) { perror("pipe failed"); return 1; }

    pid = fork();

    if (pid > 0) {
        // ===== PARENT PROCESS (Writer) =====
        close(fd[0]);
        const char *message = "Hello from Parent!";
        write(fd[1], message, strlen(message) + 1);
        printf("Parent: Sent message\n");
        close(fd[1]);
        wait(NULL);

    } else if (pid == 0) {
        // ===== CHILD PROCESS (Reader) =====
        close(fd[1]);
        read(fd[0], buffer, sizeof(buffer));
        printf("Child: Received '%s'\n", buffer);
        close(fd[0]);
    }
    return 0;
}
```

## 2. Bidirectional Communication (Two Pipes)

```
    Parent Process                          Child Process
    ┌────────────────┐                     ┌────────────────┐
    │  Write fd1[1]  │ ══ Pipe 1 ════════► │  Read fd1[0]   │
    │  Read  fd2[0]  │ ◄══ Pipe 2 ════════ │  Write fd2[1]  │
    └────────────────┘                     └────────────────┘
```

```c
int pipe1[2];  // Parent → Child
int pipe2[2];  // Child → Parent
char buffer[100];

pipe(pipe1); pipe(pipe2);
pid_t pid = fork();

if (pid > 0) {
    // PARENT
    close(pipe1[0]); close(pipe2[1]);

    write(pipe1[1], "What's your PID?", 17);

    read(pipe2[0], buffer, sizeof(buffer));
    printf("Parent received: %s\n", buffer);

    close(pipe1[1]); close(pipe2[0]);
    wait(NULL);

} else {
    // CHILD
    close(pipe1[1]); close(pipe2[0]);

    read(pipe1[0], buffer, sizeof(buffer));
    printf("Child received: %s\n", buffer);

    char reply[50];
    sprintf(reply, "My PID is %d", getpid());
    write(pipe2[1], reply, strlen(reply) + 1);

    close(pipe1[0]); close(pipe2[1]);
}
```

## 3. Named Pipe (FIFO)

Named pipes have a file path so unrelated processes can communicate.

```
    ┌─────────────────┐                    ┌─────────────────┐
    │   Process A     │                    │   Process B     │
    │   (Writer)      │                    │   (Reader)      │
    │ open("/tmp/     │                    │ open("/tmp/     │
    │   myfifo",      │                    │   myfifo",      │
    │   O_WRONLY)     │                    │   O_RDONLY)     │
    └────────┬────────┘                    └────────┬────────┘
             │         /tmp/myfifo                   │
             │    ┌─────────────────┐               │
             └───►│  Named Pipe     │◄──────────────┘
                  │  (FIFO file)    │
                  └─────────────────┘
Note: Exists in filesystem but data stays in KERNEL MEMORY (not on disk)
```

```c
// ===== Process A: Writer =====
mkfifo("/data/local/tmp/myfifo", 0666);
int fd = open("/data/local/tmp/myfifo", O_WRONLY);
const char *msg = "Hello via Named Pipe!";
write(fd, msg, strlen(msg) + 1);
close(fd);

// ===== Process B: Reader =====
char buffer[100];
int fd = open("/data/local/tmp/myfifo", O_RDONLY);
read(fd, buffer, sizeof(buffer));
printf("Received: %s\n", buffer);
close(fd);
```

## 4. Pipe in Android Java/Kotlin (ParcelFileDescriptor)

```
┌──────────────────────────────────────────────────────┐
│                Android Framework                      │
│                                                      │
│  ParcelFileDescriptor.createPipe()                   │
│  Returns: ParcelFileDescriptor[2]                    │
│     [0] = Read End                                   │
│     [1] = Write End                                  │
│                      │                               │
│                      ▼                               │
│          Linux Kernel pipe() (native impl)           │
└──────────────────────────────────────────────────────┘
```

### Pipe between Service and Activity

```kotlin
// ===== Service (Writer) =====
class MyService : Service() {

    override fun onBind(intent: Intent): IBinder = MyBinder()

    inner class MyBinder : Binder() {
        fun getDataPipe(): ParcelFileDescriptor {
            val pipe    = ParcelFileDescriptor.createPipe()
            val readEnd = pipe[0]
            val writeEnd = pipe[1]

            Thread {
                val output = ParcelFileDescriptor.AutoCloseOutputStream(writeEnd)
                output.write("Hello from Service!".toByteArray())
                output.close()
            }.start()

            return readEnd
        }
    }
}
```

```kotlin
// ===== Activity (Reader) =====
class MainActivity : AppCompatActivity() {

    private val connection = object : ServiceConnection {
        override fun onServiceConnected(name: ComponentName, binder: IBinder) {
            val myService = binder as MyService.MyBinder
            val readEnd   = myService.getDataPipe()

            Thread {
                val input = ParcelFileDescriptor.AutoCloseInputStream(readEnd)
                val data  = input.bufferedReader().readText()
                Log.d("Pipe", "Received: $data")
                input.close()
            }.start()
        }
        override fun onServiceDisconnected(name: ComponentName) {}
    }

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        bindService(Intent(this, MyService::class.java), connection, BIND_AUTO_CREATE)
    }
}
```

## 5. ContentProvider with Pipe

```
┌──────────────┐         ┌───────────────────┐        ┌────────────────┐
│  App A       │         │   ContentProvider  │        │  File/Network  │
│  (Client)    │         │   (in App B)       │        │  Resource      │
│              │         │                    │        │                │
│  resolver.   │────────►│  openFile() {      │───────►│ Read large    │
│  openFile    │         │    createPipe()    │        │ file/stream   │
│  Descriptor()│◄────────│    return readEnd  │◄───────│               │
│  Read stream │  Pipe   │    write writeEnd  │  Data  │               │
└──────────────┘         └───────────────────┘        └────────────────┘
```

```kotlin
class MyContentProvider : ContentProvider() {

    override fun openFile(uri: Uri, mode: String): ParcelFileDescriptor? {
        val pipe     = ParcelFileDescriptor.createPipe()
        val readEnd  = pipe[0]
        val writeEnd = pipe[1]

        Thread {
            val output = ParcelFileDescriptor.AutoCloseOutputStream(writeEnd)
            try {
                val file = File(context?.filesDir, "large_data.json")
                file.inputStream().use { it.copyTo(output) }
            } finally {
                output.close()
            }
        }.start()

        return readEnd
    }
}
```

## 6. `createReliablePipe()` — Error Detection

```
Regular Pipe:                      Reliable Pipe:
Writer crashes →                   Writer crashes →
Reader gets EOF (silent)           Reader gets IOException with error message
```

```kotlin
val pipe     = ParcelFileDescriptor.createReliablePipe()
val readEnd  = pipe[0]
val writeEnd = pipe[1]

// Writer signals errors
try {
    val output = ParcelFileDescriptor.AutoCloseOutputStream(writeEnd)
    // ... write data ...
    output.close()
} catch (e: Exception) {
    writeEnd.closeWithError("Write failed: ${e.message}")
}

// Reader detects errors
try {
    val input = ParcelFileDescriptor.AutoCloseInputStream(readEnd)
    val data  = input.bufferedReader().readText()
    input.close()
    readEnd.checkError()  // Throws if writer signaled error
} catch (e: IOException) {
    Log.e("Pipe", "Writer had error: ${e.message}")
}
```

## 7. Pipe Data Flow in Kernel

```
          User Space                    Kernel Space
    ┌──────────────────┐         ┌─────────────────────────┐
    │  Process A       │         │   Pipe Buffer (64KB)    │
    │  write(fd) ──────┼────────►│   ┌─┬─┬─┬─┬─┬─┬─┬─┐   │
    │                  │  copy   │   │D│A│T│A│ │ │ │ │   │
    └──────────────────┘  from   │   └─┴─┴─┴─┴─┴─┴─┴─┘   │
                         user    │         │ copy to user  │
    ┌──────────────────┐         │         ▼               │
    │  Process B       │         │   ┌─┬─┬─┬─┬─┬─┬─┬─┐   │
    │  read(fd) ◄──────┼─────────│   │D│A│T│A│ │ │ │ │   │
    └──────────────────┘         │   └─┴─┴─┴─┴─┴─┴─┴─┘   │
                                 └─────────────────────────┘

⚠️ Data is COPIED TWICE:
   1. User → Kernel (write)
   2. Kernel → User (read)
   Compare with Binder: Only 1 copy!
```

---

## 8. Blocking Behavior

```
Scenario 1: BUFFER EMPTY
  Reader calls read() → BLOCKED, waiting for data
  Writer calls write() → Reader UNBLOCKED, returns data

Scenario 2: BUFFER FULL (64KB)
  Writer calls write() → BLOCKED, buffer full
  Reader calls read() → Frees space → Writer UNBLOCKED

Scenario 3: PIPE CLOSED
  Writer calls close(fd[1]) ✗
  Reader calls read(fd[0]) → Returns 0 (EOF) → "No more data"
```

## 9. Complete Example: Inter-Process Pipe via AIDL

```
┌──────────────────┐                    ┌──────────────────┐
│   Client App     │                    │   Server App     │
│   (Process 1)    │                    │   (Process 2)    │
│                  │  Call getData()    │                  │
│                  │──── Binder ───────►│  Creates pipe()  │
│                  │◄─── readEnd ───────│  Returns readEnd │
│  Read from       │                    │  Write to        │
│  readEnd stream  │◄════ DATA ═════════│  writeEnd stream │
└──────────────────┘   (via pipe)       └──────────────────┘
```

**AIDL Interface**

```aidl
// IDataService.aidl
interface IDataService {
    ParcelFileDescriptor getData();
}
```

**Server**

```kotlin
class DataService : Service() {

    private val binder = object : IDataService.Stub() {
        override fun getData(): ParcelFileDescriptor {
            val pipe     = ParcelFileDescriptor.createReliablePipe()
            val readEnd  = pipe[0]
            val writeEnd = pipe[1]

            Thread {
                try {
                    val os = ParcelFileDescriptor.AutoCloseOutputStream(writeEnd)
                    for (i in 1..1000) {
                        os.write("Chunk $i of data\n".toByteArray())
                        Thread.sleep(10)
                    }
                    os.close()
                } catch (e: Exception) {
                    writeEnd.closeWithError(e.message)
                }
            }.start()

            return readEnd
        }
    }

    override fun onBind(intent: Intent) = binder
}
```

**Client**

```kotlin
private fun readFromService(service: IDataService) {
    val readEnd = service.data

    Thread {
        val input  = ParcelFileDescriptor.AutoCloseInputStream(readEnd)
        val reader = input.bufferedReader()

        var line: String?
        while (reader.readLine().also { line = it } != null) {
            Log.d("Client", "Received: $line")
        }

        reader.close()
        readEnd.checkError()
    }.start()
}
```

## ✅ When to Use Pipes

### 1. Large File / Data Streaming

```
Problem: Binder has 1MB transaction limit

Without Pipe (WRONG for large data):
  App A ──── Binder 💥 ────► App B
  (500MB video)  TransactionTooLargeException!

With Pipe (CORRECT):
  App A ──── Binder (just sends pipe fd) ────► App B
  App A ════ data stream (via pipe) ══════════► App B gets 500MB ✅
```

```kotlin
// ✅ GOOD: Streaming large PDF via ContentProvider pipe
class PdfProvider : ContentProvider() {
    override fun openFile(uri: Uri, mode: String): ParcelFileDescriptor {
        val pipe = ParcelFileDescriptor.createReliablePipe()

        Thread {
            val out = ParcelFileDescriptor.AutoCloseOutputStream(pipe[1])
            getLargePdfFile().inputStream().copyTo(out)  // Stream 100MB PDF
            out.close()
        }.start()

        return pipe[0]
    }
}
```

### 2. Parent-Child Process Communication

```
Android Zygote Model:

        Zygote Process
        ┌─────────────────────────────┐
        │  pipe(fd)                   │
        │  fork() ───────────────────► App Process
        │  Parent writes config ──────► Child reads config via pipe
        └─────────────────────────────┘

✅ Perfect use case: related processes, one-way setup data
```

```kotlin
// ✅ GOOD: Parent sends config to child process
fun startChildProcess(): Process {
    val process = Runtime.getRuntime().exec(
        arrayOf("/system/bin/my_native_worker")
    )
    // process.outputStream IS a pipe to child's stdin
    val writer = process.outputStream.bufferedWriter()
    writer.write("""{"config": "value", "timeout": 30}""")
    writer.close()

    // process.inputStream IS a pipe from child's stdout
    val result = process.inputStream.bufferedReader().readText()
    return process
}
```

### 3. Capturing Command / Process Output

```
Runtime.exec() uses pipes internally:

  Your App ◄══ stdout (pipe) ══ Shell Command ("logcat", "ps", "dumpsys")
  Your App ◄══ stderr (pipe) ══ Shell Command
```

```kotlin
// ✅ GOOD: Capturing logcat output via pipe
fun captureLogs(): String {
    val process = Runtime.getRuntime().exec(arrayOf("logcat", "-d", "-t", "100"))
    return process.inputStream.bufferedReader().readText()
}

// ✅ GOOD: Running shell command and getting result
fun getRunningProcesses(): List<String> {
    val process = Runtime.getRuntime().exec("ps -A")
    return process.inputStream.bufferedReader().readLines()
}
```

## ❌ When NOT to Use Pipes

### ❌ 1. Small / Simple Data Exchange

```
❌ BAD: Using pipe for simple messages
  App A creates pipe → writes "true" → App B gets "true"
  So much overhead just to send a boolean!

✅ USE INSTEAD: Intent, Broadcast, SharedPreferences, Binder
```

```kotlin
// ❌ BAD: Pipe for simple flag
val pipe = ParcelFileDescriptor.createPipe()
val out  = ParcelFileDescriptor.AutoCloseOutputStream(pipe[1])
out.write("true".toByteArray())  // Overkill!

// ✅ GOOD: Use Intent instead
val intent = Intent("com.example.ACTION_UPDATE")
intent.putExtra("flag", true)
sendBroadcast(intent)

// ✅ OR: Use SharedPreferences
prefs.edit().putBoolean("flag", true).apply()
```

### ❌ 2. Unrelated Processes (without Named Pipe)

```
❌ BAD: Anonymous pipe between unrelated apps

  App A (Package 1)              App B (Package 2)
  pipe(fd)                       How do I get fd[0] = 3?
  fd[0] = 3          ❌           IMPOSSIBLE — no shared process space!
  fd[1] = 4        IMPOSSIBLE

✅ USE INSTEAD: Named Pipe (FIFO), Socket, Binder
```

### ❌ 3. Bidirectional Communication (gets complex)

```
❌ BAD: Two-way chat using pipes
  App A: pipe1[1] write ════════════► pipe1[0] read :App B
  App A: pipe2[0] read  ◄════════════ pipe2[1] write:App B

  Complexity: 4 file descriptors, easy to deadlock, hard to synchronize

  DEADLOCK SCENARIO:
  A writes to pipe1 (full, blocks)
  B writes to pipe2 (full, blocks)
  Both waiting for other to read → DEADLOCK! 💀

✅ USE INSTEAD: Binder (AIDL), Socket (handles bidirectional natively)
```

### ❌ 4. Multiple Readers / Writers

```
❌ BAD: Multiple processes reading from same pipe
  Writer writes "HELLO"
  Reader1 gets "HEL"
  Reader2 gets "LO"
  Data split unpredictably!

✅ USE INSTEAD: Message Queue, Broadcast, EventBus, SharedMemory
```

### ❌ 5. Persistent Data Storage

```
❌ BAD: Using pipe as data store
  • Pipe data lives ONLY in kernel memory
  • App closes → Pipe destroyed
  • Device reboots → Pipe gone
  • Data NOT on disk
  • Writer faster than reader → Buffer fills (64KB) → Writer BLOCKS

✅ USE INSTEAD: Room DB, File, SharedPreferences, ContentProvider
```

### ❌ 6. Random Access Data

```
❌ BAD: Seeking / Random access via pipe
  Pipe is SEQUENTIAL (FIFO)
  Data: [A][B][C][D][E]
  Read A? → Gone forever, can't go back
  lseek() on pipe → FAILS ❌ ("Illegal seek" error)

// ❌ This will FAIL on a pipe:
Os.lseek(fd, 0, OsConstants.SEEK_SET)  // ERROR!

✅ USE INSTEAD: File, MemoryMappedFile, SharedMemory
```

### ❌ 7. High-Frequency Small Messages

```
❌ BAD: Thousands of tiny pipe writes per second
  Each write() = System call overhead
  1000 writes/sec × syscall overhead = significant CPU waste

  Sensor at 1000Hz → 1000 syscalls/sec → HIGH CPU!

✅ USE INSTEAD: SharedMemory (zero-copy, no syscall per access),
```

## Level 1 — Basic (Fresher / Junior)

---

### Q1. What is a Signal in Linux/Android?

A signal is a **software interrupt** sent to a process to notify it of an event.

**Key points to mention:**
- A form of IPC (Inter-Process Communication)
- Asynchronous notification
- Just a number (e.g. `SIGKILL=9`, `SIGTERM=15`)
- Process can handle, ignore, or use the default action

> **Analogy:** Like a doorbell — someone rings it (sends signal), you decide what to do (handle it).

---

### Q2. What are the three ways to handle a signal?

```c
signal(SIGTERM, SIG_DFL);    // 1. DEFAULT — let the system handle it
signal(SIGINT,  SIG_IGN);    // 2. IGNORE  — discard completely
signal(SIGINT,  my_handler); // 3. CUSTOM  — your own function runs
```

| Option | Description |
|--------|-------------|
| Default | Each signal has a built-in action (terminate, core dump, ignore) |
| Ignore | Signal is silently discarded |
| Custom | Your handler function runs when the signal arrives |

> ⚠️ **Bonus:** `SIGKILL` and `SIGSTOP` **cannot** be caught or ignored.

---

### Q3. What is the difference between `SIGTERM` and `SIGKILL`?

| | `SIGTERM` (15) | `SIGKILL` (9) |
|-|----------------|---------------|
| Can be caught | ✅ Yes | ❌ No |
| Can be ignored | ✅ Yes | ❌ No |
| Shutdown type | Graceful | Immediate |
| Process can clean up | ✅ Yes | ❌ No |
| Shell command | `kill -15 <pid>` | `kill -9 <pid>` |

**Real AOSP example:** `init` sends `SIGTERM` first → waits 5 seconds → if still alive, sends `SIGKILL`.

---

### Q4. What is `SIGUSR1` and `SIGUSR2`?

`SIGUSR1` (10) and `SIGUSR2` (12) are **user-defined signals with no predefined meaning** — you decide what they do.

| Signal | Common use |
|--------|-----------|
| `SIGUSR1` | Reload config / Start / ON / Request |
| `SIGUSR2` | Print status / Stop / OFF / Response |

**In AOSP:**
- `SIGUSR1` → ART uses it to force Garbage Collection
- `SIGUSR2` → Simpleperf uses it for stack sampling

---

### Q5. What is the default action of `SIGUSR1` and `SIGUSR2`?

**Default action = Terminate the process.**

If a process receives `SIGUSR1`/`SIGUSR2` without a registered handler, it **dies**. Always register a handler before using them:

```c
signal(SIGUSR1, my_handler);  // Register FIRST!
```

---

### Q6. What is the difference between `signal()` and `sigaction()`?

| Feature | `signal()` | `sigaction()` |
|---------|-----------|--------------|
| API complexity | Simple | More verbose |
| Portability | Not portable | POSIX standard |
| Handler lifetime | Resets after each call | Persists |
| Extra fault info | ❌ None | ✅ `siginfo_t` |
| Signal masking | ❌ No | ✅ Yes |
| Thread safety | ❌ Race conditions | ✅ Safe |
| Status | Deprecated | ★ Used everywhere in AOSP |

> `sigaction()` is **always** preferred in production code.

---

### Q7. What signals cannot be caught or ignored?

| Signal | Effect |
|--------|--------|
| `SIGKILL` (9) | Always kills the process immediately |
| `SIGSTOP` (19) | Always stops/freezes the process |

**Why?** Safety mechanism — the system must always be able to kill or stop any process, even deadlocked ones.

**In AOSP:**
- `lmkd` uses `SIGKILL` for OOM kills — process cannot escape
- Freezer uses `SIGSTOP` to freeze apps — process cannot escape

---

### Q8. What is `kill()`? Can it only kill processes?

**No!** Despite the name, `kill()` sends **any signal** to a process.

```c
kill(1234, SIGKILL);    // kill process 1234
kill(1234, SIGUSR1);    // send SIGUSR1 to 1234
kill(1234, SIGQUIT);    // send SIGQUIT to 1234
```

**Special `pid` values:**

| `pid` | Effect |
|-------|--------|
| `pid` | Send to specific process |
| `-pgid` | Broadcast to entire process group |
| `0` | Send to own process group |
| `-1` | Send to ALL processes ⚠️ dangerous |

**In AOSP:** AMS calls `kill(app_pid, SIGQUIT)` for ANR; `lmkd` calls `kill(app_pid, SIGKILL)` for OOM.

## Level 2 — Intermediate

### Q9. What is `siginfo_t` and when is it used?

`siginfo_t` is a structure providing **detailed information about a delivered signal**. Available when using `SA_SIGINFO` with `sigaction()`.

**Key fields:**

| Field | Meaning |
|-------|---------|
| `si_signo` | Signal number |
| `si_pid` | PID of sender |
| `si_uid` | UID of sender |
| `si_addr` | Fault address (for `SIGSEGV`, `SIGBUS`) |
| `si_code` | Why the signal was sent |
| `si_value` | Data sent with `sigqueue()` |

```c
void handler(int sig, siginfo_t* info, void* ctx) {
    printf("Signal from PID: %d\n", info->si_pid);
    printf("Fault address:   %p\n", info->si_addr);
}

struct sigaction sa;
sa.sa_sigaction = handler;
sa.sa_flags     = SA_SIGINFO;   // ← enables siginfo_t
sigaction(SIGSEGV, &sa, NULL);
```

**In AOSP:** `debuggerd` uses `si_addr` to log the crash address in tombstone files.

---

### Q10. What is a signal mask? What is `sigprocmask()`?

A **signal mask** is the set of signals that are **blocked** for a process/thread. Blocked signals become **pending** — held and delivered when unblocked.

```c
sigset_t mask, old_mask;
sigemptyset(&mask);
sigaddset(&mask, SIGINT);
sigaddset(&mask, SIGTERM);

sigprocmask(SIG_BLOCK, &mask, &old_mask);   // block; save old mask

// ── Critical section ────────────────────
do_critical_work();
// ─────────────────────────────────────────

sigprocmask(SIG_SETMASK, &old_mask, NULL);  // restore; pending signals delivered now
```

**Three operations:**

| Operation | Effect |
|-----------|--------|
| `SIG_BLOCK` | Add signals to blocked set |
| `SIG_UNBLOCK` | Remove signals from blocked set |
| `SIG_SETMASK` | Replace entire blocked set |

**In AOSP:** ART blocks `SIGQUIT` in all threads **except** the `SignalCatcher` thread.

---

### Q11. What is `sigqueue()`? How is it different from `kill()`?

```
kill()     → sends signal only           (no data)
sigqueue() → sends signal + small int    (with data)
```

```c
// Sender
union sigval val;
val.sival_int = 42;
sigqueue(pid, SIGUSR1, val);

// Receiver — must use SA_SIGINFO
void handler(int sig, siginfo_t* info, void* ctx) {
    int data     = info->si_value.sival_int;  // = 42
    pid_t sender = info->si_pid;
}
```

> **Limitation:** Only one integer or pointer worth of data. For richer payloads use a pipe, socket, or shared memory.

---

### Q12. What is `SIGCHLD`? How does `init` use it?

`SIGCHLD` is sent to a **parent** when its child process exits, is stopped, or is continued.

**`init`'s flow:**
1. `init` forks service processes (`surfaceflinger`, `audioserver`, etc.)
2. Service dies → kernel sends `SIGCHLD` to `init`
3. `init` calls `waitpid()` to reap the zombie
4. Checks if service should restart; restarts if configured

**`init` uses `signalfd()`** instead of a raw handler:
- Converts the signal to an fd event compatible with `epoll()`
- Handles it safely in the main event loop
- Key call: `waitpid(-1, &status, WNOHANG)` — reaps all dead children non-blocking

---

### Q13. What is `signalfd()`? Why does `init` use it instead of a regular handler?

`signalfd()` converts signals into **file descriptor events** — instead of a handler function, you `read()` from an fd.

```c
sigset_t mask;
sigemptyset(&mask);
sigaddset(&mask, SIGCHLD);
sigprocmask(SIG_BLOCK, &mask, NULL);         // block normal delivery

int sfd = signalfd(-1, &mask, SFD_CLOEXEC); // signals → readable fd

epoll_ctl(epoll_fd, EPOLL_CTL_ADD, sfd, &ev);

// In event loop:
struct signalfd_siginfo info;
read(sfd, &info, sizeof(info));              // safe, synchronous
```

| | Traditional handler | `signalfd()` |
|-|--------------------|-------------|
| Execution model | Async, interrupts anywhere | Synchronous, in event loop |
| Functions allowed | Async-signal-safe only | **All** functions allowed |
| `epoll` compatible | ❌ | ✅ |
| Race conditions | Possible | None |

---

### Q14. What are async-signal-safe functions? Why do they matter?

Signal handlers can interrupt execution **at any point**. If your handler calls a function that holds a lock that the interrupted code already holds → **deadlock**.

| ✅ Safe in signal handlers | ❌ Not safe — will deadlock / corrupt |
|---------------------------|--------------------------------------|
| `write()`, `read()` | `printf()` — uses malloc + locks |
| `_exit()` | `malloc()`, `free()` — internal locks |
| `signal()`, `sigaction()` | `syslog()` — uses stdio |
| `kill()`, `getpid()`, `gettid()` | `pthread_*()` — thread locks |

**AOSP solution:** `async_safe_format_log()` in Bionic — lock-free, no malloc, writes directly to `/dev/kmsg`.

**Best practice pattern:**

```c
volatile sig_atomic_t flag = 0;

void handler(int sig) { flag = 1; }   // just set flag — async-safe!

int main() {
    while (1) {
        if (flag) { flag = 0; do_work(); }  // real work done here, safely
    }
}
```

---

### Q15. What is an alternate signal stack? Why is it needed?

An **alternate signal stack** is a separate memory region used to run signal handlers.

**The problem without it:**
```
Stack overflow occurs → SIGSEGV sent → handler tries to run on same stack
                                      → stack still full → handler crashes
                                      → SIGSEGV again → infinite loop!
```

**The solution:** handler runs on its own dedicated stack.

```c
// bionic/libc/bionic/pthread_create.cpp — every thread gets 16 KB
void* stack = mmap(NULL, SIGNAL_STACK_SIZE, PROT_READ | PROT_WRITE, ...);

stack_t ss = { .ss_sp = stack, .ss_size = SIGNAL_STACK_SIZE };
sigaltstack(&ss, NULL);

// Enable in sigaction:
sa.sa_flags = SA_ONSTACK;   // use alternate stack for this handler
```

### Q16. Explain the complete ANR detection flow using signals in AOSP.

```
Step 1  AMS detects app hasn't responded for 5 seconds

Step 2  AMS sends SIGQUIT (3) to app process
        Process.sendSignal(app.pid, SIGQUIT);

Step 3  In the app, ART's SignalCatcher thread:
        → All other threads have SIGQUIT blocked via sigprocmask()
        → SignalCatcher calls sigwait() and waits

Step 4  SignalCatcher receives SIGQUIT:
        → Dumps all thread stacks
        → Writes to /data/anr/traces.txt
        → Logs to logcat

Step 5  AMS waits 200ms for dump to complete

Step 6  AMS shows "App not responding" dialog

Step 7  User clicks "Kill app":
        AMS sends SIGKILL → process dies
```

**Key design points:**
- `SIGQUIT` blocked in **all** threads except `SignalCatcher`
- `sigwait()` used — synchronous, no async-safe restrictions
- Trace always written to `/data/anr/traces.txt`

### Q17. How does ART use `SIGSEGV` for implicit null checks?

A **performance optimization** — ART removes null checks from compiled code and catches the resulting `SIGSEGV` instead.

```
Traditional (slow):                ART (fast):
──────────────────                 ───────────
if (obj == null)                   obj->method();   // no check!
    throw NPE;                     // if null → CPU fault → SIGSEGV
obj->method();                     // ART handler converts → NPE
```

**Flow:**
1. ART registers a `SIGSEGV` handler at startup (`art/runtime/fault_handler.cc`)
2. Compiled code has **no** null checks → faster, smaller
3. `obj == null` → CPU fault → kernel sends `SIGSEGV`
4. ART's handler checks if this is an implicit null check:
   - **Yes** → modify CPU context to throw `NullPointerException`, resume
   - **No** → chain to `debuggerd` → tombstone + crash

> Result: Java sees a normal `NullPointerException` with zero performance overhead for null checks.

---

### Q18. Explain the complete native crash flow from fault to tombstone.

```
1. Fault occurs
   int* ptr = NULL; *ptr = 42;

2. CPU hardware exception
   Invalid memory access detected

3. Kernel delivers SIGSEGV to process

4. Bionic's signal handler runs
   (bionic/debuggerd/handler/debuggerd_handler.cpp)
   → logs "Fatal signal 11 (SIGSEGV) fault addr 0x0"
   → connects to crash_dump via socket
   → sends crash info (pid, tid, signal, registers)
   → waits for crash_dump to finish

5. crash_dump process
   → ptrace(ATTACH) to crashed process
   → reads registers + memory maps (/proc/pid/maps)
   → unwinds call stack (libunwindstack)
   → writes tombstone: /data/tombstones/tombstone_XX
   → logs backtrace to logcat
   → notifies AMS via socket

6. AMS receives crash
   → shows "App has stopped" dialog
   → writes to DropBox
   → broadcasts ACTION_APP_ERROR

7. Process terminates
   → handler re-raises signal with SIG_DFL
   → process dies
```

**Key files:** `debuggerd_handler.cpp` · `crash_dump.cpp` · `/data/tombstones/tombstone_XX`

### Q19. How does `lmkd` use signals for memory management?

`lmkd` = Low Memory Killer Daemon

```
1. Kernel detects memory pressure
   → PSI events via /proc/pressure/memory

2. lmkd reads oom_adj scores:
   oom_adj   0 = Foreground (current app, launcher)
   oom_adj 200 = Background (recently used)
   oom_adj 600 = Cached     (not recently used)
   oom_adj 900 = Empty      (no active components)

3. lmkd selects victim (highest oom_adj)

4. kill(victim_pid, SIGKILL)
   → Process cannot escape — dies immediately
   → Memory freed

5. Repeat until pressure resolved
```

**Why `SIGKILL` not `SIGTERM`?**

| Reason | Detail |
|--------|--------|
| Urgency | Memory pressure is critical — can't wait |
| Reliability | Process might not respond to `SIGTERM` |
| Guarantee | `SIGKILL` always works, even on frozen processes |

### Q20. What is the role of `SIGCHLD` in Zygote's process management?

Zygote is the **parent of all Android app processes**. Every app death sends `SIGCHLD` to Zygote.

```cpp
// Setup — com_android_internal_os_Zygote.cpp
struct sigaction sa;
sa.sa_handler = SigChldHandler;
sa.sa_flags   = SA_NOCLDSTOP;   // only notify on death, not stop
sigaction(SIGCHLD, &sa, NULL);

// Handler — minimal, async-signal-safe only
void SigChldHandler(int sig) {
    gSigChldFlag = 1;
    write(gSigChldPipeFd, "1", 1);  // wake up poll() in main loop
}

// Main loop — all real work done here
if (gSigChldFlag) {
    gSigChldFlag = 0;
    pid_t pid = waitpid(-1, &status, WNOHANG);
    // Report to AMS via socket: "app process X died"
}
```

**`SA_NOCLDSTOP`:** Without it, `SIGCHLD` fires on child stop too. With it, only on child death — Zygote only cares about death.

---

### Q21. How does the Freezer use signals to freeze/thaw app processes?

Android freezes background apps to save battery/CPU using `SIGSTOP` and `SIGCONT`.

| Operation | Signal | Effect |
|-----------|--------|--------|
| Freeze | `SIGSTOP` (19) | Process halted — zero CPU, memory held — **uncatchable** |
| Thaw | `SIGCONT` (18) | Resumes from exact point it was frozen |

**Why not kill them?** Frozen apps resume instantly with state intact — much better UX than restart.

```
SIGKILL → process dies  (gone, memory freed)
SIGSTOP → process frozen (alive, memory held, zero CPU)
```

**Modern Android** uses the cgroup freezer — writing `"FROZEN"` to `cgroup.freeze` causes the kernel to send `SIGSTOP` internally (more reliable than manual signals).

---

### Q22. Why can't you call `malloc()` or `printf()` inside a signal handler?

They are not async-signal-safe — they hold **internal locks**.

```
Main thread:               Signal handler (interrupts main thread):
────────────               ─────────────────────────────────────────
malloc()                   ← signal arrives here!
  acquires heap lock        malloc()
  modifying heap              tries to acquire heap lock
                              → DEADLOCK! lock already held!
```

`printf()` has the same problem — it calls `malloc()` and holds a `FILE*` lock.

```c
// ❌ Wrong — can deadlock
void handler(int sig) { printf("Got signal!\n"); }

// ✅ Right — async-signal-safe
void handler(int sig) { write(STDOUT_FILENO, "Got signal!\n", 12); }
```

**AOSP solution:** `async_safe_format_log()` in Bionic — no locks, no malloc, direct write to `/dev/kmsg`.

---

### Q23. How does ART's `SignalCatcher` thread ensure only it receives `SIGQUIT`?

ART uses a combination of `pthread_sigmask()` and `sigwait()`:

```
Step 1 — In the main thread (before any other threads spawn):
  pthread_sigmask(SIG_BLOCK, &mask_with_SIGQUIT, NULL);
  // New threads INHERIT this mask → all threads have SIGQUIT blocked

Step 2 — Create SignalCatcher thread
  pthread_create(&thread, NULL, SignalCatcher::Run, this);
  // Also inherits blocked mask

Step 3 — Inside SignalCatcher thread:
  sigwait(&mask, &signal_number);
  // Atomically: unblocks SIGQUIT → waits → re-blocks → returns
```

**Result:**
- All threads: `SIGQUIT` blocked
- `SignalCatcher`: waiting via `sigwait()` — the only one that can receive it
- Clean, race-condition-free

**Why not a regular handler?** `sigwait()` is synchronous — no async-safe restrictions. Stack dump requires many non-async-safe functions.

## Level 4 — Scenario / Tricky

---

### Q24. What happens if you send `SIGKILL` to a frozen (`SIGSTOP`) process?

**The process dies immediately.**

`SIGKILL` cannot be blocked, caught, or ignored regardless of the process state.

```
kill(P, SIGSTOP) → P is frozen
kill(P, SIGKILL) → P dies immediately   ← even frozen!
```

**In AOSP:** `lmkd` sends `SIGKILL` to frozen processes when memory is critical — they die immediately.

---

### Q25. What is the difference between pending and blocked signals?

| | Blocked | Pending |
|-|---------|---------|
| What it means | Signal is in the process's signal mask | Signal was sent but not yet delivered |
| When it occurs | Set explicitly via `sigprocmask()` | Naturally follows blocking |
| What happens | Signal is held | Delivered when unblocked |

```c
sigprocmask(SIG_BLOCK, &mask, NULL);    // block SIGINT

// Someone sends SIGINT now → it becomes PENDING

sigset_t pending;
sigpending(&pending);
if (sigismember(&pending, SIGINT)) { /* yes, SIGINT is pending */ }

sigprocmask(SIG_UNBLOCK, &mask, NULL);  // unblock → handler runs NOW
```

> **Important:** Multiple pending signals of the **same type** = **one** delivery (not queued).
> **Exception:** Real-time signals (`SIGRTMIN`+) **are** queued.

---

### Q26. What happens when a signal arrives during another signal handler?

By default, the **same signal is blocked** during its own handler (prevents recursion). But **other signals can interrupt a handler**.

```c
void handler_A(int sig) {   // handling SIGUSR1
    // SIGUSR2 arrives here → handler_B runs
    // After handler_B completes: handler_A resumes
}
```

**Control re-entrancy with `sa_mask`:**

```c
struct sigaction sa;
sigaddset(&sa.sa_mask, SIGUSR2);    // also block SIGUSR2 while handling SIGUSR1
sigaction(SIGUSR1, &sa, NULL);
```

**`SA_NODEFER` flag** — allows the **same** signal to interrupt its own handler:

```c
action.sa_flags = SA_NODEFER;
// Used by debuggerd: allows SIGSEGV inside a SIGSEGV handler
// Necessary for crash dump of crash dump
```

---

### Q27. Can a process send signals to itself? How?

**Yes — multiple ways:**

```c
raise(SIGABRT);              // most common

kill(getpid(), SIGUSR1);     // same as raise()

alarm(5);                    // SIGALRM to self after 5 seconds

abort();                     // internally calls raise(SIGABRT)
```

**Real AOSP usage:**

```c
// Bionic crash handler — re-raise after generating tombstone
void handler(int sig, ...) {
    // ... generate tombstone ...
    signal(sig, SIG_DFL);
    raise(sig);              // re-raise to actually die
}
```

Also: ART raises `SIGSEGV` to itself when a stack overflow is detected → handler converts it to `StackOverflowError`.

---

### Q28. What is `tgkill()` and why is it used instead of `kill()`?

`tgkill()` sends a signal to a **specific thread** within a process.

```c
int tgkill(int tgid, int tid, int sig);
//         ^process   ^thread  ^signal
```

**The problem with `kill()`:**

```
Thread A: waiting for SIGUSR1
Thread B: doing work (no handler)

kill(pid, SIGUSR1) → kernel picks ANY thread → might go to Thread B
                                               → no handler → process terminates!
```

**`tgkill()` fixes this:**

```c
tgkill(pid, thread_a_tid, SIGUSR1);  // goes ONLY to Thread A
```

**In AOSP:** Used by profilers (Simpleperf) to sample specific threads; by `debuggerd` to target the crashing thread; for precise ANR trace targeting.

---

### Q29. How would you design a watchdog using signals?

A watchdog kills a process that fails to "check in" within a timeout:

```c
#include <signal.h>
#include <unistd.h>

volatile int watchdog_fed = 0;

void watchdog_handler(int sig) {
    if (!watchdog_fed) {
        write(STDOUT_FILENO, "WATCHDOG: hung!\n", 16);
        kill(monitor_pid, SIGUSR1);   // notify parent
        raise(SIGKILL);               // self-destruct
    }
    watchdog_fed = 0;   // reset for next window
    alarm(5);           // arm next timeout
}

void feed_watchdog() { watchdog_fed = 1; }

int main() {
    signal(SIGALRM, watchdog_handler);
    alarm(5);   // 5-second window

    while (1) {
        do_some_work();
        feed_watchdog();  // must call within 5 seconds!
    }
}
```

**AOSP equivalent:** `InputDispatcher` watchdog in `system_server` — if the UI thread doesn't respond, it triggers an ANR (`SIGQUIT` for dump, then `SIGKILL` if needed).

**Production watchdog pattern:**
- Parent monitors child via `SIGCHLD`
- Child sends `SIGUSR1` periodically ("I'm alive")
- Parent uses `alarm(timeout)` for the deadline
- No heartbeat → `SIGKILL` child → restart

### Q30. How are signals different from Binder IPC? When would you choose signals?

| Property | Signals | Binder |
|----------|---------|--------|
| Data payload | None (or one int) | Rich structured data |
| Direction | One-way | Two-way |
| Return value | ❌ None | ✅ Yes |
| Synchronous | ❌ No | ✅ Yes (optional) |
| Works if process frozen | ✅ **Yes** | ❌ No |
| Works if process hung | ✅ **Yes** | ❌ No (timeout) |
| Overhead | Very low | Higher |
| Error handling | Limited | Rich exceptions |
| Threading complexity | Complex | Handled by Binder |

**Choose Signals when:**

| Scenario | Why Signals |
|----------|------------|
| Process control (kill/stop/freeze) | `SIGKILL`, `SIGSTOP`, `SIGCONT` |
| Emergency / out-of-band | Process may be deadlocked — Binder would hang |
| Lifecycle events | `SIGCHLD` for death notifications |
| Simple boolean notifications | "Reload config", "Dump traces" |
| Target might not be listening | Signals delivered regardless |

**Real AOSP decision tree:**
```
Normal communication    → Binder
App might be frozen     → SIGQUIT  (ANR dump)
App must die now        → SIGKILL  (force stop)

Signals = the FALLBACK when Binder can't work!
```

## Quick Revision Cheat Sheet

### Signal APIs

| API | Purpose |
|-----|---------|
| `kill(pid, sig)` | Send any signal to a process or group |
| `sigqueue(pid, sig, val)` | `kill()` + integer data payload |
| `raise(sig)` | Send signal to yourself |
| `tgkill(pid, tid, sig)` | Send to a specific thread |
| `alarm(n)` | Send `SIGALRM` to self after `n` seconds |
| `signal()` | Simple handler registration (deprecated) |
| `sigaction()` | Full handler registration — use this |
| `sigprocmask()` | Block/unblock signals |
| `sigwait()` | Synchronously wait for a signal |
| `signalfd()` | Convert signals to `epoll`-able fd events |

### Uncatchable Signals

```
SIGKILL (9)   → always kills     — cannot be caught, blocked, or ignored
SIGSTOP (19)  → always freezes   — cannot be caught, blocked, or ignored
```

### AOSP Signal IPC Map

```
AMS    ──SIGQUIT──► App       (ANR trace dump)
AMS    ──SIGKILL──► App       (force stop)
lmkd   ──SIGKILL──► App       (OOM kill)
init   ──SIGHUP───► Service   (reload config)
init   ──SIGTERM──► Service   (graceful stop)
init   ──SIGKILL──► Service   (force stop)
init   ◄──SIGCHLD── Service   (died → reap + maybe restart)
crash  ──SIGSEGV──► debuggerd (tombstone)
```

### Key Facts

| Topic | Fact |
|-------|------|
| `SIGUSR1` | Signal 10 — ART uses for forced GC |
| `SIGUSR2` | Signal 12 — Simpleperf uses for stack sampling |
| Async-safe | `write()` ✅  `printf()` ❌ |
| Alternate stack | 16 KB per thread — needed for stack overflow handling |
| `signalfd` | Converts signals to fd events for use with `epoll` |
| ART null checks | `SIGSEGV` → converted to `NullPointerException` |
| ART `SignalCatcher` | Uses `sigwait()` for `SIGQUIT` — only thread that can receive it |
| `init` + `SIGCHLD` | Uses `signalfd` + `epoll` — not a raw signal handler |
