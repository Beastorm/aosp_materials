## 1. Files

**One process writes data to a file; another reads from the same file.**

```
┌───────────┐                         ┌───────────┐
│ Process A │                         │ Process B │
│           │    ┌───────────────┐    │           │
│  WRITE ───┼───►│   FILE        │◄───┼── READ    │
│           │    │ /data/app/... │    │           │
└───────────┘         DISK            └───────────┘
```

```java
// Process A - Writing
File file = new File(context.getFilesDir(), "shared_data.txt");
FileOutputStream fos = new FileOutputStream(file);
fos.write("Hello from Process A".getBytes());
fos.close();

// Process B - Reading
FileInputStream fis = new FileInputStream(file);
byte[] data = new byte[1024];
fis.read(data);
String message = new String(data).trim();
fis.close();
```

**✅ When to USE:**

| Scenario | Why |
|---|---|
| Storing configuration/settings | Persistent, survives reboot |
| Sharing large data (images, videos) | No size limit |
| SharedPreferences | Android's built-in file-based storage |
| Logging | Multiple processes can write logs |
| Data that needs to persist | Files survive process death |

**❌ When NOT to USE:**

| Scenario | Why Not |
|---|---|
| Real-time communication | Too SLOW (disk I/O) |
| Frequent small messages | High overhead per operation |
| Synchronization needed | No built-in locking mechanism |
| Low-latency requirements | Disk access is 1000× slower than memory |

## 2. Signals

**A software interrupt to notify a process about an event. One-way, no data payload.**

```
┌───────────┐    SIGNAL (e.g., SIGKILL)    ┌───────────┐
│           │ ──────────────────────────►   │           │
│ Process A │    (just a number, no data)   │ Process B │
│ (Sender)  │                              │  ☠️ DIES   │
└───────────┘                              └───────────┘
```

**Common Android Signals:**

```
┌──────────┬───────┬────────────────────────────┐
│ Signal   │ Number│ Purpose                    │
├──────────┼───────┼────────────────────────────┤
│ SIGKILL  │   9   │ Force kill process         │
│ SIGTERM  │  15   │ Graceful termination       │
│ SIGSTOP  │  19   │ Pause/Freeze process       │
│ SIGCONT  │  18   │ Resume paused process      │
│ SIGUSR1  │  10   │ User-defined signal        │
│ SIGSEGV  │  11   │ Segmentation fault (crash) │
└──────────┴───────┴────────────────────────────┘
```

**Android System Using Signals:**

```
ActivityManagerService (system_server)
  "App not responding" / Low memory killer
          │
          │ SIGKILL (9)
          ▼
   Your App Process  ☠️ killed immediately, no cleanup

ANR Detection:
  system_server sends SIGQUIT (3) to app
  → App dumps stack trace into /data/anr/
```

**✅ When to USE:** Process lifecycle management, ANR detection, crash handling (SIGSEGV), Low Memory Killer, simple process notifications.

**❌ When NOT to USE:** Transferring data, complex communication, app-to-app IPC, reliable/two-way communication, normal app development.

## 3. Sockets

**A bidirectional communication endpoint — works locally or across networks.**

```
┌───────────┐◄────── Two-Way Channel ─────►┌───────────┐
│ Process A │                              │ Process B │
│ (Client)  │    ┌──────────────────┐      │ (Server)  │
│  Socket ──┼───►│  DATA STREAM     │◄─────┼── Socket  │
└───────────┘    └──────────────────┘      └───────────┘
```

**Types of Sockets in Android:**

```
1. UNIX Domain Sockets (Local — same device)
   Process A ◄──/dev/socket/zygote──► Process B
   • Fastest socket type, no network overhead
   • Used heavily in Android system

2. TCP/IP Sockets (Network capable)
   Client ◄──192.168.1.1:8080──► Server
   • Can work across devices, higher overhead

3. LocalSocket (Android-specific Java wrapper)
   App ◄──abstract namespace──► Service
```

**How Android Uses Sockets:**

```
ZYGOTE CONNECTION (Unix Domain Socket):
  system_server ◄──/dev/socket/zygote──► Zygote
  "Fork new app process" → fork() → New App Process

ADB CONNECTION (TCP Socket):
  adb client (PC) ◄──TCP port 5037──► adbd daemon (Phone)

NETWORK COMMUNICATION:
  Your App ◄──TCP port 443──► Web Server (Internet)
```

```java
// Server (in a Service)
ServerSocket serverSocket = new ServerSocket(8080);
Socket client = serverSocket.accept();
BufferedReader in = new BufferedReader(
        new InputStreamReader(client.getInputStream()));
String message = in.readLine();

// Client (in another process)
Socket socket = new Socket("localhost", 8080);
PrintWriter out = new PrintWriter(socket.getOutputStream(), true);
out.println("Hello Server");
```

**✅ When to USE:** Network communication, cross-device IPC, system daemon communication, bidirectional streaming, large data transfer.

**❌ When NOT to USE:** Simple same-device app-to-app (use Binder), Activity to Service (use Binder/Intent), high-frequency small messages.

## 4. Pipes

**A unidirectional data channel. Data flows in ONE direction.**

```
┌───────────┐     ┌──════════════──┐       ┌───────────┐
│ Process A │────►│  PIPE ──────►  │──────►│ Process B │
│ (Writer)  │     └──════════════──┘       │ (Reader)  │
└───────────┘     One direction only       └───────────┘
```

**Types of Pipes:**

```
1. ANONYMOUS PIPE (Unnamed)
   • Only between PARENT-CHILD processes
   • Created by pipe() system call
   • Disappears when processes end

2. NAMED PIPE (FIFO)
   • Any processes can use (via file path: /data/myfifo)
   • Exists as a special file in filesystem

3. ParcelFileDescriptor.createPipe() [Android]
   • Android's Java wrapper for pipes
   • Used in ContentProvider for large data
```

**How Android Uses Pipes:**

```
ContentProvider openFile() Pattern:
  App A (Consumer)  ◄──PIPE fd[0]──  ContentProvider (App B)
  InputStream                          OutputStream → write data

Zygote Fork:
  system_server ──"fork app X"──► Zygote → fork() → New Process
  system_server ◄──"PID=12345"─── Zygote

Looper EventQueue (internally uses pipe/eventfd):
  Worker Thread ──write──► PIPE ──read──► Looper → Handler
```

```java
// Android Pipe in ContentProvider
ParcelFileDescriptor[] pipe = ParcelFileDescriptor.createPipe();
ParcelFileDescriptor readEnd  = pipe[0];  // Give to consumer
ParcelFileDescriptor writeEnd = pipe[1];  // Provider writes here

new Thread(() -> {
    FileOutputStream fos = new FileOutputStream(writeEnd.getFileDescriptor());
    fos.write(largeData);
    fos.close();
}).start();

return readEnd;  // Return read end to caller
```

**Bidirectional Communication with 2 Pipes:**

```
Process A ────► PIPE 1 ────► Process B
Process A ◄──── PIPE 2 ◄──── Process B
```

**✅ When to USE:** Parent-child process communication, streaming large data via ContentProvider, producer-consumer pattern, Looper/MessageQueue wakeup.

**❌ When NOT to USE:** Unrelated processes (anonymous pipes need parent-child), multiple readers/writers, bidirectional (complex with 2 pipes), normal Android app IPC.

## 5. Semaphores

**A synchronization mechanism for controlling access to shared resources using a counter. NOT for data transfer — it's a traffic signal.**

```
Semaphore = Counter (e.g., starts at 1)

Process A: acquire() → Counter 1→0 → "Go ahead!" ✅
Process B: acquire() → Counter=0  → "WAIT! Busy!" 🚫

Process A finishes → release() → Counter 0→1
Process B: UNBLOCKED → Counter 1→0 → "Go ahead!" ✅
```

**Types:**

```
Binary Semaphore (counter = 0 or 1):
  Only one thread at a time → mutex-like behavior

Counting Semaphore (counter = N):
  Database connection pool (max 3):
  Thread 1: acquire() → counter=2 ✅
  Thread 2: acquire() → counter=1 ✅
  Thread 3: acquire() → counter=0 ✅
  Thread 4: acquire() → counter=0 ❌ BLOCKED
  Thread 1: release() → counter=1
  Thread 4: UNBLOCKED → counter=0 ✅
```

**How Android Uses Semaphores:**

```java
// 1. java.util.concurrent.Semaphore
Semaphore sem = new Semaphore(3);
sem.acquire();   // wait / decrement
// ... use resource ...
sem.release();   // signal / increment

// 2. Native Code (NDK)
#include <semaphore.h>
sem_t sem;
sem_init(&sem, 1, 1);  // pshared=1 for inter-process
sem_wait(&sem);        // P operation
sem_post(&sem);        // V operation
```

```java
// Limiting concurrent network requests to 3
Semaphore networkSemaphore = new Semaphore(3);

void makeNetworkRequest() throws InterruptedException {
    networkSemaphore.acquire();
    try { /* make HTTP request */ }
    finally { networkSemaphore.release(); }
}
```

**✅ When to USE:** Controlling concurrent access, connection pool management, rate limiting, producer-consumer sync, NDK synchronization.

**❌ When NOT to USE:** Data transfer (carries no data), app-to-app communication, simple locking (use `synchronized`/`ReentrantLock`), normal app development.

## 6. Shared Memory

**A region of memory mapped into multiple processes' address space. FASTEST IPC — zero copies.**

```
┌───────────────────────────────────────────────────────┐
│                    PHYSICAL MEMORY                    │
│         ┌──────────────────────────────────┐          │
│         │     SHARED MEMORY REGION         │          │
│         │  Data: "Hello!"                  │          │
│         └──────────┬──────────┬────────────┘          │
│                    │ mapped   │ mapped                 │
│               ┌────▼────┐ ┌──▼──────┐                │
│               │Process A│ │Process B│                │
│               │ptr=0x1000│ │ptr=0x5000│               │
│               │*ptr → "Hello!"       │                │
│               └─────────┘ └─────────┘                │
│                                                       │
│  ⚡ NO COPYING! Both processes see the same memory    │
└───────────────────────────────────────────────────────┘
```

**Android Implementations:**

```java
// SharedMemory API (API 27+)
SharedMemory sharedMemory = SharedMemory.create("myRegion", 1024);
ByteBuffer buf = sharedMemory.mapReadWrite();
buf.putInt(42);                                    // Write
sharedMemory.setProtect(OsConstants.PROT_READ);    // Make read-only

// Pass to another process via Binder (SharedMemory is Parcelable)
// parcel.writeParcelable(sharedMemory, 0);

// Process B:
ByteBuffer readBuf = sharedMemory.mapReadOnly();
int value = readBuf.getInt();   // 42
```

**Real-World Use Cases:**

```
GRAPHICS BUFFER (SurfaceFlinger):
  App draws directly into shared GraphicBuffer
  SurfaceFlinger reads same buffer → displays on screen
  NO DATA COPYING → Ultra fast!
  At 30fps = 240MB/sec — impossible with copies!

CURSOR DATA (ContentProvider):
  CursorWindow (backed by Ashmem) shares DB results
  without copying between processes

AUDIO (AudioFlinger):
  Music App ──SHM──► AudioFlinger ──SHM──► Audio HAL
  Lock-free ring buffers → latency <10ms
```

**Performance Comparison:**

```
Transfer 1MB:
Shared Memory  ▓▓            0.001ms  (pointer access)
Binder         ▓▓▓▓▓▓▓▓     0.5ms    (1 copy)
Socket         ▓▓▓▓▓▓▓▓▓▓▓▓ 1.2ms    (2 copies)
Intent         ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓ 2.0ms+ (bundle)
```

**✅ When to USE:** Large data transfer, graphics/video buffers, Cursor data, real-time audio/video, high-frequency data exchange, NDK performance-critical code.

**❌ When NOT to USE:** Small data transfer, simple messages/commands, without proper synchronization (race conditions!), security-sensitive data.

## 7. Binder (Android's Primary IPC)

**Android's custom IPC mechanism built as a kernel driver. The backbone of ALL Android system services.**

```
┌────────┐     ┌──────────────┐      ┌────────┐
│ App A  │────►│ BINDER DRIVER│─────►│ App B  │
│(Client)│     │  (Kernel)    │      │(Server)│
│        │◄────│ /dev/binder  │◄─────│        │
└────────┘     └──────────────┘      └────────┘

Features:
• ONE copy (kernel maps memory)
• Built-in security (PID/UID verification — unforgeable!)
• Object-oriented RPC
• Thread pool management
• Death notification (DeathRecipient)
• Reference counting
```

**How Binder Works:**

```
Client: locationService.getLastLocation()  (looks like a local call!)
        │
        ▼
Proxy: marshals data → Parcel { transaction code, parameters }
        │
        ▼
Binder Driver (Kernel):
  1. Verify caller UID/PID
  2. ONE COPY to server's memory space
  3. Wake up server thread
        │
        ▼
Stub: onTransact() → reads Parcel → calls real implementation
        │
        ▼
Service: Location loc = getLastKnownLocation(); return loc;
        │ (reply goes back same path)
        ▼
Client: receives Location(lat=37.7, lng=-122.4) ✓
```

**Copy Count Comparison:**

```
Traditional IPC (Socket/Pipe):
  Sender ──COPY1──► Kernel Buffer ──COPY2──► Receiver   (2 copies)

Binder IPC:
  Sender ──COPY1──► Kernel (mmap'd to Receiver's space)  (1 copy)
  Receiver reads directly — no second copy!

Shared Memory:
  Sender → Shared Region ← Receiver   (0 copies, but no security)
```

**AIDL — Auto-generates Proxy and Stub:**

```java
// IMyService.aidl
interface IMyService {
    int add(int a, int b);
    String getName();
}
// Android build tool auto-generates Stub (server) and Stub.Proxy (client)
```

```java
// Server
public class MyService extends Service {
    private final IMyService.Stub binder = new IMyService.Stub() {
        @Override public int add(int a, int b) { return a + b; }
        @Override public String getName()      { return "Android"; }
    };
    @Override public IBinder onBind(Intent intent) { return binder; }
}

// Client
IMyService service = IMyService.Stub.asInterface(binder);
int result = service.add(3, 4);  // = 7
// Looks local! Actually crosses process boundary via Binder.
```

**Security Model:**

```
Every Binder transaction carries UID + PID set by KERNEL (cannot be faked!)

Malicious App (UID=10087): "Give me system data"
System Service: checks UID → No permission → DENIED ✗

Compare with Socket:
Malicious App: "I'm system_server" (can LIE about identity)
Service: No way to verify! 😱
```

**Everything in Android Uses Binder:**

```
Your App ──startActivity()──► Intent ──► Binder ──► ActivityManagerService
Your App ──getContentResolver()──► Binder ──► ContentProvider
Your App ──context.getSystemService("location")──► Binder ──► LocationManagerService
Intents, Broadcasts, ContentProviders, Messenger — all built on Binder!
```

**✅ When to USE:** App to System Service (THE way), app-to-app IPC, AIDL services, Intents/Broadcasts, ContentProviders — whenever possible in Android.

**❌ When NOT to USE:** Very large data (>1MB transaction limit), network communication, sharing large buffers (use Shared Memory instead), streaming data.

```

│                     GOLDEN RULES                           │
│                                                            │
│  🥇 BINDER      → Default choice for Android IPC          │

│  For normal Android app development:                       │
```
