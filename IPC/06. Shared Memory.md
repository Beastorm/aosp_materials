# Shared Memory IPC in Android — Complete Guide

## What is Shared Memory IPC?

Shared Memory IPC allows two or more processes to access the **same region of memory** directly — making it the **fastest form of IPC** because data doesn't need to be copied between processes.

---

## Core Concept

```
┌─────────────────────────────────────────────────────────┐
│                    PHYSICAL MEMORY (RAM)                 │
│                                                         │
│         ┌─────────────────────────────┐                 │
│         │    SHARED MEMORY REGION     │                 │
│         │    (e.g., 4KB - several MB) │                 │
│         └──────────┬──────────────────┘                 │
│                    │                                    │
│         ┌──────────┴──────────┐                         │
│         │                     │                         │
│    ┌────▼─────┐         ┌────▼─────┐                   │
│    │ Process A │         │ Process B │                   │
│    │ (Writer)  │         │ (Reader)  │                   │
│    └──────────┘         └──────────┘                    │
│                                                         │
│    Both processes see the SAME physical memory           │
│    mapped into their own virtual address space           │
└─────────────────────────────────────────────────────────┘
```

### Why is it Fast?

```
Traditional IPC (e.g., Binder):
Process A ──copy──► Kernel Buffer ──copy──► Process B
                    (2 copies!)

Shared Memory:
Process A ──write──► Shared Region ◄──read── Process B
                    (0 copies! Same memory!)
```

## 1. Ashmem — Anonymous Shared Memory

Ashmem is Android's custom kernel driver for shared memory. It's like Linux's `shmem` but with Android-specific features like memory pinning/unpinning.

### How Ashmem Works Step by Step

```
Step 1: Process A creates shared memory
  fd = open("/dev/ashmem")
  ioctl(fd, SET_NAME, "my_mem")
  ioctl(fd, SET_SIZE, 4096)
  → Kernel creates ashmem region, returns fd

Step 2: Process A maps the memory
  ptr = mmap(fd, 4096, ...)
  ptr ────────► [Shared Memory Region]

Step 3: Send fd to Process B via Binder
  Process A ──fd──Binder──► Process B

Step 4: Process B maps the SAME memory
  ptr = mmap(fd, 4096, ...)
  ptr ────────► [SAME Shared Memory Region]
```

## 2. SharedMemory API (Java — API 27+)

### Simple Example: Producer-Consumer

```java
// ═══════════════════════════════════════════
// PROCESS A — The PRODUCER (e.g., a Service)
// ═══════════════════════════════════════════

// Step 1: Create shared memory region
SharedMemory sharedMemory = SharedMemory.create("my_shared_data", 1024);

// Step 2: Map it to write
ByteBuffer buffer = sharedMemory.mapReadWrite();

// Step 3: Write data
buffer.putInt(42);
buffer.put("Hello from Process A!".getBytes());

// Step 4: Make read-only for safety
SharedMemory.unmap(buffer);
sharedMemory.setProtect(OsConstants.PROT_READ);

// Step 5: Send to Process B via Binder (SharedMemory implements Parcelable)
```

```java
// ═══════════════════════════════════════════
// PROCESS B — The CONSUMER (e.g., a Client)
// ═══════════════════════════════════════════

// Step 1: Receive SharedMemory from Binder
// SharedMemory sharedMemory = service.getSharedMemory();

// Step 2: Map it to read
ByteBuffer buffer = sharedMemory.mapReadOnly();

// Step 3: Read data
int number = buffer.getInt();           // 42
byte[] strBytes = new byte[21];
buffer.get(strBytes);
String message = new String(strBytes);  // "Hello from Process A!"

// Step 4: Cleanup
SharedMemory.unmap(buffer);
sharedMemory.close();
```

### Complete Working Example with AIDL

**AIDL Interface**

```java
// ISharedMemoryService.aidl
package com.example.shmem;

interface ISharedMemoryService {
    SharedMemory getSharedMemory();
}
```

**Service (Process A)**

```java
public class SharedMemoryService extends Service {

    private SharedMemory sharedMemory;

    @Override
    public void onCreate() {
        super.onCreate();
        try {
            sharedMemory = SharedMemory.create("sensor_data", 4096);

            ByteBuffer buffer = sharedMemory.mapReadWrite();
            buffer.putFloat(23.5f);                      // temperature
            buffer.putFloat(65.2f);                      // humidity
            buffer.putFloat(1013.0f);                    // pressure
            buffer.putLong(System.currentTimeMillis());  // timestamp
            SharedMemory.unmap(buffer);

            sharedMemory.setProtect(OsConstants.PROT_READ);  // read-only
        } catch (ErrnoException e) {
            e.printStackTrace();
        }
    }

    private final ISharedMemoryService.Stub binder =
        new ISharedMemoryService.Stub() {
            @Override
            public SharedMemory getSharedMemory() { return sharedMemory; }
        };

    @Override public IBinder onBind(Intent intent) { return binder; }
}
```

**Client (Process B)**

```java
public class ClientActivity extends AppCompatActivity {

    private ISharedMemoryService service;

    private ServiceConnection connection = new ServiceConnection() {
        @Override
        public void onServiceConnected(ComponentName name, IBinder binder) {
            service = ISharedMemoryService.Stub.asInterface(binder);
            readSharedData();
        }
        @Override public void onServiceDisconnected(ComponentName name) { service = null; }
    };

    private void readSharedData() {
        try {
            SharedMemory sharedMemory = service.getSharedMemory();
            ByteBuffer buffer = sharedMemory.mapReadOnly();

            float temp     = buffer.getFloat();   // 23.5
            float humidity = buffer.getFloat();   // 65.2
            float pressure = buffer.getFloat();   // 1013.0
            long timestamp = buffer.getLong();

            Log.d("Client", "Temp: " + temp + " Humidity: " + humidity);

            SharedMemory.unmap(buffer);
            sharedMemory.close();
        } catch (Exception e) {
            e.printStackTrace();
        }
    }
}
```

## 3. Native (C/C++) Shared Memory

```cpp
// ═══════════════════════════════════════
// PROCESS A — Native Producer
// ═══════════════════════════════════════

#include <android/sharedmem.h>
#include <sys/mman.h>

// Step 1: Create shared memory
int fd = ASharedMemory_create("native_buffer", 4096);

// Step 2: Map it
void* ptr = mmap(NULL, 4096, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);

// Step 3: Write data
struct SensorData { float temperature; float humidity; int64_t timestamp; };

SensorData* data = (SensorData*)ptr;
data->temperature = 25.3f;
data->humidity    = 70.1f;
data->timestamp   = time(NULL);

// Step 4: Restrict to read-only
ASharedMemory_setProt(fd, PROT_READ);

// Step 5: Send fd to other process (via Binder/socket)
```

```cpp
// ═══════════════════════════════════════
// PROCESS B — Native Consumer
// ═══════════════════════════════════════

// Step 1: Receive fd from Process A
void* ptr = mmap(NULL, 4096, PROT_READ, MAP_SHARED, fd, 0);

SensorData* data = (SensorData*)ptr;
printf("Temperature: %.1f\n", data->temperature);
printf("Humidity: %.1f\n",    data->humidity);

munmap(ptr, 4096);
close(fd);
```

## 4. How File Descriptor Sharing Works

```
┌──────────────────────────────────────────────────────────────┐
│           FILE DESCRIPTOR PASSING MECHANISM                   │
│                                                               │
│  Process A             Kernel              Process B          │
│  fd = 5  ──Binder──►  Translate  ──Binder──►  fd = 8        │
│                        fd 5 in A                             │
│                          to                                   │
│  Points to ──────────►  fd 8 in B  ◄────── Points to        │
│  same kernel                                same kernel       │
│  file object                                file object       │
│                                                               │
│  ❗ fd numbers are different, but point to the SAME          │
│     underlying kernel object (shared memory region)          │
└──────────────────────────────────────────────────────────────┘
```

**Methods to share fd:**

```
1. Binder Transaction (most common)
   └── ParcelFileDescriptor / SharedMemory (Parcelable, sent via AIDL)

2. Unix Domain Socket
   └── sendmsg() with SCM_RIGHTS (used by system services)

3. Inherited via fork()
   └── Child gets copy of parent's fd table (Zygote → App process)
```

## 6. Synchronization — The Critical Challenge

Shared memory has **no built-in synchronization**. You must handle it yourself!

```
THE RACE CONDITION PROBLEM:

  Process A (Writer)         Process B (Reader)
  Write byte 1: 'H'
  Write byte 2: 'e'
                             Read: "He" + garbage! 💥
  Write byte 3: 'l'
  Write byte 4: 'l'
  Write byte 5: 'o'
                             Read: "Hello" ✅

  Problem: Reader sees PARTIAL writes!
```

### Synchronization Solutions

```
1. Mutex/Futex (in shared memory itself)
   pthread_mutex with PTHREAD_PROCESS_SHARED
   ✅ Fast  ❌ Complex to set up

2. Atomic Operations
   std::atomic / AtomicInteger
   ✅ Lock-free  ❌ Only for simple data types

3. Ring Buffer / Circular Buffer
   Single producer, single consumer
   ✅ Lock-free  ✅ High throughput

4. Binder notification + Shared Memory
   Write to shmem → notify via Binder
   ✅ Simple  ❌ Binder overhead for notification

5. eventfd / pipe for signaling
   Write data → signal via eventfd
   ✅ Lightweight  ✅ Works well with epoll
```

### Ring Buffer Layout (Lock-Free)

```
Shared Memory:
┌──────┬──────┬────────────────────────────────────┐
│write │read  │         Data Buffer                 │
│index │index │                                     │
│(atom)│(atom)│  [0] [1] [2] [3] [4] [5] [6] [7]  │
│  =5  │  =2  │   D   D   .   .   .   .   .   .   │
└──────┴──────┴────────────────────────────────────┘
                ▲           ▲
              read_idx    write_idx
             (consumer)  (producer)

Producer writes at write_index, increments atomically
Consumer reads at read_index, increments atomically
No locks needed for single-producer single-consumer!
```

```cpp
struct SharedRingBuffer {
    std::atomic<uint32_t> write_idx;
    std::atomic<uint32_t> read_idx;
    uint32_t capacity;
    char data[];

    bool produce(const void* item, size_t size) {
        uint32_t w = write_idx.load(std::memory_order_relaxed);
        uint32_t r = read_idx.load(std::memory_order_acquire);
        if ((w - r) >= capacity) return false;  // Full!
        memcpy(&data[(w % capacity) * size], item, size);
        write_idx.store(w + 1, std::memory_order_release);
        return true;
    }

    bool consume(void* item, size_t size) {
        uint32_t r = read_idx.load(std::memory_order_relaxed);
        uint32_t w = write_idx.load(std::memory_order_acquire);
        if (r == w) return false;  // Empty!
        memcpy(item, &data[(r % capacity) * size], size);
        read_idx.store(r + 1, std::memory_order_release);
        return true;
    }
};
```

## 8. Real-World Use Cases

### Camera Preview (CameraService → App)

```
Camera HAL (Native Process) ──► Shared Memory (GraphicBuffer) ◄── Camera App

Frame: 1920 × 1080 × 4 bytes = ~8MB per frame
At 30fps = 240MB/sec

❗ Without shared memory, 30fps camera preview would be
   IMPOSSIBLY slow due to massive data transfer overhead
```

### Audio Streaming (AudioFlinger)

```
Music App ──SHM──► AudioFlinger ──SHM──► Audio HAL
(generate PCM)    (mix streams)          (output to DAC)

Each stage uses ring buffers in shared memory:
✅ Low latency audio (<10ms)
✅ Zero-copy between processes
✅ Lock-free ring buffers for real-time performance
```

### SurfaceFlinger (UI Rendering)

```
App 1 (Gmail)    App 2 (StatusBar)    App 3 (NavBar)
     │                 │                    │
     ▼                 ▼                    ▼
 BufferQueue       BufferQueue         BufferQueue    ← GraphicBuffers (SHM!)
     │                 │                    │
     └─────────────────┼────────────────────┘
                        │
                        ▼
               SurfaceFlinger (Compositor)
               Composites all layers
                        │
                        ▼
                  Display Hardware

Each BufferQueue uses triple-buffering:
┌────────┐  ┌────────┐  ┌────────┐
│Buffer 0│  │Buffer 1│  │Buffer 2│
│(drawing)│  │(queued)│  │(display)│
└────────┘  └────────┘  └────────┘
```

### Machine Learning Inference

```
Camera App                         ML Service
Capture frame (1920×1080)          TFLite Model (Object Detect)
       │                                  │
       └──────► Shared Memory (8MB) ◄─────┘
                ┌──────────────┐
                │  Image Data  │  ← Camera writes
                ├──────────────┤
                │  Results     │  ← ML service writes
                │  [{box, cls}]│
                └──────────────┘

✅ No need to serialize/deserialize 8MB image

### Multi-Process Browser-like App

```
Main Process (UI)           Renderer Process (Web Content)
  Display bitmap                Parse HTML/CSS, Render, Paint
        │                              │
        └──► Shared Memory (Bitmap) ◄──┘

## 9. Security Considerations

```
┌─────────────────────────────────────────────────────────────┐
│  1. FD-Based Access Control                                 │
│     Only processes that RECEIVE the fd can access memory    │
│     Process A ──fd──► Process B  ✅ Can access             │
│     Process C (never got fd)     ❌ Cannot access          │
│                                                             │
│  2. Protection Flags                                        │
│     PROT_READ             → Read only (consumer)            │
│     PROT_READ | PROT_WRITE → Read/Write                    │
│                                                             │
│     ⚠️ Protection can only be REDUCED, never increased      │
│     PROT_READ|WRITE → PROT_READ  ✅                        │
│     PROT_READ → PROT_READ|WRITE  ❌                        │
│                                                             │
│  3. SELinux Policy                                          │
│     Controls which processes can create and share regions   │
└─────────────────────────────────────────────────────────────┘
```

## When to Use Shared Memory

```
┌──────────────────────────────────────────────────────────────┐
│                    DECISION FLOWCHART                         │
│                                                              │
│              How much data to transfer?                       │
│                       │                                      │
│           ┌───────────┼───────────┐                          │
│           │           │           │                          │
│        < 1KB       1KB-1MB      > 1MB                       │
│           │           │           │                          │
│           ▼           ▼           ▼                          │
│       Use Binder  Use Binder   Need real-time                │
│       (Intent,    with          or continuous?               │
│        Messenger) Parcels      YES → SHARED MEMORY ✅        │
│                                NO  → Binder+Parcel           │
│                                                              │
│  USE SHARED MEMORY WHEN:                                     │
│  ✅ Large data (images, audio, video frames)                 │
│  ✅ High frequency updates (sensor data, 60fps rendering)    │
│  ✅ Low latency required (audio < 10ms)                      │
│  ✅ Multiple readers for same data                           │
│  ✅ Zero-copy is essential                                   │
│                                                              │
│  DON'T USE WHEN:                                             │
│  ❌ Small data (< 1KB) — Binder is simpler                  │
│  ❌ One-time RPC calls — overkill                            │
│  ❌ Security-critical — harder to validate data              │
│  ❌ Need automatic synchronization                           │
└──────────────────────────────────────────────────────────────┘
```

## Summary

| Aspect | Details |
|---|---|
| **What** | Mapping same physical memory into multiple process address spaces |
| **Why** | Zero-copy, fastest IPC, essential for multimedia |
| **How** | SharedMemory API (Java) / ASharedMemory (NDK) / ashmem (kernel) |
| **fd sharing** | Via Binder (Parcelable), Unix sockets, or fork inheritance |
| **Sync** | Manual — use atomics, mutexes, ring buffers, or Binder notifications |
| **Android uses** | Camera, Audio, SurfaceFlinger, GPU buffers, Sensors |
| **Limitations** | No built-in sync, complex error handling, API 27+ for Java |
