# A Deep Dive into the Android Boot Process: Step-by-Step Breakdown

## Introduction

The Android boot process is an intricate sequence that takes place from the moment
you **power on** an Android device to the point where the system is **ready for user
interaction**. This process involves several key stages, each of which is crucial for
initializing the hardware and software components that make up the Android operating
system.

In this article, we will explore each phase of the boot process in meticulous detail,
highlighting the **role** and **functioning** of the components involved.

## Let's Begin the Android Boot Process Exploration! 💪

---

## Stage 1: Boot ROM

When the device is **powered on**, the first thing that happens is that the power
supply changes to a **powered-up state**. When the power supply senses that board
power levels have stabilized, it sends a **RESET signal** to the CPU. This signal
causes the CPU to load data from **Boot ROM** and start executing it. This is a small
piece of code that is **hardwired** in the CPU ASIC (Application Specific Integrated
Circuit).

### What is Boot ROM?

The boot process begins with the **Boot ROM**, a small piece of **immutable code**
embedded into the device's hardware, typically within the **System-on-Chip (SoC)**.
This code is the **first thing executed** when the device is powered on.

The Boot ROM's role is generally quite limited:

- Initializing some basic hardware components like **clocks**, **power controllers**,
  and some **on-chip memory** (usually internal SRAM).
- It does **NOT** initialize full system memory (RAM) at this stage.
- This is because it doesn't yet have access to the external **DRAM** and doesn't
  yet know how much DRAM is installed or how it's configured.

### Key Responsibilities

- Uses a small amount of **on-chip memory (internal SRAM)** for its execution.
- Finds and loads the **Primary Bootloader (PBL)** into on-chip SRAM.
- Searches for the bootloader in predefined storage locations such as:
  - eMMC
  - NAND flash
  - SD card
- The exact location is typically **hardcoded** based on the device's architecture.

### Boot ROM Flow

1. Establishes the **boot media sequence**.
2. Loads the **first stage bootloader (PBL)** to internal SRAM.
3. Performs a **jump** — execution continues in the bootloader (PBL).

### Pseudo Code Example

```cpp
void BootROM_Start() {
    Initialize_CPU();       // Set up CPU and system clocks
    Discovery_Bootloader(); // eMMC, NAND flash, SD card
    Load_Bootloader();      // Locate the bootloader on SRAM
    Jump_To_Bootloader();   // Transfer execution to the bootloader
}
```

## Stage 2: Bootloader

The **bootloader** is the next critical phase in the boot process. It is a piece of
software that acts as an **intermediary** between the Boot ROM and the operating
system, preparing the environment for the Android kernel to run.

### What is a Bootloader?

The bootloader is a special program **separate from the Linux kernel** that is used
to set up initial memories and load the kernel to RAM.

> - On **desktop systems**: bootloaders are programs like **GRUB**.
> - In **embedded Linux**: **uBoot** is often the bootloader of choice.
> - **Device manufacturers** often use their own proprietary bootloaders.

The bootloader is often divided into **two parts**:

---

### 2.1 Primary Bootloader (PBL)

After the Boot ROM initializes the hardware, it loads the **Primary Bootloader
(PBL)**. The PBL is responsible for loading and executing the **Secondary Bootloader
(SBL)**.

**PBL main tasks:**

- Initializing **critical hardware components**.
- Setting up the **memory controller**.
- Loading the **SBL into RAM**.

#### Pseudo Code Example

```cpp
void primary_bootloader_main() {
    init_hardware();                 // Initialize basic hardware
    setup_memory();                  // Set up the memory controller
    load_secondary_bootloader();     // Load the next stage
    jump_to_secondary_bootloader();  // Transfer control
}
```

---

### 2.2 Secondary Bootloader (SBL)

The **Secondary Bootloader (SBL)** is a more complex software that performs
additional hardware initialization and loads the kernel.

The SBL also includes:

- A **splash screen**
- **Boot animation**
- **Diagnostic features**

It prepares the system for the Android kernel and performs tasks like **verifying
the integrity** of the system images.

#### SBL Key Tasks

- **Hardware Initialization and Setup:** Configuring additional peripherals like
  display controllers, input devices, and network interfaces.

- **Partition Verification:** Verifying the integrity of key system partitions such
  as the **boot**, **recovery**, and **system** partitions. This may involve checking
  **cryptographic signatures** or **hash values**.

- **Kernel Loading and Initialization:** Loading the **Linux kernel** into memory
  from the boot partition. Also passes essential parameters to the kernel such as:
  - Location of the **root filesystem**
  - **Device Tree Blob (DTB)** — contains hardware configuration data

- **Fastboot and Recovery Modes:** Provides interfaces for accessing special modes.

---

#### Fastboot Mode

A system is usually forced into **Fastboot mode** using some kind of hardware flag:

- Flipping a **DIP-switch**
- Holding some combination of **buttons** during system startup

The bootloader inspects the switches as part of initialization and determines whether
it should run the **fastboot program** or not.

> If the Android device is connected to a host PC through **ADB (Android Debug
> Bridge)**, it is possible to restart the system in fastboot mode via:
>
> ```text
> adb reboot bootloader
> ```

#### Recovery Mode

Android devices support an **alternate boot path: Recovery Mode**.

Unlike Fastboot, Recovery mode boots a **complete, if limited, operating system**:

- Has a **full network stack**.
- Can **mount and unmount volumes**.
- Runs **adb** and a **shell**.
- Does **NOT** start the Android container.

> AOSP contains code for a flashable recovery image in the `bootable/recovery`
> directory. To generate the flashable image file `recovery.img`, use:
>
> ```text
> make -j8 recoveryimage
> ```

---

#### SBL Pseudo Code Example

```cpp
void secondary_bootloader_main() {
    verify_boot_partition();  // Check boot partition integrity
    display_splash_screen();  // Display a splash screen
    load_kernel_image();      // Load the Android kernel
    setup_Device_Tree();      // Load device tree for kernel

    if (Fastboot_Mode_Requested) {
        enter_fastboot_mode(); // Fastboot mode for flashing
    } else if (Recovery_Mode_Requested) {
        enter_recovery_mode(); // Recovery mode
    } else {
        jump_to_kernel();      // Transfer control to Android kernel
    }
}
```

## Stage 3: Linux Kernel

The **Linux kernel** starts up in a similar way on Android as on other systems.
It will set up everything that is needed for the system to run:

- Initialize **interrupt controllers**
- Set up **memory protections**
- Configure **caches**
- Set up **scheduling**

The **kernel** is the core component of the Android operating system. It is
responsible for managing the system's resources, including **memory**, **CPU**,
and **hardware peripherals**. The Android OS uses a **modified version of the
Linux kernel**, specifically optimized for mobile devices.

### Key Functions

- **System Memory Management:** The kernel sets up the **Memory Management Unit
  (MMU)** and initializes the system's memory map, which includes:
  - Configuring **virtual memory**
  - Setting up **paging**
  - Allocating **memory regions** for different system processes

- **Device Driver Initialization:** The kernel initializes and loads the necessary
  **device drivers** for hardware components such as:
  - Display
  - Audio
  - Network interfaces
  - Storage devices

  > Device drivers act as intermediaries between the hardware and the operating system, enabling communication and control.

- **Mounting the Root Filesystem:** The kernel mounts the **root filesystem**,
  which is typically an **initramfs** (initial RAM filesystem) loaded into memory
  by the bootloader. The root filesystem contains the basic tools and scripts
  required to initialize the user space.

- **Launching the Init Process:** The kernel starts the first user-space process,
  known as the **init process**, which has a **Process ID (PID) of 1**. The init
  process is responsible for starting all other system processes and services.

### Pseudo Code Example (Kernel Initialization Flow)

```cpp
void start_kernel(void) {
    setup_arch();                    // Set up architecture-specific config
    init_IRQ();                      // Initialize the interrupt system
    initialize_memory_management();  // Set up virtual memory
    initialize_device_drivers();     // Load and init drivers
    mount_root_filesystem();         // Mount initramfs
    start_init_process();            // Launch init process (PID 1)
}
```

## Stage 4: Init Process

> The init process is the **"grandmother"** of all system processes. Every other
> process in the system will be launched from this process or one of its descendants.

The **init process** is the first **user-space process** started by the kernel.
It plays a central role in the boot process by:

- Initializing the **Android user space**
- Starting **essential system services**
- Setting up the **overall system environment**

### The Init Process Mainly Does Four Things

#### 1. Create Folders and Mount the Device

The init process mounts various system partitions, such as:

- `/system`
- `/data`
- `/cache`

Ensuring that they are available for use by the system and applications.

#### 2. Set Up SELinux Policies

The init process initializes **SELinux (Security-Enhanced Linux)** policies if the
device is configured to use SELinux. This adds an extra layer of security by
enforcing **mandatory access controls**.

#### 3. Initialize and Start the Property Service

The init process loads **Android properties** — key-value pairs used throughout
the Android OS to:

- Control system behaviors
- Manage configuration settings
- Define environment variables

**Examples of Android properties:**

| Property | Description |
|----------|-------------|
| `ro.build.version.sdk` | Defines the version of the Android SDK |
| `ro.product.model` | Identifies the model of the device |
| `ro.secure` | Indicates whether the device runs in secure mode |

> **Android properties vs Windows Registry:**
> Android properties share some conceptual similarities with the **Windows Registry**,
> but they are much simpler. Like the Windows Registry, Android properties can be
> read and modified at runtime. However, the Windows Registry is a more complex
> hierarchical database system, while Android properties are simple **key-value pairs**
> stored in memory.

**Querying properties in Java:**

```java
String sdkVersion = System.getProperty("ro.build.version.sdk");
```

**Android provides commands to define or modify properties:**

- `setprop` — used to **set** a property
- `getprop` — used to **retrieve** the value of a property

#### 4. Parse the init.rc Configuration File and Start the Zygote Process

The init process parses a series of configuration files (`init.rc` and other `.rc`
files) that contain instructions for:

- Starting system services
- Mounting filesystems
- Setting up networking
- Configuring system properties

**Critical system services started:**

- `vold` — volume daemon for managing storage devices
- `netd` — network daemon for handling network interfaces
- `servicemanager` — a core Android service manager
- **Zygote process** — started first of all

---

### Init Process: Files and Modules

Most of the modules involved are located in the `/system/core/init` folder.

#### main.cpp — Entry Point

```cpp
//  $AOSP/system/core/init/main.cpp (simplified)
int main(int argc, char** argv) {

    if (argc > 1) {
        if (!strcmp(argv[1], "selinux_setup")) {
            return SetupSelinux(argv);
        }
        if (!strcmp(argv[1], "second_stage")) {
            return SecondStageMain(argc, argv);
        }
    }
    return FirstStageMain(argc, argv);
}
```

---

### FirstStageMain()

The `FirstStageMain()` method is mainly responsible for **creating directories**
and **mounting devices**.

```cpp
//  $AOSP/system/core/init/first_stage_init.cpp (simplified)
int FirstStageMain(int argc, char** argv) {

    CHECKCALL(mount("tmpfs", "/dev", "tmpfs", MS_NOSUID, "mode=0755"));
    CHECKCALL(mkdir("/dev/pts", 0755));
    CHECKCALL(mkdir("/dev/socket", 0755));
    CHECKCALL(mkdir("/dev/dm-user", 0755));
    CHECKCALL(mount("devpts", "/dev/pts", "devpts", 0, NULL));

    CHECKCALL(mount("sysfs", "/sys", "sysfs", 0, NULL));
    CHECKCALL(mount("selinuxfs", "/sys/fs/selinux", "selinuxfs", 0, NULL));

    CHECKCALL(mount("tmpfs", "/mnt", "tmpfs", MS_NOEXEC|MS_NOSUID|MS_NODEV,
                    "mode=0755,uid=0,gid=1000"));
    CHECKCALL(mkdir("/mnt/vendor", 0755));
    CHECKCALL(mkdir("/mnt/product", 0755));

    // Call init process with selinux_setup as cmd line
    const char* path = "/system/bin/init";
    const char* args[] = {path, "selinux_setup", nullptr};
    execv(path, const_cast<char**>(args));
    return 1;
}
```

**Primary partitions mounted during `FirstStageMain()`:**

| Partition | Purpose |
|-----------|---------|
| `/system` | Core Android OS files, framework, system libraries, and system apps |
| `/vendor` | Device-specific binaries, drivers, and configurations |
| `/proc` | Kernel-level information |
| `/sys` | System information and device drivers |
| `/dev` | Device access |

> `FirstStageMain()` is responsible for preparing a **minimal environment** where
> the Android OS can initialize its core components.

Finally, `FirstStageMain()` passes control back to the init process with
**`"selinux_setup"`** as the command line.

---

### SetupSelinux()

```cpp
//  $AOSP/system/core/init/selinux.cpp (simplified)
int SetupSelinux(char** argv) {

    LoadSelinuxPolicyAndroid();
    SelinuxSetEnforcement();

    // Call init process with second_stage as cmd line
    const char* path = "/system/bin/init";
    const char* args[] = {path, "second_stage", nullptr};
    execv(path, const_cast<char**>(args));

    return 1;
}
```

**Key responsibilities of `SetupSelinux()`:**

- **Loads the SELinux policy** from the system's predefined policy files. This
  policy defines which operations each process and user can perform on system
  resources like files, devices, and sockets.

- **Sets SELinux enforcement mode:**
  - **Enforcing mode** — policy violations are blocked (used in production devices).
  - **Permissive mode** — violations are logged but not blocked.

- **Labels files and processes** — ensures that all relevant files and processes on
  the system are labeled correctly according to the SELinux policy.

Finally, `SetupSelinux()` passes control back to the init process with
**`"second_stage"`** as the command line.

### SecondStageMain()

```cpp
//  $AOSP/system/core/init/init.cpp (simplified)
int SecondStageMain(int argc, char** argv) {

    // Step 1: Load system properties
    PropertyInit();

    // Step 2: Parse init.rc and other .rc files
    ActionManager& am = ActionManager::GetInstance();
    ServiceList& sm = ServiceList::GetInstance();
    LoadBootScripts(am, sm);

    return 0;
}

static void LoadBootScripts(ActionManager& action_manager,
                            ServiceList& service_list) {
    Parser parser = CreateParser(action_manager, service_list);
    std::string bootscript = GetProperty("ro.boot.init_rc", "");
    parser.ParseConfig(bootscript);
}
```

```cpp
//  $AOSP/system/core/init/property_service.cpp (simplified)
void PropertyInit() {

    mkdir("/dev/__properties__", S_IRWXU | S_IXGRP | S_IXOTH);
    CreateSerializedPropertyInfo();
    __system_property_area_init();
    property_info_area.LoadDefaultPath();

    PropertyLoadBootDefaults();
    PropertyLoadDerivedDefaults();
}
```

**Key responsibilities of `SecondStageMain()`:**

- **Setting Up System Properties** (`PropertyInit` method call): System properties
  that configure the behavior of various components are set during this stage.
  These properties can control everything from **security settings** to
  **hardware configurations**.

- **Parsing and Executing `.rc` Scripts** (`LoadBootScripts` method call): Parses
  configuration files like:
  - `init.rc`
  - `init.zygote64.rc`
  - Other device-specific `*.rc` scripts

  These files define the **system services**, **properties**, and **actions**
  needed to bring the system to a fully operational state.

- **Service Initialization:** After parsing the scripts, `SecondStageMain()` starts
  various services defined in these `*.rc` files, including:
  - `vold` — for managing volumes
  - `netd` — for networking
  - **Zygote process**

### Android Init Language

The configuration files in Android, such as `init.rc`, are written in a custom
language known as the **"Android Init Language"**.

> **Android Init Language** is a **domain-specific language (DSL)** designed
> specifically for Android's init process. The language is **declarative** and used
> to define system properties, services, actions, and commands executed during the
> boot process.

The syntax is simple, with commands like `service`, `on`, `start`, `mount`, and more.

#### Example init.rc File

Located in `system/core/rootdir/`:

```text
# Basic init.rc file for Android

on boot
    # Set initial system properties
    setprop ro.bootmode normal

    # Mount essential filesystems
    mount_all /fstab.$(ro.hardware)

    # Start key services
    start ueventd
    start servicemanager
    start vold
    start zygote

# Additional services and configurations
```

**Key tasks in `init.rc` include:**

| Task | Description |
|------|-------------|
| **Mounting Filesystems** | Mounts `/system`, `/data`, and `/vendor` |
| **Setting System Properties** | Sets device identifiers, debug settings, security configurations |
| **Starting Core Services** | Starts `vold`, `netd`, `servicemanager`, Zygote, and others |
