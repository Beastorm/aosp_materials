## Step 1 — `ZygoteInit.java`

The `main()` method of `ZygoteInit` is the entry point for the Zygote process. It performs three key actions:

1. **Preloads** classes and resources shared by all future app processes
2. **Creates** the Zygote server socket (listens for fork requests)
3. **Forks** the SystemServer process via `forkSystemServer()`

```java
// $AOSP/frameworks/base/core/java/com/android/internal/os/ZygoteInit.java
public static void main(String[] argv) {

    // Preload classes and resources
    preload();

    // Create server socket for future process forking
    ZygoteServer zygoteServer = new ZygoteServer();

    boolean startSystemServer = false;
    for (int i = 1; i < argv.length; i++) {
        if ("start-system-server".equals(argv[i])) {
            startSystemServer = true;
        }
    }

    if (startSystemServer) {
        // Fork the SystemServer process
        Runnable r = forkSystemServer(abiList, zygoteSocketName, zygoteServer);
        if (r != null) {
            r.run();
            return;
        }
    }

    // Start accepting requests to fork new processes
    zygoteServer.runSelectLoop();
}
```

### `forkSystemServer()` — Hardcoded Args

The class name `com.android.server.SystemServer` is hardcoded into the arguments, instructing the forked process which Java class to run.

```java
// $AOSP/frameworks/base/core/java/com/android/internal/os/ZygoteInit.java
private static Runnable forkSystemServer(String abiList, String socketName,
        ZygoteServer zygoteServer) {

    String[] args = {
        "--setuid=1000",
        "--setgid=1000",
        "--setgroups=1001,1002,1003,...",
        "--capabilities=" + capabilities + "," + capabilities,
        "--nice-name=system_server",
        "--runtime-args",
        "--target-sdk-version=" + VMRuntime.SDK_VERSION_CUR_DEVELOPMENT,
        "com.android.server.SystemServer",   // ← class to run in the child process
    };

    // ...parse args...

    pid = Zygote.forkSystemServer(
        parsedArgs.mUid, parsedArgs.mGid,
        parsedArgs.mGids,
        parsedArgs.mRuntimeFlags,
        null,
        parsedArgs.mPermittedCapabilities,
        parsedArgs.mEffectiveCapabilities);

    return null;
}
```

## Step 2 — `Zygote.java`

The `Zygote` class handles the actual process forking. `forkSystemServer()` delegates to the native layer via `nativeForkSystemServer()`.

```java
// $AOSP/frameworks/base/core/java/com/android/internal/os/Zygote.java
static int forkSystemServer(int uid, int gid, int[] gids, int runtimeFlags,
        int[][] rlimits, long permittedCapabilities, long effectiveCapabilities)
{
    ZygoteHooks.preFork();

    int pid = nativeForkSystemServer(
        uid, gid, gids, runtimeFlags, rlimits,
        permittedCapabilities, effectiveCapabilities);

    // Reset thread priority to default for new apps
    Thread.currentThread().setPriority(Thread.NORM_PRIORITY);

    ZygoteHooks.postForkCommon();
    return pid;
}

// Implemented in com_android_os_Zygote.cpp
private static native int nativeForkSystemServer(int uid, int gid, int[] gids,
    int runtimeFlags, int[][] rlimits, long permittedCapabilities,
    long effectiveCapabilities);
```

## Step 3 — `com_android_os_Zygote.cpp`

The native C++ layer performs the actual `fork()` system call via `zygote::ForkCommon()`.

```cpp
// $AOSP/frameworks/base/core/jni/com_android_internal_os_Zygote.cpp
static jint com_android_internal_os_Zygote_nativeForkSystemServer(
    JNIEnv* env, jclass, uid_t uid, gid_t gid, jintArray gids,
    jint runtime_flags, jobjectArray rlimits, jlong permitted_capabilities,
    jlong effective_capabilities)
{
    pid_t pid = zygote::ForkCommon(env, true,
                                   fds_to_close,
                                   fds_to_ignore,
                                   true);
    return pid;
}
```

**Fork return values:**

| Process | Return value of `fork()` |
|---|---|
| **Parent** (Zygote) | PID of the child process |
| **Child** (SystemServer / app) | `0` |

Native methods involved:

- `nativeForkSystemServer` — forks the SystemServer process
- `nativeForkForApp` — forks new app processes

## Step 4 — `SystemServer.java`

Once forked, the child process starts the JVM and executes `SystemServer.main()`, which calls `run()`.

```java
// $AOSP/frameworks/base/services/java/com/android/server/SystemServer.java

// Entry point from Zygote
public static void main(String[] args) {
    new SystemServer().run();
}
```

The `run()` method starts all Android framework services in three phases:

```java
private void run() {
    try {
        startBootstrapServices();   // Phase 1: foundational services
        startCoreServices();        // Phase 2: core services
        startOthersServices();      // Phase 3: peripheral & UI services
    } catch (Throwable ex) {
        Slog.e("System", "Failure starting system services", ex);
        throw ex;
    }
}
```

---

### Phase 1 — `startBootstrapServices()`

Critical services with complex mutual dependencies — started together as a group.

```java
private void startBootstrapServices() {
    // Manages app lifecycle (Activity, Service, ContentProvider, BroadcastReceiver)
    mActivityManagerService = mSystemServiceManager.startService(ActivityManagerService.Lifecycle.class);

    // Controls device wake/sleep states and battery efficiency
    mPowerManagerService = mSystemServiceManager.startService(PowerManagerService.class);

    // Manages LEDs and display backlight
    mSystemServiceManager.startService(LightsService.class);

    // Manages physical displays and multi-screen scenarios
    mDisplayManagerService = mSystemServiceManager.startService(DisplayManagerService.class);

    // Manages app install, update, removal, and permissions
    mPackageManagerService = mSystemServiceManager.startService(PackageManagerService.class);
}
```

| Service | Responsibility |
|---|---|
| `ActivityManagerService` | Lifecycle of Activity, Service, ContentProvider, BroadcastReceiver |
| `PowerManagerService` | Wake/sleep states, battery efficiency |
| `DisplayManagerService` | Physical displays, multi-display configuration |
| `PackageManagerService` | App install, update, removal, permissions |
| `LightsService` | Backlight and LED management |

---

### Phase 2 — `startCoreServices()`

Essential services that don't depend on the bootstrap group.

```java
private void startCoreServices() {
    // Monitors battery level; requires LightsService
    mSystemServiceManager.startService(BatteryService.class);

    // Tracks how often apps are used
    mSystemServiceManager.startService(UsageStatsService.class);

    // Manages GPU resources and drivers

```

| Service | Responsibility |
|---|---|
| `BatteryService` | Battery level, charging status, temperature, health; requires `LightsService` |
| `UsageStatsService` | Tracks app usage frequency |
| `GpuService` | GPU resource allocation, deallocation, and tracking |

### Phase 3 — `startOthersServices()`

Peripheral and UI services; also triggers the SystemUI startup.

```java
private void startOthersServices() {
    inputManager = new InputManagerService(context);

    wm = new WindowManagerService(context, inputManager);
```

| Service | Responsibility |
|---|---|
| `InputManagerService` | Touch, key presses, motion events, external input devices |

| `BluetoothService` | BT enable/disable, device discovery, pairing, BLE support |
| `NetworkManagementService` | Network interfaces, bandwidth control, Wi-Fi/mobile/Ethernet |
| `AlarmManagerService` | Time-based task scheduling for background app execution |
| `CameraServiceProxy` | Camera hardware access, Camera2 API, image/video capture |
| `NotificationManagerService` | App notifications, notification bar management |
| `AudioService` | Volume control, audio routing, media/call/alarm stream management |

## Step 5 — SystemUI Startup

### `startSystemUi()` in `SystemServer`

```java
private static void startSystemUi(Context context, WindowManagerService windowManager) {
    PackageManagerInternal pm = LocalServices.getService(PackageManagerInternal.class);

    Intent intent = new Intent();
    intent.setComponent(pm.getSystemUiServiceComponent());
    intent.addFlags(Intent.FLAG_DEBUG_TRIAGED_MISSING);

    // Start SystemUIService under the system user context
    context.startServiceAsUser(intent, UserHandle.SYSTEM);

    // Notify WindowManager that SystemUI has started
    windowManager.onSystemUiStarted();
}
```

### `startServicesIfNeeded()` — Instantiation via Reflection

Each component name is resolved and instantiated via **Java reflection**, then started with `start()`.

```java
private void startServicesIfNeeded(String metricsPrefix, String[] services) {
    if (mServicesStarted) return;
    mServices = new SystemUI[services.length];

    for (int i = 0; i < services.length; i++) {
        String clsName = services[i];
        try {
            SystemUI obj = mComponentHelper.resolveSystemUI(clsName);
            if (obj == null) {
                Constructor constructor = Class.forName(clsName).getConstructor(Context.class);
                obj = (SystemUI) constructor.newInstance(this);
            }
            mServices[i] = obj;
        } catch (ClassNotFoundException | NoSuchMethodException |
                 IllegalAccessException | InstantiationException |
                 InvocationTargetException ex) {
            throw new RuntimeException(ex);
        }
        mServices[i].start();
    }
    mServicesStarted = true;
}
```

## 🏠 Launcher Startup Mechanism

The Launcher (home screen) is started via a chain of calls originating from `SystemServer`, flowing through `ActivityManagerService (AMS)` and `ActivityTaskManagerService (ATMS)`.

The pivotal method is `AMS.systemReady()`, which ultimately triggers `startHomeActivityLocked()`.

---

### 5.1 — `startOtherServices()` in `SystemServer`

```java
private void startOthersServices() {
    // ... start other services ...

    // Signal AMS that the system is ready to launch the home screen
    mActivityManagerService.systemReady(() -> {
        // Optional callback after systemReady
    });

    try {
        startSystemUi(context, windowManagerF);
    } catch (Throwable e) {
        reportWtf("starting System UI", e);
    }
}
```

---

### 5.2 — `systemReady()` in `ActivityManagerService`

```java
// from ActivityManagerService.java
public void systemReady(final Runnable goingCallback) {
    // ...
    startHomeActivityLocked(currentUserId, "systemReady");

    if (bootingSystemUser) {
        // On multi-display devices, start home on ALL displays
        mAtmInternal.startHomeOnAllDisplays(currentUserId, "systemReady");
    }
    // ...
}
```

> `mAtmInternal` refers to `ActivityTaskManagerService` (ATMS), which manages activity tasks and displays.

---

### 5.3 — `startHomeOnAllDisplays()` in `ActivityTaskManagerService`

```java
// from ActivityTaskManagerService.java
public void startHomeOnAllDisplays(String reason) {
    synchronized (mGlobalLock) {
        final int displayId = DEFAULT_DISPLAY;   // typically Display 0
        startHomeOnDisplay(displayId, reason);
    }
}
```

---

### 5.4 — `startHomeOnDisplay()` in `ActivityTaskManagerService`

```java
// from ActivityTaskManagerService.java
void startHomeOnDisplay(int displayId, String reason) {
    final Intent intent = getHomeIntent();          // ACTION_MAIN + CATEGORY_HOME
    intent.setFlags(Intent.FLAG_ACTIVITY_NEW_TASK);

    startHomeActivityLocked(intent, displayId, reason);
}
```

> `getHomeIntent()` constructs an `Intent` with:
> - Action: `Intent.ACTION_MAIN`
> - Category: `Intent.CATEGORY_HOME`

---

### 5.5 — `startHomeActivityLocked()` — Core Launch Method

```java
// from ActivityTaskManagerService.java
boolean startHomeActivityLocked(Intent intent, int displayId, String reason) {
    // Find the app that handles ACTION_MAIN + CATEGORY_HOME
    ActivityInfo aInfo = resolveHomeActivity(intent);

    if (aInfo == null) {
        return false;   // No home activity found
    }

    // Start the Launcher activity
    return startActivityLocked(intent, aInfo, displayId);
}
```

---

### 5.6 — `resolveHomeActivity()` — Finding the Launcher

```java
ActivityInfo resolveHomeActivity(Intent intent) {
    // Ask PackageManager to find which app handles the intent
    ResolveInfo resolveInfo = mPackageManager.resolveActivity(intent, ...);

    if (resolveInfo != null && resolveInfo.activityInfo != null) {
        return resolveInfo.activityInfo;
    }

    return null;   // No matching Launcher found
}
```

> `PackageManager` scans installed apps for one that declares:
> ```xml
> <intent-filter>
>     <action android:name="android.intent.action.MAIN" />
>     <category android:name="android.intent.category.HOME" />
> </intent-filter>
> ```

---

### 5.7 — `startActivityLocked()` — Displaying the Launcher

```java
// from ActivityManagerService.java
private void startActivityLocked(Intent intent, UserHandle user) {
    // Create an ActivityRecord representing the Launcher in the stack
    ActivityRecord r = new ActivityRecord(...);

    // Notify WindowManager to display the activity
    mWindowManager.addWindow(r);
}
```

**What happens here:**

1. An `ActivityRecord` is created — representing the Launcher in the activity stack
2. `WindowManagerService` is notified to display the activity
3. The home screen UI (icons, widgets) is presented to the user

## 🔄 Launcher Boot Sequence — Full Flow

```
SystemServer.startOtherServices()
    │
    └──▶ AMS.systemReady()
              │
              └──▶ ATMS.startHomeOnAllDisplays()
                        │
                        └──▶ startHomeOnDisplay()

                                  └──▶ startHomeActivityLocked()

```

### Launcher Launch — Step-by-Step Recap

```
1. SystemServer.startOtherServices()  →  calls AMS.systemReady()
2. AMS.systemReady()                  →  calls ATMS.startHomeOnAllDisplays()
3. startHomeOnDisplay()               →  constructs ACTION_MAIN + CATEGORY_HOME intent
4. startHomeActivityLocked()          →  resolves Launcher via PackageManager
5. startActivityLocked()              →  adds Launcher to activity stack
6. WindowManagerService               →  displays the Launcher UI
```
