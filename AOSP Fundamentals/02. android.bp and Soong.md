## 1. Build System Overview

```
Source Code (Text files)  →  BUILD SYSTEM  →  Artifacts (.img, .apk, .so)
       ↓                                              ↓
Java, C++, XML, AIDL                  system.img, boot.img, vendor.img
(humans write this)                   (phone can run this)
```

**The build system is the machinery that transforms source into runnable Android.**

---

## 2. Complete Build Pipeline

```
STEP 1          STEP 2          STEP 3          STEP 4

Android.bp  →   Blueprint   →   Soong      →   Ninja Rules
Android.mk  →   Kati        →   (Go code)  →   (.ninja files)
                                    ↓
                              STEP 5: Ninja Executes
                                    ↓
                    ┌───────────────────────────────┐
                    │     COMPILERS & TOOLS          │
                    │                               │
                    │  javac → .class → .dex        │
                    │  clang → .o → .so/.a          │
                    │  aapt2 → resources.arsc        │
                    │  aidl  → .java stubs           │
                    └───────────────────────────────┘
                                    ↓
                              STEP 6: Linking
                                    ↓
                              STEP 7: Packaging
                                    ↓
                    ┌───────────────────────────────┐
                    │         ARTIFACTS              │
                    │                               │
                    │  system.img  boot.img          │
                    │  vendor.img  .apk .so          │
                    └───────────────────────────────┘
```

## 3. Build System Components

### Soong (Primary Build System)

- **Written in:** Go
- **Introduced:** Android 7.0
- **Reads:** `Android.bp` files
- **Produces:** Ninja build rules

**Why Soong replaced Make:**

| Old (Make) | New (Soong) |
|---|---|
| Serial analysis | Parallel analysis |
| Slow dependency check | Fast dependency check |
| Hard to debug | Easy to debug |
| No type safety | Type-safe Go code |
| Minutes to analyze | Seconds to analyze |
| Hard to unit test | Easy to unit test |

**How Soong works:**
1. Reads all `Android.bp` files
2. Builds a dependency graph
3. Generates `.ninja` files
4. Ninja executes the actual compilation

**Location in AOSP:** `build/soong/`, `build/blueprint/`

**Soong bootstrap:** `build/soong/bootstrap.bash` first builds Soong itself from Go source, then Soong builds Android. "Soong builds itself before building Android" — like a factory that first builds its own machines.

---

### Blueprint

A **parser** for `Android.bp` files, written in Go, part of Soong.

```
Android.bp files → Blueprint Parser → Module objects → Soong → Ninja rules
```

> **Analogy:** Blueprint = grammar rules for the `Android.bp` language. Just as English grammar defines valid sentences, Blueprint defines valid `Android.bp` syntax.

**Location:** `build/blueprint/`

---

### Kati (Make Compatibility Layer)

A Make clone written in Go that reads `Android.mk` files (old format) and converts them to Ninja rules.

```
Android.mk → Kati → Ninja rules  ┐
Android.bp → Soong → Ninja rules ┘  Both feed into same Ninja build!
```

**Why needed:** AOSP has thousands of legacy `Android.mk` files that can't all be rewritten overnight. Kati bridges the gap. Being phased out as `.mk` files migrate to `.bp`.

**Location:** `build/kati/`

---

### Ninja

A fast build **executor** — does the actual compilation work by reading `.ninja` files generated by Soong/Kati.

**Why Ninja is fast:**
- Minimal overhead
- Parallel execution
- Smart dependency tracking (only rebuilds changed files)

**Ninja files location:** `out/build-*.ninja`, `out/soong/build.ninja`

> **Analogy:** Soong = Architect (designs what to build). Ninja = Construction crew (actually builds it). The architect gives blueprints to the crew, who builds efficiently from them.

---

### Bazel (Future Direction)

Google's universal build system, currently being adopted by AOSP via a "mixed build" approach (Android 12+).

**Current status:** Some modules use Soong, some use Bazel — both work together.

**Why Bazel:**
- Hermetic builds (reproducible)
- Remote build caching
- Better multi-language support
- Already used by Google internally

**Location:** `build/bazel/`

Bazel will eventually replace Soong completely, but for now it's a mixed build.

## 4. Build Definition Files

### `Android.bp` — New Format (Soong)

Uses a JSON-like syntax. Every module declares its type, name, source files, and dependencies.

```bp
// C++ executable binary
cc_binary {
    name: "my_daemon",
    srcs: [
        "src/main.cpp",
        "src/utils.cpp",
    ],
    shared_libs: [
        "liblog",
        "libcutils",
        "libbinder",
    ],
    static_libs: ["libmyhelper"],
    cflags: ["-Wall", "-Werror", "-DDEBUG"],
    include_dirs: ["include/"],
}

// C++ shared library
cc_library_shared {
    name: "libmylib",
    srcs: ["src/mylib.cpp"],
    export_include_dirs: ["include"],
    shared_libs: ["liblog"],
}

// C++ static library
cc_library_static {
    name: "libmystatic",
    srcs: ["src/static.cpp"],
}

// Java library
java_library {
    name: "my-java-lib",
    srcs: ["src/**/*.java"],
    libs: ["framework", "android.os.statsd-java"],
    sdk_version: "current",
}

// Android App (APK)
android_app {
    name: "MyApp",
    srcs: ["src/**/*.java"],
    resource_dirs: ["res"],
    manifest: "AndroidManifest.xml",
    libs: ["framework"],
    platform_apis: true,
    certificate: "platform",
    privileged: true,
    optimize: {
        enabled: true,
        optimize: true,
        shrink: true,
        proguard_flags_files: ["proguard.flags"],
    },
}

// Android App with AIDL
android_app {
    name: "MyServiceApp",
    srcs: [
        "src/**/*.java",
        "src/**/*.aidl",
    ],
    aidl: {
        include_dirs: ["src/aidl"],
    },
}

// Prebuilt APK
android_app_import {
    name: "PrebuiltApp",
    apk: "PrebuiltApp.apk",
    certificate: "PRESIGNED",
    privileged: true,
}

// Prebuilt shared library
cc_prebuilt_library_shared {
    name: "libprebuilt",
    srcs: ["lib/libprebuilt.so"],
}
```

---

### `Android.mk` — Old Format (Kati/Make)

Still used in many places but being replaced by `Android.bp`.

```makefile
# HEADER (required in every Android.mk)
LOCAL_PATH := $(call my-dir)
include $(CLEAR_VARS)

# ── C++ Executable ──────────────────────────────────
LOCAL_MODULE           := my_daemon
LOCAL_SRC_FILES        := src/main.cpp src/utils.cpp
LOCAL_SHARED_LIBRARIES := liblog libcutils libbinder
LOCAL_CFLAGS           := -Wall -Werror
include $(BUILD_EXECUTABLE)

# ── Shared Library (.so) ─────────────────────────────
include $(CLEAR_VARS)
LOCAL_MODULE           := libmylib
LOCAL_SRC_FILES        := src/mylib.cpp
LOCAL_SHARED_LIBRARIES := liblog
include $(BUILD_SHARED_LIBRARY)

# ── Java Library ─────────────────────────────────────
include $(CLEAR_VARS)
LOCAL_MODULE         := my-java-lib
LOCAL_SRC_FILES      := $(call all-java-files-under, src)
LOCAL_JAVA_LIBRARIES := framework
include $(BUILD_JAVA_LIBRARY)

# ── Android App (APK) ────────────────────────────────
include $(CLEAR_VARS)
LOCAL_MODULE            := MyApp
LOCAL_SRC_FILES         := $(call all-java-files-under, src)
LOCAL_RESOURCE_DIR      := $(LOCAL_PATH)/res
LOCAL_PACKAGE_NAME      := MyApp
LOCAL_CERTIFICATE       := platform
LOCAL_PRIVILEGED_MODULE := true
include $(BUILD_PACKAGE)
```

**`BUILD_*` variable reference:**

| Variable | Output |
|---|---|
| `BUILD_EXECUTABLE` | Binary executable |
| `BUILD_SHARED_LIBRARY` | `.so` file |
| `BUILD_STATIC_LIBRARY` | `.a` file |
| `BUILD_JAVA_LIBRARY` | `.jar` file |
| `BUILD_PACKAGE` | `.apk` file |
| `BUILD_HOST_EXECUTABLE` | Runs on host (your PC) |
| `BUILD_HOST_SHARED_LIBRARY` | `.so` for host |

## 5. Artifact Types

### APK (Android Application Package)

The installable Android app format. Contains: code + resources + manifest.

**Build steps:**

```
STEP 1: AIDL Compilation
  IMyInterface.aidl → aidl compiler → IMyInterface.java

STEP 2: Resource Compilation
  res/ + AndroidManifest.xml → aapt2 → resources.arsc + R.java

STEP 3: Java Compilation
  *.java (including generated) → javac → *.class

STEP 4: DEX Conversion
  *.class → d8 (DEX compiler) → classes.dex

STEP 5: APK Packaging
  classes.dex + resources.arsc + res/ + manifest → aapt2 → MyApp.apk (unsigned)

STEP 6: Signing
  MyApp.apk → apksigner (with platform key) → MyApp.apk (signed)

STEP 7: Alignment
  MyApp.apk (signed) → zipalign → MyApp.apk (final, memory-map optimized)
```

**APK locations on device:**

| Path | Contents |
|---|---|
| `/system/app/` | Regular system apps |
| `/system/priv-app/` | Privileged system apps |
| `/vendor/app/` | Vendor apps |
| `/product/app/` | Product apps |
| `/data/app/` | User-installed apps |

---

### Shared Library (`.so`)

A **Shared Object / Dynamic Library** — compiled C/C++ code loaded into memory at runtime. Multiple apps share the same library instance in memory.

**Why shared:** `libssl.so` used by 50 different apps — without sharing that's 50 copies in memory; with sharing it's 1 copy used by all 50.

**Build steps:**

```
STEP 1: Preprocess
  mylib.cpp → clang preprocessor → expands #include, #define

STEP 2: Compile to Object Files
  mylib.cpp → clang++ → mylib.o

STEP 3: Link into .so
  mylib.o + liblog.so + libcutils.so → lld (linker) → libmylib.so
```

Key clang flags: `-fPIC` (Position Independent Code, required for `.so`), `-shared`.

**Common system `.so` files:**
```
/system/lib64/
├── libc.so       → C library (bionic)
├── libm.so       → Math library
├── libdl.so      → Dynamic linker
├── libart.so     → Android Runtime
├── libbinder.so  → Binder IPC
├── liblog.so     → Logging
├── libssl.so     → SSL/TLS
└── libsqlite.so  → SQLite database
```

**Output location:** `out/target/product/[device]/system/lib64/` (64-bit), `system/lib/` (32-bit), `vendor/lib64/hw/` (HAL `.so` files)

---

### Static Library (`.a`)

An **Archive** — compiled C/C++ object files **copied into** the final binary at link time. Not shared — each binary has its own copy.

**.a vs .so:**

| | `.a` (Static) | `.so` (Shared) |
|---|---|---|
| Memory | Duplicated per binary | One copy shared |
| Runtime dependency | None | Must exist on device |
| Binary size | Larger | Smaller |
| Security patches | Requires relinking | Update one file |
| Best for | Small utils, test libs | Large libs used widely |

```bp
cc_library_static {
    name: "libmystatic",
    srcs: ["src/utils.cpp", "src/helper.cpp"],
    export_include_dirs: ["include"],
}

// Using it:
cc_binary {
    name: "my_binary",
    srcs: ["main.cpp"],
    static_libs: ["libmystatic"],  // Linked in at build time
    shared_libs: ["liblog"],        // Loaded at runtime
}
```

---

### Executable Binary

A standalone program that runs directly on the device.

```
main.cpp + utils.cpp
     ↓ clang++ → .o files
main.o + utils.o + liblog.so + libcutils.so
     ↓ lld (linker)
my_binary (executable)
```

```bp
cc_binary {
    name: "my_daemon",
    srcs: ["main.cpp", "daemon.cpp"],
    shared_libs: ["liblog", "libcutils", "libbinder", "libutils"],
    init_rc: ["my_daemon.rc"],
    vintf_fragments: ["my_daemon.xml"],
}
```

**Init RC file:**
```
service my_daemon /system/bin/my_daemon
    class main
    user system
    group system
    onrestart restart surfaceflinger
```

**Common system binaries:**
```
/system/bin/
├── app_process64  → Starts Java processes (Zygote/apps)
├── surfaceflinger → Display compositor
├── adbd           → ADB daemon
├── installd       → APK installer daemon
├── vold           → Volume/storage daemon
├── netd           → Network daemon
├── logd           → Log daemon
├── sh             → Android shell
└── dumpstate      → Bug report tool
```

**Host binary** (runs on your PC, not phone):
```bp
cc_binary_host {
    name: "host_tool",
    srcs: ["tool.cpp"],
}
// Output: out/host/linux-x86/bin/host_tool
```

### Java Library (`.jar`)

Compiled Java classes. Types in AOSP:

| Type | Purpose |
|---|---|
| `java_library` | For use by other Java code |
| `java_sdk_library` | Public API library with stubs |
| `android_library` | Has Android resources too |

```bp
java_library {
    name: "my-java-lib",
    srcs: [
        "src/com/example/**/*.java",
        "src/com/example/**/*.aidl",
    ],
    libs: ["framework"],      // Compile-time dep (not bundled)
    static_libs: ["gson"],    // Bundled into this .jar
    sdk_version: "current",
}

java_sdk_library {
    name: "my.sdk.library",
    srcs: ["src/**/*.java"],
    api_packages: ["com.example.mylib"],
    public: { enabled: true },
}
```

**The most important `.jar`:** `framework.jar` — built from `frameworks/base/Android.bp`, lives at `/system/framework/framework.jar`. Contains every core Android API class: `Activity`, `Context`, `View`, etc.

**Output location:** `out/target/common/obj/JAVA_LIBRARIES/`, `out/target/product/[device]/system/framework/`

---

### AIDL Stubs

Auto-generated Java/C++ code from `.aidl` files that creates IPC boilerplate automatically.

```aidl
// IMyService.aidl
interface IMyService {
    String getMessage(int id);
    void sendData(in byte[] data);
    List<String> getAllItems();
}
```

The AIDL compiler generates:
- `IMyService` — the interface
- `IMyService.Stub` — server extends this (abstract)
- `IMyService.Stub.Proxy` — client gets this automatically

```bp
aidl_interface {
    name: "my-aidl-interface",
    srcs: ["aidl/**/*.aidl"],
    versions: ["1", "2"],
    stability: "vintf",
    backend: {
        java: { enabled: true },
        cpp:  { enabled: true },
        ndk:  { enabled: true },
    },
}
```

**Generated file location:** `out/soong/.intermediates/[module]/gen/aidl/`

---

### System Images (`.img`)

Complete filesystem images — exact copies of what goes on each phone partition.

**How `system.img` is created:**
```
All compiled artifacts are staged into:
out/target/product/[device]/system/
├── app/MyApp.apk
├── priv-app/Settings.apk
├── framework/framework.jar
├── lib64/libc.so
├── bin/surfaceflinger
└── ...
     ↓
Staged system/ directory → make_ext4fs / mke2fs / erofs → system.img
```

**How `boot.img` is created:**
```
Kernel binary (from kernel/) + Ramdisk (from system/core/init/)
     ↓ mkbootimg tool
boot.img
```

**Image reference:**

| Image | Filesystem | Contents |
|---|---|---|
| `system.img` | ext4 / erofs | Android OS files |
| `vendor.img` | ext4 / erofs | HAL, firmware, drivers |
| `boot.img` | cpio/gzip | Kernel + ramdisk |
| `recovery.img` | cpio/gzip | Recovery OS |
| `userdata.img` | ext4 | Empty user partition |
| `product.img` | ext4 / erofs | OEM apps |
| `system_ext.img` | ext4 / erofs | Extended system |
| `cache.img` | ext4 | Empty cache |

**Build commands:**
```bash
make systemimage    # Build system.img only
make bootimage      # Build boot.img only
make vendorimage    # Build vendor.img only
make otapackage     # Build OTA zip package
make dist           # Build all for distribution
```

### VINTF / HAL Manifest

XML file declaring what HALs a device provides. The framework reads this to know what hardware is available.

```xml
<?xml version="1.0" encoding="UTF-8"?>
<manifest version="2.0" type="device">
    <hal format="aidl">
        <name>android.hardware.camera.provider</name>
        <version>1</version>
        <interface>
            <name>ICameraProvider</name>
            <instance>internal/0</instance>
        </interface>
    </hal>
    <hal format="aidl">
        <name>android.hardware.audio.core</name>
        <version>1</version>
    </hal>
</manifest>
```

```bp
cc_binary {
    name: "android.hardware.camera.provider",
    vintf_fragments: ["manifest_camera.xml"],
    ...
}
```

### OTA Package

A ZIP file containing all update files + instructions, applied by recovery to update the phone.

```bash
make otapackage -j$(nproc)
# Output: out/target/product/[device]/[device]-ota-*.zip
```

**Full OTA contents:**
```
ota.zip
├── META-INF/
│   ├── MANIFEST.MF            → File checksums
│   ├── CERT.RSA               → Signing certificate
│   └── com/google/android/
│       ├── update-binary      → Updater binary
│       └── updater-script     → Update instructions
├── system/                    → New system files
├── vendor/                    → New vendor files
└── boot.img                   → New boot image
```

**Incremental OTA** (diff only — much smaller):
```bash
ota_from_target_files \
  -i old_target_files.zip \
  new_target_files.zip \
  incremental_ota.zip
```

### Host Tools

Programs that run on **your computer**, not the phone. Used during the build process or for development.

| Tool | Purpose |
|---|---|
| `aapt2` | Compiles Android resources |
| `dex2oat` | Compiles DEX to native code |
| `fastboot` | Flashes images to device |
| `adb` | Debug bridge |
| `mkbootimg` | Creates `boot.img` |
| `make_ext4fs` | Creates ext4 filesystem images |

```bp
cc_binary_host {
    name: "my_host_tool",
    srcs: ["tool.cpp"],
    stl: "libc++",
}

java_binary_host {
    name: "my_java_tool",
    srcs: ["src/**/*.java"],
    main_class: "com.example.Tool",
}
```

**Output location:** `out/host/linux-x86/bin/` (executables), `out/host/linux-x86/lib64/` (libraries)

---

### Source → Tool → Artifact Mapping

| Source File Type | Tool Used | Artifact Type |
|---|---|---|
| `.java` | javac | `.class` |
| `.class` | d8 | `.dex` |
| `.dex` + res | aapt2 | `.apk` |
| `.cpp` / `.c` | clang | `.o` |
| `.o` files | lld (linker) | `.so` (shared) |
| `.o` files | ar (archiver) | `.a` (static) |
| `.o` + `.a` + `.so` | lld (linker) | binary |
| `.aidl` | aidl | `.java` / `.cpp` stubs |
| `.proto` | protoc | `.java` / `.cpp` |
| `.rs` (RenderScript) | llvm-rs-cc | `.bc` + `.java` |
| `res/` + manifest | aapt2 | `resources.arsc` |
| `system/` (staged) | mke2fs | `system.img` |
| `vendor/` (staged) | mke2fs | `vendor.img` |
| kernel + ramdisk | mkbootimg | `boot.img` |

## 6. Build Configuration System

### Product Configuration

```
device/google/bluejay/
├── AndroidProducts.mk     → Declares product name
├── device.mk              → Device packages & configs
├── BoardConfig.mk         → Hardware/kernel config
└── overlay/               → Resource overrides
```

**`AndroidProducts.mk`:**
```makefile
PRODUCT_MAKEFILES := $(LOCAL_DIR)/aosp_bluejay.mk
```

**`aosp_bluejay.mk`:**
```makefile
$(call inherit-product, device/google/bluejay/device.mk)
PRODUCT_NAME   := aosp_bluejay
PRODUCT_DEVICE := bluejay
PRODUCT_BRAND  := Android
PRODUCT_MODEL  := Pixel 6a
```

**`device.mk`:**
```makefile
PRODUCT_PACKAGES += \
    Launcher3 Settings Dialer Camera2 MyCustomApp

PRODUCT_PROPERTY_OVERRIDES += \
    ro.product.name=bluejay \
    dalvik.vm.heapsize=512m
```

**`BoardConfig.mk`:**
```makefile
TARGET_ARCH         := arm64
TARGET_ARCH_VARIANT := armv8-2a
TARGET_CPU_VARIANT  := cortex-a55

TARGET_KERNEL_SOURCE := kernel/google/gs101
TARGET_KERNEL_CONFIG := bluejay_defconfig
BOARD_KERNEL_BASE    := 0x00000000

BOARD_SYSTEMIMAGE_PARTITION_SIZE := 2147483648
BOARD_VENDORIMAGE_PARTITION_SIZE := 1073741824
```

### Build Flags & Conditional Building

```makefile
# Conditional inclusion based on device
ifeq ($(TARGET_PRODUCT), aosp_bluejay)
    PRODUCT_PACKAGES += PixelSpecificApp
endif

# Debug vs Release
ifeq ($(TARGET_BUILD_VARIANT), eng)
    PRODUCT_PACKAGES += DebugTool
    PRODUCT_PROPERTY_OVERRIDES += debug.myapp.enabled=true
endif
```

```bp
// In Android.bp — conditional per platform/arch
cc_binary {
    name: "my_binary",
    srcs: ["main.cpp"],

    target: {
        android: {
            shared_libs: ["liblog"],  // Android only
        },
        host: {
            static_libs: ["liblog"],  // Host (PC) only
        },
    },

    arch: {
        arm64: {
            srcs: ["src/arm64_optimized.cpp"],  // ARM64 only
        },
        x86_64: {
            srcs: ["src/x86_optimized.cpp"],    // x86 only
        },
    },
}
```

## 7. Complete Build Flow Diagram

```
source build/envsetup.sh
           ↓
        lunch aosp_x86_64-eng
           ↓ reads device configs
        m -j$(nproc)
           ↓
    ┌──────────────────────────────────────────────────┐
    │              ANALYSIS PHASE                      │
    │                                                  │
    │  Android.bp → Soong  ─────────────────────────┐ │
    │  Android.mk → Kati   ─────────────────────────┤ │
    │                              ↓                 │ │
    │                        build.ninja             │ │
    └──────────────────────────────────────────────────┘
           ↓
    ┌──────────────────────────────────────────────────┐
    │              COMPILATION PHASE                   │
    │                                                  │
    │  .java  → javac  → .class → d8   → .dex         │
    │  .cpp   → clang  → .o    → lld  → .so/.a/binary │
    │  .aidl  → aidl   → .java → javac → .class        │
    │  res/   → aapt2  → resources.arsc + R.java        │
    │  .proto → protoc → .java/.cpp                    │
    └──────────────────────────────────────────────────┘
           ↓
    ┌──────────────────────────────────────────────────┐
    │              PACKAGING PHASE                     │
    │                                                  │
    │  .dex + res  → APK signer → .apk                │
    │  .so files   → staged to system/lib64/           │
    │  binaries    → staged to system/bin/             │
    │  .jar files  → staged to system/framework/       │
    └──────────────────────────────────────────────────┘
           ↓
    ┌──────────────────────────────────────────────────┐
    │              IMAGE CREATION PHASE                │
    │                                                  │
    │  system/ → mke2fs    → system.img               │
    │  vendor/ → mke2fs    → vendor.img               │
    │  kernel + ramdisk → mkbootimg → boot.img        │
    └──────────────────────────────────────────────────┘
           ↓
    ┌──────────────────────────────────────────────────┐
    │              OUTPUT                              │
    │                                                  │
    │  out/target/product/[device]/                   │
    │  ├── system.img    ← Android OS                 │
    │  ├── vendor.img    ← HAL/Drivers                │
    │  ├── boot.img      ← Kernel                     │
    │  ├── userdata.img  ← User partition             │
    │  └── *.apk, *.so  ← Individual artifacts        │
    └──────────────────────────────────────────────────┘
           ↓
    fastboot flashall / emulator
           ↓
         📱 RUNNING ANDROID!
```

## 8. Quick Reference Table

| Artifact | Tool | `Android.bp` Module Type |
|---|---|---|
| `.apk` | aapt2 + d8 + signer | `android_app` |
| `.apk` (prebuilt) | none | `android_app_import` |
| `.so` | clang + lld | `cc_library_shared` |
| `.a` | clang + ar | `cc_library_static` |
| binary | clang + lld | `cc_binary` |
| host binary | clang + lld | `cc_binary_host` |
| `.jar` | javac + jar | `java_library` |
| SDK `.jar` | javac + metalava | `java_sdk_library` |
| `.jar` (prebuilt) | none | `java_import` |
| AIDL stubs | aidl | `aidl_interface` |
| Proto stubs | protoc | `java_proto_library` |
| `system.img` | mke2fs | `make systemimage` |
| `boot.img` | mkbootimg | `make bootimage` |
| OTA zip | ota tools | `make otapackage` |
| HAL binary | clang + lld | `cc_binary` (with `vintf_fragments`) |

---

> 💡 **Key Insight:** AOSP uses a layered build system: `Android.bp`/`.mk` → Soong/Kati → Ninja → Compilers → Artifacts. Each layer has a specific job, making the system modular and maintainable.

> 💡 **Interview Tip:** Always mention that Soong is replacing Make, Ninja is the executor, and different artifact types use different compilers — `clang` for C++, `javac`+`d8` for Java, `aidl` for IPC interfaces.

## 1. What is Dependency Resolution?

When you build Module A, it **needs** Module B to work. Module B needs Module C. Module C needs Module D. The build system must figure out:

1. **What** depends on what
2. In **what order** to build them
3. **What to rebuild** when something changes

This process = **Dependency Resolution**.

**Real example:**

```
Settings.apk       needs → framework.jar
framework.jar      needs → libandroid_runtime.so
libandroid_runtime needs → libbinder.so
libbinder.so       needs → libutils.so
libutils.so        needs → libc.so
libc.so            → NO dependencies (leaf node)

BUILD ORDER (bottom up):
libc.so → libutils.so → libbinder.so →
libandroid_runtime.so → framework.jar → Settings.apk
```

---

## 2. Dependency Resolution Pipeline

```
STEP 1: COLLECTION
  Soong reads ALL Android.bp files across entire AOSP.
  Every module declares its dependencies explicitly.

  Android.bp (Settings) + Android.bp (framework) + ...
              ↓
  ┌──────────────────────────────────────────────┐
  │         SOONG MODULE REGISTRY                │
  │  "I know about ALL modules and their deps"   │
  └──────────────────────────────────────────────┘

STEP 2: GRAPH BUILDING
  Soong builds a DAG (Directed Acyclic Graph).

  Settings ──→ framework ──→ libandroid_runtime
  libandroid_runtime ──→ libbinder ──→ libutils ──→ libc (leaf)

STEP 3: TOPOLOGICAL SORT
  Figure out build order: leaves first, dependents last.

  libc → libutils → libbinder → libandroid_runtime → framework → Settings

STEP 4: NINJA RULE GENERATION
  Soong writes .ninja files with the correct order.
  Ninja executes in parallel where possible.

STEP 5: INCREMENTAL DETECTION
  Ninja checks file timestamps.
  Only rebuilds what actually changed.
  If libc.so unchanged → don't rebuild libutils.so.
```

---

## 3. Dependency Graph (DAG)

**DAG = Directed Acyclic Graph**
- **Directed** — arrows go one way (A depends on B)
- **Acyclic** — no circular dependencies (`A→B→C→A` = ERROR)

```
                   Settings.apk
                        │
             ┌──────────┴──────────┐
             ↓                     ↓
        framework.jar       android-support.jar
             │
   ┌─────────┴──────────────────┐
   ↓                            ↓
libandroid_runtime.so      services.jar
   │
┌──┴─────────────────┐
↓                    ↓
libbinder.so    libhwbinder.so
   │
   ↓
libutils.so
   │
   ↓
libc.so  ← LEAF (no dependencies)
```

Arrow direction = "depends on". `Settings.apk → framework.jar` means "build framework **before** Settings."

**Parallel build opportunities:** `framework.jar` and `android-support.jar` have no dependency between them — build them **simultaneously** on different CPU cores, saving build time. Same for `libbinder.so` and `libhwbinder.so`.

## 4. Dependency Types in Android.bp

### `shared_libs` — Runtime Dependency (C/C++)

The `.so` file is loaded **at runtime** — not bundled into your module. Must exist on the device.

```bp
cc_binary {
    name: "my_binary",
    srcs: ["main.cpp"],
    shared_libs: [
        "liblog",     // Load liblog.so at runtime
        "libbinder",  // Load libbinder.so at runtime
        "libcutils",
    ],
}
```

- **Build time:** Link against the `.so` (get symbols)
- **Runtime:** Dynamic linker loads the `.so` from `/system/lib64/`
- **Dependency resolution:** All listed `.so` files must be built first

> **Analogy:** Like saying "my car needs fuel at runtime" — the car is built without fuel, but needs it to drive.

---

### `static_libs` — Compile-time Dependency (C/C++)

Library code is **copied into** your module at build time. NOT a separate `.so` on device. Your binary becomes larger but self-contained.

```bp
cc_binary {
    name: "my_binary",
    srcs: ["main.cpp"],
    static_libs: [
        "libmyhelper",  // Code merged into my_binary
        "libjsoncpp",   // Code merged into my_binary
    ],
}
```

**Diamond dependency problem with static libs:**

```
        my_binary
       ↙         ↘
  libA.a         libB.a
       ↘         ↙
         libC.a (static)
```

If both `libA` and `libB` statically link `libC`, `my_binary` gets **two copies** of `libC` code → linker errors (duplicate symbols). Solution: make `libC` a `shared_lib` instead.

---

### `libs` — Java Compile-time Dependency

Java library available at **compile time**, not bundled into the output. Must exist on the device's classpath.

```bp
android_app {
    name: "MyApp",
    srcs: ["src/**/*.java"],
    libs: [
        "framework",     // Not bundled in APK — device already has it
    ],
    static_libs: [
        "gson",          // BUNDLED inside APK
        "retrofit",      // BUNDLED inside APK
    ],
}
```

---

### `static_libs` — Java Bundled Dependency

Java library code **merged into** your JAR/APK. No separate `.jar` needed at runtime.

```bp
android_app {
    name: "Settings",
    srcs: ["src/**/*.java"],
    static_libs: [
        "SettingsLib",                        // Merged into Settings.apk
        "androidx.preference_preference",     // Merged in
        "com.google.android.material_material",
    ],
}
```

Full dependency chain for the above — **all must compile before Settings.apk**:
```
Settings.apk
└── SettingsLib (merged)
│   └── androidx.core (merged)
└── androidx.preference (merged)
    └── androidx.annotation (merged)
```

---

### `header_libs` — C++ Headers Only

Provides only header files (`.h`). No compiled code — just for compilation type checking.

```bp
cc_library_headers {
    name: "libmylib_headers",
    export_include_dirs: ["include"],
}

cc_binary {
    name: "my_binary",
    srcs: ["main.cpp"],
    header_libs: ["libmylib_headers"],
    // Gains access to #include "mylib.h"
}
```

No linking needed — just file availability check before compilation.

---

### `defaults` — Shared Configuration Template

A template of common settings that multiple modules inherit.

```bp
cc_defaults {
    name: "my_defaults",
    shared_libs: ["liblog", "libcutils", "libbinder"],
    cflags: ["-Wall", "-Werror", "-DANDROID"],
}

cc_binary {
    name: "module_a",
    defaults: ["my_defaults"],  // Inherits all deps above
    srcs: ["a.cpp"],
}

cc_binary {
    name: "module_b",
    defaults: ["my_defaults"],  // Same deps
    srcs: ["b.cpp"],
}
```

When resolving `module_a`'s deps, Soong expands `my_defaults` and adds `liblog`, `libcutils`, `libbinder` to its dependency set.

---

### `export_*` — Transitive Dependencies

When A uses B, and B **exports** C, A automatically gets C too.

```bp
// libbase exports its headers
cc_library_shared {
    name: "libbase",
    srcs: ["base.cpp"],
    export_include_dirs: ["include"],         // Exported!
    export_shared_lib_headers: ["liblog"],    // Exported!
}

// libnetwork uses libbase
cc_library_shared {
    name: "libnetwork",
    srcs: ["network.cpp"],
    shared_libs: ["libbase"],
    // Automatically gets libbase's exported includes
    // Automatically gets liblog headers (exported by libbase)
}

// my_app uses libnetwork
cc_binary {
    name: "my_app",
    srcs: ["app.cpp"],
    shared_libs: ["libnetwork"],
    // Transitively gets libbase includes
    // Can #include files from libbase in app.cpp!
}
```

Transitive chain: `my_app → libnetwork → libbase → liblog (headers only)`

Without `export_*`, `my_app` can only see `libnetwork` headers — not `libbase`.

## 5. How Soong Resolves Dependencies

### Phase 1 — Module Registration

Soong reads **every** `Android.bp` in the entire AOSP tree and registers all modules into a global map.

```
GLOBAL MODULE MAP (after reading all files):

MODULE NAME              TYPE                DEPS
─────────────────────────────────────────────────────────────────
liblog                   cc_library_shared   []
libbinder                cc_library_shared   [libutils, libc]
libutils                 cc_library_shared   [libc]
libc                     cc_library_shared   []
my_binary                cc_binary           [liblog, libbinder]
Settings                 android_app         [framework]
framework                java_library        [libandroid_runtime]
... 800+ more modules
```

**Problem detection at this phase:** If `"libfoo"` is listed as a dep but no module named `libfoo` exists → Soong errors immediately with `"ERROR: module 'libfoo' not found"`. Fail fast before any compilation.

---

### Phase 2 — Dependency Graph Construction

Soong connects modules using their declared dependencies and builds the graph in memory.

```
Algorithm:
  For each module M:
    For each dep D in M.shared_libs + M.static_libs + M.libs:
      Find module D in global map
      Add edge: M → D
      Recursively process D's dependencies

Example trace:
  Process Settings  → add edge: Settings → framework
  Process framework → add edge: framework → libandroid_runtime
  Process libandroid_runtime:
    → add edge: libandroid_runtime → libbinder
    → add edge: libandroid_runtime → libutils
  Process libbinder:
    → add edge: libbinder → libutils
    → add edge: libbinder → libc
  Process libc: no deps → LEAF, stop
```

**Circular dependency detection:** If a node already in the current traversal path is encountered again, Soong errors immediately:
```
ERROR: module A depends on B which depends on A (cycle)
```

---

### Phase 3 — Topological Sort

Finds the correct build order using **Kahn's Algorithm**: leaves first, dependents last.

```
INITIAL: Settings ← framework ← libandroid_runtime ← libbinder ← libutils ← libc

ROUND 1: libc has no deps → BUILD libc ✅, remove its edges
ROUND 2: libutils: dep (libc) done → BUILD libutils ✅
ROUND 3: libbinder: deps done → BUILD libbinder ✅
...continues...

FINAL BUILD ORDER:
libc → libutils → libbinder → libandroid_runtime → framework → Settings
```

**Parallel execution:** When multiple nodes become leaves at the same time, build them simultaneously on different CPU cores.

---

### Phase 4 — Ninja File Generation

Soong produces `.ninja` files describing commands, order, and input/output files.

```ninja
# Build rule definition
rule compile_cpp
  command = clang++ $cFlags -c $in -o $out

rule link_shared
  command = clang++ -shared $in -o $out $ldFlags

# Build statements with explicit dependencies
build out/libc.so: link_shared out/libc.o
  ldFlags = -lm

build out/libutils.so: link_shared out/libutils.o | out/libc.so
  #                                                ^ DEPENDENCY!

build out/libbinder.so: link_shared out/libbinder.o | out/libutils.so out/libc.so

build out/Settings.apk: package_apk out/Settings.dex | out/framework.jar
```

**Ninja parallel execution:**
```
Thread 1: Build libc.so
Thread 2: (waiting...)

libc.so done!

Thread 1: Build libutils.so   (libc.so ready)
Thread 2: Build libm.so       (no deps, runs in parallel!)

...etc
```

---

### Phase 5 — Incremental Build Detection

Ninja tracks **file timestamps** and compares input vs output modification times.

```
If input.cpp modified time  >  output.o modified time:
  → Input changed AFTER output was created → REBUILD

If input.cpp modified time  <  output.o modified time:
  → Output is newer → UP TO DATE, SKIP
```

**Example cascade:**

```
You edit: frameworks/base/core/java/android/app/Activity.java

Activity.java  (modified: 2:30 PM)
framework.jar  (modified: 1:00 PM)  → Activity.java NEWER → REBUILD framework.jar!

framework.jar  (modified: 2:35 PM)
Settings.apk   (modified: 1:00 PM)  → framework.jar NEWER → REBUILD Settings.apk!

libssl.so      → no dependency on changed path → NOT REBUILT
Camera.apk     → doesn't depend on Activity.java chain → NOT REBUILT
```

**Key insight:** Changing a core library like `libc.so` triggers a long cascade rebuild. Changing a single app is fast because only that app rebuilds.

## 6. Dependency Resolution in Detail

### Java Dependency Resolution

```
android_app {
    name: "MyApp",
    srcs: ["src/**/*.java"],
    libs: ["framework", "mylib"],
    static_libs: ["gson"],
}
```

Soong creates the `javac` command:
```bash
javac \
  -classpath framework.jar:mylib.jar:gson.jar \
  -sourcepath src/ \
  src/**/*.java \
  -d out/MyApp/classes/
```

All `libs` and `static_libs` **must be built before** `javac` runs.

**`libs` vs `static_libs` in Java:**

```
libs: ["framework"]
  → framework.jar on COMPILE classpath
  → NOT included in MyApp.apk
  → At runtime, uses /system/framework/framework.jar

static_libs: ["gson"]
  → gson.jar on COMPILE classpath
  → gson code MERGED into MyApp's classes.dex
  → No separate gson.jar needed on device
```

---

### C/C++ Dependency Resolution

**Header resolution:**
```bp
cc_binary {
    name: "my_binary",
    srcs: ["main.cpp"],
    shared_libs: ["libmylib"],  // libmylib exports its headers
}

cc_library_shared {
    name: "libmylib",
    export_include_dirs: ["include"],  // Exported!
}
// my_binary automatically gets libmylib's include/ in its search path
```

**Symbol resolution at link time:**
```
main.cpp calls: binder_open()

Linker checks:
1. Is binder_open() in main.o?       → No
2. Is binder_open() in libbinder.so? → YES ✅
3. Record: "my_binary needs libbinder.so at runtime"

Runtime:
→ Dynamic linker reads my_binary's dependency list
→ Loads /system/lib64/libbinder.so
→ Resolves binder_open() address
→ Call succeeds
```

**Missing symbol error** (caught at link time, not runtime):
```
ld: error: undefined symbol: binder_open
>>> referenced by main.cpp:25

Fix: Add "libbinder" to shared_libs in Android.bp
```

**Viewing a binary's runtime dependencies:**
```bash
readelf -d my_binary | grep NEEDED
# → NEEDED: libbinder.so
# → NEEDED: libutils.so
# → NEEDED: libc.so
```

---

### AIDL Dependency Resolution

```bp
aidl_interface {
    name: "my-aidl",
    srcs: ["aidl/IMyService.aidl"],
    versions: ["1", "2"],
    stability: "vintf",
    backend: {
        java: { enabled: true },
        cpp:  { enabled: true },
        ndk:  { enabled: true },
    },
}
```

**What Soong auto-generates from this:**
- `my-aidl-V1-java` / `my-aidl-V2-java` — Java stubs
- `my-aidl-V1-cpp` / `my-aidl-V2-cpp` — C++ stubs
- `my-aidl-V1-ndk` / `my-aidl-V2-ndk` — NDK stubs

**Using the generated stubs:**
```bp
// Java client
java_library {
    name: "my-client",
    srcs: ["src/**/*.java"],
    libs: ["my-aidl-V2-java"],
}

// C++ server
cc_binary {
    name: "my-server",
    srcs: ["server.cpp"],
    shared_libs: ["my-aidl-V2-cpp", "libbinder"],
}
```

**Soong-guaranteed order:**
1. `aidl` compiler runs on `IMyService.aidl` first
2. Generates `my-aidl-V2-java` stubs
3. **Then** compiles `my-client` using those stubs

## 7. Common Errors & Debugging

### Error 1 — Module Not Found

```
Android.bp: error: "libfoo" depends on undefined module "libbar"
```

```bash
# Search for the module definition:
grep -r 'name: "libbar"' --include="Android.bp" .
```

**Common causes:** typo in module name, module in `vendor/` but not accessible, module renamed in newer AOSP, missing `local_manifest` project.

---

### Error 2 — Circular Dependency

```
Android.bp: error: module "libA" depends on "libB"
which depends on "libA" (cycle)
```

**Solution — break the cycle:**

```
BAD (circular):
  libA needs libB for foo()
  libB needs libA for bar()

GOOD (extract shared code):
  libCommon (contains shared functions)
  libA → libCommon
  libB → libCommon
```

---

### Error 3 — Duplicate Module Name

```
Android.bp: error: module "libfoo" already defined
at external/libfoo/Android.bp:5:1
```

```bash
grep -r 'name: "libfoo"' --include="Android.bp" .
```

**Solutions:** rename one module, use `override_android_app` for apps, use `soong_namespace` to isolate modules.

---

### Error 4 — Missing Symbol (Link Error)

```
ld: error: undefined symbol: binder_open
>>> referenced by main.cpp:25
```

```bash
# Find which library provides this symbol:
grep -r "binder_open" --include="*.h" .
nm -D out/target/product/.../libbinder.so | grep binder_open
```

**Fix:**
```bp
cc_binary {
    name: "my_binary",
    shared_libs: ["libbinder"],   // ADD THIS
}
```

---

### Error 5 — AIDL Version Mismatch

```
AIDL interface "my-aidl" version 3 requested but only versions [1, 2] exist
```

```bash
ls aidl/my-aidl/aidl_api/
# Shows: 1/  2/  (version 3 doesn't exist yet)
```

**Solutions:**
```bp
libs: ["my-aidl-V2-java"]    // Use existing version 2
```
Or freeze a new version:
```bash
m my-aidl-freeze-api   # Creates version 3 snapshot
```

## 9. Quick Reference Table

| Type | Bundled? | Runtime Dep? | Language |
|---|---|---|---|
| `shared_libs` | ❌ No | ✅ Yes (`.so`) | C/C++ |
| `static_libs` | ✅ Yes (`.a`) | ❌ No | C/C++ |
| `header_libs` | ❌ No (headers only) | ❌ No | C/C++ |
| `libs` (Java) | ❌ No | ✅ Yes (`.jar`) | Java/Kotlin |
| `static_libs` (Java) | ✅ Yes (merged) | ❌ No | Java/Kotlin |
| `defaults` | Inherits | Depends on contents | Both |
| `export_*` | ❌ No | Transitive | Both |

---

> 💡 **Key Insight:** Dependency resolution in AOSP is a 5-phase process: Register → Graph Build → Topological Sort → Ninja Generation → Incremental Execution. The DAG ensures correct order; Ninja ensures only changed files are rebuilt.

> 💡 **Interview Tip:** Circular dependencies cause build errors. `shared_libs` are runtime deps while `static_libs` are bundled at build time. Ninja's incremental builds make day-to-day development fast — changing one app only rebuilds that app, not all of AOSP.
