# AOSP Setup — Every Term Explained Simply

---

## 📱 What is AOSP?

**AOSP = Android Open Source Project**

It's the free, open-source base code of Android that Google shares with everyone. Think of it like a recipe — anyone can take it, modify it, and cook their own version of Android.

> **Example:** Samsung takes AOSP → adds their own UI (One UI) → sells Galaxy phones with it.

---

## 🖥️ System Requirements

### 1. Linux OS (Operating System)

The software that runs your computer (like Windows, but for developers).

> **Example:** Ubuntu 20.04 is a version of Linux — AOSP builds best on Linux.
> **Why:** AOSP was designed to compile on Linux, not Windows.

---

### 2. 64-bit Environment

How much data your computer can process at once.

> **Example:**
> - 64-bit = a 4-lane highway (fast)
> - 32-bit = a 1-lane road (slow)
>
> AOSP needs the 4-lane highway (64-bit) because it's HUGE.

---

### 3. RAM (Random Access Memory)

Your computer's "short-term memory" — used while actively working.

> **Example:** Like a desk — bigger desk = more papers you can spread out at once.
> - Opening Chrome uses ~2 GB RAM
> - Building AOSP uses 16–64 GB RAM
>
> AOSP needs at least **16 GB RAM** (64 GB recommended).

---

### 4. Disk Space (Storage)

Your computer's "long-term memory" — where files are saved permanently.

> **Example:** Like a filing cabinet.
> - AOSP source code = ~100 GB
> - After building = ~300 GB+
>
> You need at least **400 GB** free space.

---

### 5. CPU (Central Processing Unit)

The "brain" of your computer that does calculations. More cores = more hands working at the same time.

> **Example:**
> - Building with 4 cores → ~6 hours
> - Building with 16 cores → ~1.5 hours
>
> AOSP recommends a multi-core processor (8+ cores).

---

## 🔧 Tools & Software

### 6. JDK (Java Development Kit)

A toolbox for writing and running Java programs. Android's framework is partly written in Java.

> **Example:** JDK is like a carpenter's toolkit:
> - Hammer (`javac` compiler) → builds the code
> - Measuring tape (debugger) → finds errors

```bash
sudo apt install openjdk-11-jdk
```

---

### 7. Python

A programming language used to write AOSP's build scripts.

> **Example:** Python tells the computer step-by-step what to do:
> "Download this file, then compile that code, then package it."

```bash
sudo apt install python3
```

---

### 8. Git

A "version control" tool — tracks every change made to code.

> **Example:** Like Google Docs "Version History":
> - You can see who changed what and when
> - You can go back to an older version if something breaks

```bash
git log       # shows history of changes
git checkout  # go back to a previous version
```

---

### 9. Repo Tool

A special tool made by Google to manage **multiple** Git projects at once. AOSP has 800+ individual Git projects (repositories).

> **Example:**
> - Git = manages 1 project (like tracking 1 student's grades)
> - Repo = manages 800+ projects (like tracking ALL students in a school)

```bash
mkdir ~/bin
curl https://storage.googleapis.com/git-repo-downloads/repo > ~/bin/repo
chmod a+x ~/bin/repo
```

---

### 10. Manifest File (`default.xml`)

A "shopping list" that tells Repo which projects to download.

> **Example:** Like a recipe's ingredient list:
> - Download `frameworks/base` from this URL
> - Download `packages/apps/Settings` from this URL
> - Download 798 more things...

---

## 📥 Downloading AOSP

### 11. `repo init`

"Prepare to download" — sets up the folder structure and tells Repo **where** to get the code and **which version**.

```bash
repo init -u https://android.googlesource.com/platform/manifest -b android-14.0.0_r1
```

- `-u` = URL (the web address where the code lives)
- `-b` = Branch (which version of Android)

> **Think of it like:** "I want to order from THIS restaurant (`-u`), and I want the lunch menu (`-b`)."

---

### 12. Branch

A **version** or **copy** of the code.

> **Example:**
> - `android-14.0.0_r1` → Android 14, release 1
> - `android-13.0.0_r1` → Android 13, release 1
> - `main` → Latest development (not stable)
>
> Like a book:
> - 1st Edition (Branch: `v1`)
> - 2nd Edition (Branch: `v2`) — has corrections
> - Draft (Branch: `main`) — still being written

---

### 13. `repo sync`

"Download everything NOW" — fetches all 800+ projects.

```bash
repo sync -j8
```

- `-j8` = use 8 parallel downloads (like 8 people downloading different parts)

> Downloads ~100 GB of code. Takes 30 minutes to several hours depending on internet speed.

---

### 14. Mirror

A full **local copy** of the entire AOSP stored on your computer, so you don't re-download everything each time.

> **Example:** Like photocopying a library book — instead of going to the library every day, you keep a copy at home.

```bash
repo init --mirror -u https://android.googlesource.com/platform/manifest
```

---

## 🏗️ Building AOSP

### 15. `source build/envsetup.sh`

"Load the build tools into your terminal." Like loading bullets into a gun before shooting.

```bash
source build/envsetup.sh
```

> - Without this: `lunch: command not found`
> - With this: `lunch` works!
>
> `envsetup.sh` = "environment setup script"
> `source` = "run this script and keep its effects active"

---

### 16. `lunch`

"Choose what you want to build" — pick the **device** and **build type**.

```bash
lunch aosp_x86_64-eng
```

| Part | Meaning |
|---|---|
| `aosp` | Base Android (no company modifications) |
| `x86_64` | For Intel/AMD computers (not phones) |
| `arm64` | For ARM phones (Samsung, Pixel, etc.) |
| `eng` | Engineering build (for developers) |

> **Think of it like ordering food:**
> `lunch [dish_name]-[spice_level]`
> `lunch aosp_bluejay-userdebug`
> → Pixel 6a, medium debug level

---

### 17. Build Variants (`eng` / `userdebug` / `user`)

| Variant | Meaning |
|---|---|
| `eng` | **Engineer build** — all debugging tools ON, full root access. Like a car with the hood open for mechanics. |
| `userdebug` | **User + Debug build** — mostly like a real phone, but debug tools and root access available. Like a normal car with mechanic tools in the trunk. |
| `user` | **Production build** — no debugging, no root access. Like a car sold to customers with a locked hood. |

---

### 18. `m` or `make`

"START BUILDING!" — compiles all the code into a working Android system.

```bash
m -j16
```

- `m` = "make everything"
- `-j16` = use 16 CPU cores (parallel workers)

> **Like building a house:**
> - `-j1` = 1 worker → takes forever
> - `-j16` = 16 workers → much faster!
>
> Build time: **1–6 hours** depending on computer power.

---

### 19. Compile / Compilation

Converting human-readable code → machine-readable code (0s and 1s).

> **Example:**
> - Human writes: `System.out.println("Hello");` (Java code)
> - Compiler produces: `01001000 01100101 01101100...` (machine code)
>
> The compiler is the **translator** between Java and the CPU.

---

### 20. Build System (Soong / Blueprint)

The system that knows **how** to compile everything in the right order.

- **Soong** — AOSP's current build system, written in Go. Reads `Android.bp` files.
- **Blueprint (`.bp`)** — A file that says "here's what to build and how."

```bp
cc_binary {
    name: "my_app",           // Name of the program
    srcs: ["main.cpp"],       // Source code files
    shared_libs: ["liblog"],  // Libraries it depends on
}
```

> **Like a recipe card:**
> - Name: Chocolate Cake
> - Ingredients: flour, eggs, chocolate
> - Depends on: oven being preheated

---

### 21. Makefile (`Android.mk`) — Old System

Older version of `Android.bp`, still used in some places. Being replaced by Soong.

```makefile
LOCAL_PATH := $(call my-dir)
include $(CLEAR_VARS)
LOCAL_MODULE := my_app
LOCAL_SRC_FILES := main.cpp
include $(BUILD_EXECUTABLE)
```

---

### 22. Ninja

The actual "worker" that runs compilation commands super fast. Soong creates the instructions → Ninja executes them.

> **Example:**
> - Soong = Architect (draws the blueprint)
> - Ninja = Construction crew (builds based on blueprint)
>
> You don't interact with Ninja directly — Soong handles it.

---

## 📂 AOSP Directory Structure

```
aosp/
├── art/            → Android Runtime (engine that runs apps)
├── bionic/         → C library (basic building blocks for the system)
├── bootable/       → Bootloader & Recovery (what starts Android)
├── build/          → Build system files (how to compile everything)
├── cts/            → Compatibility Test Suite (tests for certification)
├── dalvik/         → Old runtime (replaced by ART)
├── device/         → Device-specific configs (Pixel, emulator, etc.)
├── external/       → Third-party libraries (SQLite, zlib, etc.)
├── frameworks/     → ★ CORE Android Framework (Activity, View, etc.)
│   ├── base/       → THE main framework code
│   └── native/     → C++ framework code
├── hardware/       → HAL (Hardware Abstraction Layer)
├── kernel/         → Linux Kernel source
├── packages/       → Built-in apps (Settings, Launcher, Camera)
├── system/         → Core system components (init, adb, etc.)
├── vendor/         → Vendor/company specific code
└── out/            → ★ Build output (the final compiled Android)
```

---

### 23. `frameworks/base`

The **heart** of Android — contains Activity, Service, View, Window Manager, Package Manager, and more.

> **Example:** When you write this in an app:
> ```java
> startActivity(new Intent(this, SecondActivity.class));
> ```
> The code that makes `startActivity()` work lives in `frameworks/base`.

---

### 24. HAL (Hardware Abstraction Layer)

A "translator" between Android software and hardware.

> **Example:**
> - Your app says: "Turn on the camera"
> - Android Framework says: "OK, HAL, please talk to the camera hardware"
> - HAL says to hardware: "Hey sensor, start capturing images"
>
> Why? Because Samsung's camera chip is different from Google's. HAL hides these differences — Android doesn't need to know the details.
>
> Like a **universal remote** — works with any TV brand.

---

### 25. Kernel

The **core** of the operating system — manages hardware directly.

> **Example:** If Android is a car:
> - Apps = passengers
> - Framework = dashboard & steering wheel
> - HAL = transmission
> - Kernel = **ENGINE**

---

### 26. ART (Android Runtime)

The engine that actually **runs** your Android apps.

> **Example:** You write Java/Kotlin → compiled to DEX format → ART runs it.
>
> - **Dalvik (old):** Translating a book one page at a time while reading
> - **ART (new):** Translating the whole book before you start reading (AOT = Ahead Of Time compilation → faster)

---

### 27. Bionic

Android's version of `libc` — the basic C library. Provides fundamental functions like memory allocation, math, and strings.

> **Example:**
> - `printf("Hello")` → uses Bionic's implementation
> - `malloc(100)` → uses Bionic to allocate memory
>
> Desktop Linux uses `glibc`. Android uses **Bionic** (smaller, faster, designed for mobile).

---

## 📤 Output & Flashing

### 28. `out/` Directory

Where the finished build goes — the "output" folder.

```
out/target/product/generic_x86_64/
├── system.img     → The main Android system
├── boot.img       → Kernel + ramdisk (what boots the phone)
├── vendor.img     → Hardware-specific drivers
├── userdata.img   → Empty user data partition
└── recovery.img   → Recovery mode image
```

---

### 29. IMG File (Image File)

A complete **snapshot** of a partition, ready to be written to a device.

> **Example:** `system.img` contains ALL the system files (framework, apps, libraries).
> Like a "zip file" of an entire hard drive section — you **flash** this onto the phone's storage.

---

### 30. Flash / Flashing

**Writing / installing** the Android build onto a phone's storage.

```bash
fastboot flash system system.img
```

> "Take `system.img` and write it to the phone's system partition."
> Like burning a CD — you write data onto the disk. Except here, you write Android onto the phone's internal storage.

---

### 31. Fastboot

A tool + phone mode used to flash images onto a device.

> **Example:**
> 1. Put phone in fastboot mode (hold Power + Volume Down)
> 2. Connect USB cable
> 3. Run: `fastboot flash boot boot.img`
>
> Fastboot = direct communication with the phone's bootloader. Like "safe mode" but even lower level — for installing the OS itself.

---

### 32. ADB (Android Debug Bridge)

A tool to communicate with an Android device from your computer.

```bash
adb devices          # list connected devices
adb shell            # open a terminal ON the phone
adb install app.apk  # install an app
adb logcat           # see live logs from the phone
```

> Like **SSH for Android** — remote control via USB or WiFi.

---

### 33. Emulator

A **virtual phone** that runs on your computer (no real phone needed!).

```bash
emulator &   # opens a fake phone window on your screen
```

> - `x86_64` builds → for emulator (faster)
> - `arm64` builds → for real phones
>
> Useful for testing when you don't have a physical device.

---

## 🧪 Testing Terms

### 34. CTS (Compatibility Test Suite)

Google's test to check if your Android build is "real Android." Required to ship Google Play Store.

> **Example:** Tests things like:
> - Does the camera API work correctly?
> - Does Bluetooth follow the standard?
> - Does Activity lifecycle behave properly?
>
> Like a **driving test** — you must pass to get a license.

---

### 35. VTS (Vendor Test Suite)

Tests specifically for the **hardware layer** (HAL).

> **Example:**
> - "Does the fingerprint sensor HAL return results in the correct format?"
> - "Does the audio HAL support all required sample rates?"

---

### 36. GTS (Google Test Suite)

Tests for Google Mobile Services (GMS) — Play Store, Gmail, Maps, etc.

> **Example:** "Can Google Play Store install apps?" / "Does Google Maps get location correctly?"
> Not open source — only for licensed manufacturers.

---

## 🔄 Complete AOSP Setup Flow

```bash
# Step 1: Install dependencies
sudo apt update
sudo apt install git-core gnupg flex bison build-essential \
  zip curl zlib1g-dev libc6-dev-i386 x11proto-core-dev \
  libx11-dev lib32z1-dev libgl1-mesa-dev libxml2-utils \
  xsltproc unzip fontconfig python3 openjdk-11-jdk

# Step 2: Install Repo tool
mkdir ~/bin
export PATH=~/bin:$PATH
curl https://storage.googleapis.com/git-repo-downloads/repo > ~/bin/repo
chmod a+x ~/bin/repo

# Step 3: Create working directory
mkdir ~/aosp
cd ~/aosp

# Step 4: Initialize Repo (choose Android version)
repo init -u https://android.googlesource.com/platform/manifest \
  -b android-14.0.0_r1

# Step 5: Download source code (~100GB)
repo sync -j$(nproc)

# Step 6: Setup build environment
source build/envsetup.sh

# Step 7: Choose target
lunch aosp_x86_64-eng          # for emulator
# OR
lunch aosp_bluejay-userdebug   # for Pixel 6a

# Step 8: Build (1–6 hours)
m -j$(nproc)

# Step 9: Run / test
emulator &          # on emulator
# OR
fastboot flashall   # on real device
```

```bash

## Step 5 — Install Repo Tool

```bash
# Create bin directory in home folder
mkdir -p ~/bin

# Add bin to PATH so the computer can find the repo command
export PATH=~/bin:$PATH

# Download repo tool
curl https://storage.googleapis.com/git-repo-downloads/repo > ~/bin/repo

# Give execute permission
chmod a+x ~/bin/repo

# Verify installation
repo --version
```

| Command | Meaning |
|---|---|
| `mkdir ~/bin` | Create a folder called `bin` in your home directory |
| `export PATH` | Tell the computer to look in `~/bin` for commands |
| `curl` | Download the repo script from Google's server |
| `chmod a+x` | Give permission to run the file (make it executable) |

## Step 6 — Make PATH Permanent

```bash
# Add to .bashrc so it loads every time a terminal opens
echo 'export PATH=~/bin:$PATH' >> ~/.bashrc

# Apply changes now without restarting the terminal
source ~/.bashrc
```

## Step 7 — Create AOSP Working Directory

```bash
# Create folder (use a drive with 400 GB+ free)
mkdir -p ~/aosp

# Go into that folder
cd ~/aosp
```

> Make a new empty folder where all Android code will be downloaded — like creating an empty room before moving furniture in.

---

## Step 8 — Initialize Repo (Choose Android Version)

```bash
repo init \
  -u https://android.googlesource.com/platform/manifest \
  -b android-14.0.0_r1
```

| Flag | Meaning |
|---|---|
| `repo init` | "Prepare this folder for AOSP download" |
| `-u` | URL — where the master list of code lives |
| `-b` | Branch — which version of Android |

### Common Branch Names

| Branch | Android Version |
|---|---|
| `android-14.0.0_r1` | Android 14 (latest) |
| `android-13.0.0_r83` | Android 13 |
| `android-12.1.0_r27` | Android 12L |
| `android-12.0.0_r34` | Android 12 |
| `android-11.0.0_r48` | Android 11 |
| `main` | Latest (unstable / dev) |

---

## Step 9 — Download Source Code

```bash
repo sync -j$(nproc) --no-clone-bundle --no-tags
```

| Flag | Meaning |
|---|---|
| `repo sync` | Start downloading everything |
| `-j$(nproc)` | Use all available CPU cores for parallel download |
| `--no-clone-bundle` | Download smaller chunks (faster) |
| `--no-tags` | Don't download extra tag info (saves space) |

> `$(nproc)` automatically detects how many CPU cores you have. If you have 8 cores → becomes `-j8`.
>
> Downloads ~100 GB. Time: 30 minutes to several hours.

```bash
# If sync fails, run again — it resumes automatically:
repo sync -j$(nproc) --no-clone-bundle --no-tags
```

---

## Step 10 — Check Download Complete

```bash
# Check size of downloaded code (~80–120 GB expected)
du -sh ~/aosp/

# Check important folders exist:
ls ~/aosp/frameworks/
ls ~/aosp/packages/
ls ~/aosp/system/
```

---

## Step 11 — Setup Build Environment

```bash
# Must be inside the aosp directory
cd ~/aosp

# Load build tools into current terminal session
source build/envsetup.sh
```

Expected output:
```
including device/generic/car/vendorsetup.sh
including device/generic/mini-emulator-arm64/vendorsetup.sh
including device/generic/x86/vendorsetup.sh
...
```

> This "activates" special AOSP commands like `lunch`, `m`, `mm`, `mmm`, `adb`, `fastboot`. Without this → these commands won't work!

## Step 12 — Choose What to Build (`lunch`)

```bash
# For emulator (most common for beginners):
lunch aosp_x86_64-eng

# For Pixel 6a:
lunch aosp_bluejay-userdebug

# For Pixel 7:
lunch aosp_panther-userdebug

# See ALL available targets:
lunch
```

**Format:** `lunch [PRODUCT]-[BUILD_VARIANT]`

| Part | Options | Meaning |
|---|---|---|
| **Product** | `aosp_x86_64` | Generic Android for x86_64 emulator |
| | `aosp_arm64` | Generic Android for ARM64 devices |
| | `aosp_bluejay` | Pixel 6a |
| | `aosp_panther` | Pixel 7 |
| **Variant** | `eng` | Full debug (for developers) |
| | `userdebug` | Semi-debug (for testing on real device) |
| | `user` | Final release (for end users) |

Expected output after `lunch`:
```
============================================
PLATFORM_VERSION_CODENAME=REL
PLATFORM_VERSION=14
TARGET_PRODUCT=aosp_x86_64
TARGET_BUILD_VARIANT=eng
TARGET_ARCH=x86_64
...
============================================
```

---

## Step 13 — Start Building

```bash
m -j$(nproc)
```

| Flag | Meaning |
|---|---|

## 📊 What Happens During a Build

**Phase 1 — Analyzing** *(a few minutes)*

Reads all `Android.bp` and `Android.mk` files, figures out what needs to be built, creates build plan.

```
Starting build with ninja...
[analyzing dependencies...]
```

**Phase 2 — Compiling** *(majority of time)*

Compiles C/C++ files (`.c`, `.cpp` → `.o`), Java files (`.java` → `.class` → `.dex`), AIDL files, and resource files.

```
[  5% 2000/40000] Compiling C++ frameworks/native/...
[ 10% 4000/40000] Compiling Java frameworks/base/...
[ 15% 6000/40000] Building AIDL...
```

**Phase 3 — Linking** *(30–60 minutes)*

Links compiled pieces together, creates `.so` libraries and executables.

```
[ 80% 32000/40000] Linking libandroid_runtime.so...
[ 85% 34000/40000] Linking system_server...
```

**Phase 4 — Packaging** *(30–60 minutes)*

Packages everything into `.img` files.

```
[ 95% 38000/40000] Packaging system.img...
[100% 40000/40000] Build Complete!
```

## 📄 Manifest Files — Complete Explanation

### What is a Manifest?

A **master list** that tells the `repo` tool which git repositories to download, from which URLs, at which versions.

> Without manifest: You'd need to manually clone 800+ git repos.
> With manifest: `repo sync` downloads all 800+ automatically.

Location: `.repo/manifest.xml` (created after `repo init`)

---

### `manifest.xml` — Full Structure

```xml
<?xml version="1.0" encoding="UTF-8"?>
<manifest>

  <!-- 1. REMOTE — WHERE to download FROM -->
  <remote  name="aosp"
           fetch="https://android.googlesource.com"
           review="https://android-review.googlesource.com" />
  <!--
    name="aosp"  → nickname for this server
    fetch=       → base URL of all repositories
    review=      → Gerrit code review server URL

    Example: fetch="https://android.googlesource.com"
             + project path="platform/frameworks/base"
             = https://android.googlesource.com/platform/frameworks/base
  -->

  <!-- 2. DEFAULT — Default settings -->
  <default revision="refs/tags/android-14.0.0_r1"
           remote="aosp"
           sync-j="4"
           sync-c="true" />
  <!--
    revision=  → Default branch/tag (if project doesn't specify)
    remote=    → Default remote server
    sync-j=    → Default parallel download threads
    sync-c=    → Only download current branch (saves space)
  -->

  <!-- 3. PROJECT — WHAT to download -->

  <project path="art"
           name="platform/art"
           groups="pdk" />
  <!--
    path= → WHERE to put it on your computer (local folder)
    name= → repository name on server
    Full URL = fetch_url + name
             = https://android.googlesource.com/platform/art
    groups= → categorize projects (optional)
  -->

  <project path="bionic"
           name="platform/bionic"
           groups="pdk" />

  <project path="build/soong"
           name="platform/build/soong"
           clone-depth="1" />
  <!--
    clone-depth="1" → Only download latest version, not full history.
                      Saves disk space and time!
  -->

  <project path="frameworks/base"
           name="platform/frameworks/base"
           groups="pdk-cw-fs,pdk-fs" />

  <project path="packages/apps/Settings"
           name="platform/packages/apps/Settings" />

  <project path="packages/apps/Launcher3"
           name="platform/packages/apps/Launcher3" />

  <!-- Device specific -->
  <project path="device/google/bluejay"
           name="device/google/bluejay"
           remote="aosp" />

  <!-- With a branch override (different from default) -->
  <project path="kernel/google/redbull"
           name="kernel/google/redbull"
           revision="android-msm-redbull-4.19-android12"
           remote="aosp" />
  <!--
    revision= here OVERRIDES the default revision.
    This kernel uses a DIFFERENT branch than the rest of AOSP.
  -->

  <!-- With annotation -->
  <project path="external/sqlite"
           name="platform/external/sqlite">
    <annotation name="Mad-Author" value="sqlite_team" />
  </project>

  <!-- 4. COPYFILE — Copy a file after sync -->
  <project path="build/make" name="platform/build">
    <copyfile src="core/root.mk" dest="Makefile" />
  </project>
  <!--
    After downloading, copies:
    build/make/core/root.mk → ./Makefile (root of AOSP)
    This is how the top-level Makefile gets created!
  -->

  <!-- 5. LINKFILE — Create a symlink -->
  <project path="build/make" name="platform/build">
    <linkfile src="CleanSpec.mk" dest="CleanSpec.mk" />
  </project>

  <!-- 6. REMOVE-PROJECT — Exclude a project -->
  <remove-project name="platform/packages/apps/Browser2" />
  <!--
    Removes this project from download.
    Used in local manifests to remove things you don't want.
  -->

  <!-- 7. INCLUDE — Include another manifest -->
  <include name="default.xml" />
  <!--
    Merges another manifest file — like #include in C.
  -->

  <!-- 8. EXTEND-PROJECT — Modify an existing project -->
  <extend-project name="platform/frameworks/base"
                  groups="my-custom-group" />
  <!--
    Add extra attributes to an already-defined project
    without redefining it completely.
  -->

</manifest>
```

## 🌿 Branch Interpretation — Complete Guide

### Branch Naming Format

```
android  -  14  .  0  .  0  _  r  1
   ↑         ↑     ↑     ↑     ↑  ↑
   │         │     │     │     │  └── Release number
   │         │     │     │     └───── 'r' = release
   │         │     │     └─────────── Patch version
   │         │     └───────────────── Minor version
   │         └─────────────────────── Major version (Android version)
   └───────────────────────────────── Always "android"
```

### Branch Examples Decoded

| Branch Name | Meaning |
|---|---|
| `android-14.0.0_r1` | Android 14, first release |
| `android-14.0.0_r25` | Android 14, 25th update (bug fixes) |
| `android-13.0.0_r1` | Android 13, first release |
| `android-13.0.0_r83` | Android 13, 83rd update (very stable) |
| `android-12.1.0_r1` | Android 12L (tablet version) |
| `android-12.0.0_r34` | Android 12, 34th update |
| `android-11.0.0_r1` | Android 11, first release |
| `main` | Latest development (**UNSTABLE!**) |
| `master` | Old name for `main` branch |
| `android-security-14.0.0_r1` | Security-only patch for Android 14 |

### Special Branch Types

| Type | Example | Characteristics |
|---|---|---|
| **Release** | `android-14.0.0_r1` | Stable, tested, used in production phones. Safe to use. |
| **Development** | `main` / `master` | Latest code actively being developed. May have bugs. |
| **Security** | `android-security-13.0.0_r83` | Security patches only, no new features. |
| **Kernel** | `android-msm-redbull-4.19-android12` | Different format: chipset + device + kernel version + Android version. |
| **Refs/Tags** | `refs/tags/android-14.0.0_r1` | Exact specific commit — immutable snapshot, never changes. |
| **Refs/Heads** | `refs/heads/main` | Points to latest commit on a branch — changes as new commits arrive. |

---

### How Revision Works in Manifest

```xml
<!-- OPTION 1: Tag — specific snapshot (RECOMMENDED) -->
<default revision="refs/tags/android-14.0.0_r1" />
<!--
  STABLE: This commit will NEVER change.
  Like: "Use exactly page 42 of this book, always."
-->

<!-- OPTION 2: Branch — moving target -->
<default revision="refs/heads/main" />
<!--
  UNSTABLE: Gets new commits daily.
  Like: "Use the latest page of this book (keeps changing)."
-->

<!-- OPTION 3: Short name — auto-detected -->
<default revision="android-14.0.0_r1" />
<!--
  Repo auto-detects if it's a tag or branch. Simpler to write.
-->

<!-- OPTION 4: Specific commit hash -->
<project name="platform/frameworks/base"
         revision="a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2" />
<!--
  40-character SHA hash = EXACT commit.
  Most specific — locks to one exact change.
  Like: "Use exactly line 3, page 42, edition 2."
-->
```

## 🔄 How Repo Uses the Manifest

```
STEP 1: repo init -u [URL] -b [BRANCH]
   │
   ├── Downloads the manifest repository from URL
   ├── Checks out the branch [BRANCH]
   └── Creates .repo/manifests/ with manifest.xml

STEP 2: repo sync
   │
   ├── Reads .repo/manifest.xml
   ├── Also reads .repo/local_manifests/*.xml
   │
   ├── For EACH <project> entry:
   │   ├── Reads: name, path, remote, revision
   │   ├── Constructs full URL: remote.fetch + name
   │   ├── Downloads git repo to .repo/projects/
   │   └── Checks out revision into: path/
   │
   └── Runs all <copyfile> and <linkfile> operations
```

Example for one project:

```xml
<remote name="aosp" fetch="https://android.googlesource.com"/>
<project name="platform/frameworks/base" path="frameworks/base"
         revision="refs/tags/android-14.0.0_r1"/>
```

Repo does:
```
URL = https://android.googlesource.com + platform/frameworks/base
    = https://android.googlesource.com/platform/frameworks/base

git clone [URL] → .repo/projects/platform/frameworks/base.git
git checkout refs/tags/android-14.0.0_r1
Put files in → frameworks/base/
```
