## 1. AOSP Basics

---

**Q1. What is AOSP and why does it exist?**

<details>
<summary>Answer</summary>

**AOSP = Android Open Source Project** — the free, open-source base code of Android that Google maintains and shares with everyone.

**Why it exists:**

1. **Open Source Philosophy** — anyone can view, modify, and use the code, promoting innovation and collaboration.
2. **Device Manufacturer Freedom** — Samsung, Xiaomi, OnePlus take AOSP, add their own UI, and ship their own Android version.
3. **Transparency** — users and developers can see exactly what their OS is doing.
4. **Ecosystem Growth** — more manufacturers → more devices → more users → more apps.

```
AOSP (Base Code)
     ↓
Samsung → adds One UI → Galaxy phones
Xiaomi  → adds MIUI   → Mi phones
Google  → adds GMS    → Pixel phones
LineageOS → keeps clean → Custom ROM
```

**Key point:** AOSP ≠ Full Android. AOSP + GMS (Google Mobile Services) = Full Android. GMS includes Play Store, Gmail, Maps — and is **not** open source.

</details>

---

**Q2. What is the difference between AOSP and Android?**

<details>
<summary>Answer</summary>

| | AOSP | Android (Commercial) |
|---|---|---|
| License | Free & Open | Has proprietary components |
| Play Store | ❌ Not included | ✅ Included |
| Google Apps | ❌ None | ✅ Gmail, Maps, YouTube |
| Usage | Anyone can use freely | Need Google license for GMS |
| Composition | Base framework only | AOSP + GMS + OEM customization |
| Certification | None required | Needs CTS/GTS certification |

> **Analogy:** AOSP = plain bread (free recipe, anyone can bake). Android = sandwich (bread + fillings like Google apps).

**Real example:** Amazon Fire tablets run AOSP but NOT Android — they have no Google Play Store and use their own App Store instead.

</details>

**Q3. What is the `repo` tool and why is it needed?**

<details>
<summary>Answer</summary>

`repo` is a tool created by Google to manage **multiple Git repositories at once**.

**Why needed:** AOSP has 800+ separate Git repositories. Without `repo`, you'd need to manually `git clone` every one of them. With `repo sync`, all 800+ are downloaded in a single command.

| | Git | Repo |
|---|---|---|
| Manages | 1 repository | 800+ repositories |
| Download | `git clone` (per repo) | `repo sync` (all at once) |
| Branch | `git checkout` | `repo start` (all repos) |
| Status | `git status` | `repo status` (all repos) |

> **Analogy:** Git = managing 1 student's grades. Repo = managing ALL students in the entire school.

**Key repo commands:**

```bash
repo init    # Set up + choose Android version
repo sync    # Download/update all code
repo status  # See changes across all repos
repo diff    # See diffs across all repos
repo start   # Create new branch in all repos
repo upload  # Upload changes for code review
repo forall  # Run a command in every repo
```

</details>

---

**Q4. What is the difference between `repo init` and `repo sync`?**

<details>
<summary>Answer</summary>

| Command | What it does |
|---|---|
| `repo init -u [URL] -b [BRANCH]` | Sets up the folder, downloads the manifest, chooses Android version — **no source code yet** |
| `repo sync` | Actually downloads all 800+ source repositories — this is the ~100 GB download |

```bash
# Step 1 — prepare (tiny download, just the manifest)
repo init -u https://android.googlesource.com/platform/manifest \
  -b android-14.0.0_r1

# Step 2 — download everything (~100 GB)
repo sync -j$(nproc) --no-clone-bundle --no-tags
```

- `-j$(nproc)` — uses all CPU cores for parallel download
- `--no-clone-bundle` — downloads smaller chunks (faster)
- `--no-tags` — skips extra tag info (saves space)

If `repo sync` fails partway through, simply re-run the same command — it resumes automatically.

</details>

## 2. Build System

---

**Q5. Explain the AOSP Build System — Soong vs Make.**

<details>
<summary>Answer</summary>

AOSP has two build systems:

**Old system: Make (`Android.mk`)**
- Uses `.mk` (Makefile) files
- Slow for large projects, hard to maintain
- Still present in some legacy code

```makefile
LOCAL_PATH := $(call my-dir)
include $(CLEAR_VARS)
LOCAL_MODULE    := my_module
LOCAL_SRC_FILES := main.cpp
include $(BUILD_EXECUTABLE)
```

**New system: Soong (`Android.bp`)**
- Uses `.bp` (Blueprint) files, written in Go
- Much faster, better dependency management
- Google is migrating everything to Soong

```bp
cc_binary {
    name: "my_module",
    srcs: ["main.cpp"],
    shared_libs: ["liblog"],
}
```

**How they work together:**

```
Android.bp → Blueprint → Soong → Ninja rules → Ninja executes → Compiled output
```

> **Analogy:** Make = old typewriter (works but slow). Soong = modern computer (fast and efficient). Ninja = the actual typist doing the work.

**Interview insight:** Soong replaced Make because AOSP grew too large. With 800+ projects, Make was taking hours just to analyze dependencies. Soong does this in minutes.

</details>

---

**Q6. What does `source build/envsetup.sh` do?**

<details>
<summary>Answer</summary>

It **loads the build environment into your current terminal session**, making AOSP-specific commands available.

**Commands it adds:**

| Command | Purpose |
|---|---|
| `lunch` | Choose target device/variant |
| `m` | Build everything |
| `mm` | Build current directory module |
| `mmm [path]` | Build specific module by path |
| `mma` | Build module + all dependencies |
| `croot` | `cd` to AOSP root directory |
| `cgrep` | `grep` in C/C++ files |
| `jgrep` | `grep` in Java files |
| `godir` | Go to directory of a file |

**Important:** Must be run **every time** you open a new terminal. Without it: `lunch: command not found`. After it: everything works.

> **Analogy:** Like putting on a tool belt before starting work. The tools are always there, but you need to wear the belt to use them.

</details>

---

**Q7. What is the `lunch` command? Explain build variants.**

<details>
<summary>Answer</summary>

`lunch` = choose **what to build** and for **which device**.

**Format:** `lunch [PRODUCT]-[BUILD_VARIANT]`

```bash
lunch aosp_x86_64-eng
#     ↑           ↑
#  PRODUCT     VARIANT
```

**Products:**

| Product | Description |
|---|---|
| `aosp_x86_64` | Generic build for PC emulator (Intel/AMD) |
| `aosp_arm64` | Generic build for ARM device |
| `aosp_bluejay` | Google Pixel 6a |
| `aosp_panther` | Google Pixel 7 |

**Variants:**

| Variant | Features | Use When |
|---|---|---|
| `eng` | All debug tools ✅, root access ✅, ADB always on ✅, slow ❌ | Active development |
| `userdebug` | Root ✅, debug tools ✅, close to production ✅ | QA testing on real device |
| `user` | No root ❌, no debug ❌, optimized ✅, secure ✅ | Final product for customers |

> **Analogy:** `eng` = car with hood open for mechanics. `userdebug` = car with diagnostics port accessible. `user` = car sold to customers with hood locked.

</details>

---

**Q8. What is the difference between `m`, `mm`, `mmm`, and `mma`?**

<details>
<summary>Answer</summary>

| Command | Builds | Use Case |
|---|---|---|
| `m` | Everything | First full build |
| `m [module]` | Specific named module | Know the module name |
| `mm` | Module in current directory | Already `cd`'d into it |
| `mmm [path]` | Module at given path | Know exact path, from anywhere |
| `mma` | Module + its dependencies | Dependencies also changed |
| `mmma [path]` | Path + dependencies | Full module build with deps |

```bash
m -j16                                # Build all of AOSP
m Settings                            # Build only Settings
cd packages/apps/Settings && mm -j8  # Build Settings (from inside dir)
mmm packages/apps/Settings -j$(nproc) # Build Settings (from anywhere)
```

**Practical answer:** In daily development, `mm` or `mmm` is used to rebuild just the module being worked on. Full `m` is only used when setting up fresh or when many modules have changed.

</details>

---

**Q9. What are the four phases of an AOSP build?**

<details>
<summary>Answer</summary>

| Phase | Duration | What Happens |
|---|---|---|
| **Analyzing** | A few minutes | Reads all `Android.bp` / `Android.mk` files, determines what to build, creates build plan |
| **Compiling** | Majority of time | Compiles `.c`/`.cpp` → `.o`, `.java` → `.class` → `.dex`, AIDL files, resource files |
| **Linking** | 30–60 minutes | Links compiled pieces into `.so` libraries and executables |
| **Packaging** | 30–60 minutes | Packages everything into `.img` files (`system.img`, `boot.img`, `vendor.img`) |

**Build time estimates:**

| Cores | Time |
|---|---|
| 4 | 4–6 hours |
| 8 | 2–3 hours |
| 16 | 1–1.5 hours |
| 32 | 30–45 minutes |

</details>

---

**Q10. What does `ccache` do and why use it?**

<details>
<summary>Answer</summary>

`ccache` is a compiler cache — it stores the results of previous compilations so that if the same file is compiled again with the same inputs, it uses the cached result instead of recompiling.

```bash
export USE_CCACHE=1
export CCACHE_DIR=~/.ccache
ccache -M 50G     # Set 50 GB cache size
m -j$(nproc)
```

- **First build:** normal speed (no cache yet)
- **Second build:** 2–5× faster (cache hits)

Especially useful when you `make clean` and rebuild, or switch between branches frequently. 50 GB is the recommended cache size for AOSP.

</details>

## 3. Directory Structure

---

**Q11. Explain the top-level AOSP directory structure. What lives where?**

<details>
<summary>Answer</summary>

| Directory | Purpose |
|---|---|
| `frameworks/` ★ | **Core Android Framework** — Activity, Service, View, Intent, all Java APIs |
| `packages/` | All built-in applications — Settings, Launcher, Dialer, Camera |
| `system/` | Core system components — `init` (PID 1), ADB, logd, vold |
| `hardware/` | HAL interface definitions (HIDL/AIDL) |
| `device/` | Device-specific configs — Pixel codenames, board configs |
| `kernel/` | Linux kernel source |
| `art/` | Android Runtime — runs your APK code |
| `bionic/` | Android's C library (like glibc but smaller/faster) |
| `external/` | Third-party open source libraries — SQLite, OpenSSL, zlib |
| `build/` | Build system — Soong, Blueprint, Ninja templates |
| `out/` | **Build output** (not source) — `system.img`, `boot.img`, `vendor.img` |

**Key examples:**
- `Activity.java` lives in: `frameworks/base/core/java/android/app/Activity.java`
- Settings app lives in: `packages/apps/Settings/`
- `ls` command lives in: `system/core/toolbox/ls.cpp`

</details>

---

**Q12. What is `frameworks/base` and why is it the most important directory?**

<details>
<summary>Answer</summary>

`frameworks/base` is **the heart of Android** — it contains every core API that Android developers use.

```
frameworks/base/
├── core/java/android/
│   ├── app/        → Activity, Service, BroadcastReceiver
│   ├── content/    → Context, Intent, ContentProvider
│   ├── view/       → View, ViewGroup, all UI widgets
│   ├── widget/     → TextView, Button, RecyclerView
│   ├── os/         → Handler, Looper, Bundle, Binder
│   └── graphics/   → Canvas, Paint, Bitmap
│
└── services/java/com/android/server/
    ├── ActivityManagerService.java   → Manages apps/activities
    ├── WindowManagerService.java     → Manages windows/display
    ├── PackageManagerService.java    → Manages APK installs
    └── PowerManagerService.java      → Manages battery/sleep
```

When you write `startActivity(...)` in your app, the code that **makes it work** lives in `frameworks/base`. When you call `btn.setOnClickListener(...)`, the `Button` class lives in `frameworks/base/core/java/android/widget/Button.java`.

</details>

---

**Q13. What is `bionic/` and how does it differ from `glibc`?**

<details>
<summary>Answer</summary>

`bionic` is Android's version of the **C standard library** (`libc`), replacing `glibc` used by desktop Linux.

```
bionic/
├── libc/    → C Standard Library (malloc, printf, stdio, DNS...)
├── libm/    → Math library (sin, cos, sqrt...)
├── libdl/   → Dynamic linker library
└── linker/  → Dynamic linker (loads .so files at runtime)
```

| | glibc (Desktop Linux) | Bionic (Android) |
|---|---|---|
| Size | Large | Smaller |
| Performance | General purpose | Optimized for mobile |
| License | LGPL | BSD |
| Threading | pthreads | Custom Android threads |

When any C/C++ code calls `malloc()` or `printf()`, those functions are implemented in `bionic/libc/`.

</details>

---

**Q14. What is `external/` and give examples of what lives there?**

<details>
<summary>Answer</summary>

`external/` contains **third-party open source libraries** that Android uses but didn't write. They are pulled in as-is from upstream open source projects.

Key examples:

| Library | Purpose |
|---|---|
| `external/sqlite` | SQLite database engine |
| `external/openssl` | Security / Encryption |
| `external/zlib` | Compression |
| `external/libpng` / `libjpeg` | Image format libraries |
| `external/chromium` | Web rendering engine |
| `external/llvm` / `clang` | Compiler toolchain |
| `external/curl` | HTTP library |
| `external/conscrypt` | TLS/SSL library |
| `external/webrtc` | Real-time communication |

> **Example:** When an app uses a SQLite database — `App → android.database.sqlite → external/sqlite/`. The actual database engine is the open source SQLite code living in `external/`.

</details>

## 4. Partitions & Treble

---

**Q15. Explain Android's partition structure.**

<details>
<summary>Answer</summary>

| Partition | Image | Size | Contents |
|---|---|---|---|
| `/boot` | `boot.img` | ~100 MB | Linux kernel + `init` + ramdisk |
| `/system` | `system.img` | 2–4 GB | Android OS, framework, apps, libraries |
| `/vendor` | `vendor.img` | 500 MB–1 GB | Hardware drivers, HAL implementations, firmware |
| `/product` | `product.img` | Variable | OEM-specific apps (e.g. Google apps on Pixel) |
| `/recovery` | `recovery.img` | ~100 MB | Recovery mode OS |
| `/data` | `userdata.img` | Remaining space | User apps, user data — wiped on factory reset |
| `/cache` | `cache.img` | ~100 MB | Temporary cache |

**Key:** `/data` is the only partition **not** built from AOSP source — it is created empty and filled by the user.

</details>

---

**Q16. What is Project Treble and how does it relate to partitions?**

<details>
<summary>Answer</summary>

Project Treble (Android 8.0, 2017) **separated the vendor partition from the system partition** to make Android updates faster and easier.

**Before Treble:** `/system` contained both Android OS code and vendor/hardware code mixed together. Updating the OS required retesting all vendor code — causing 12–18 month delays (or no update at all).

**After Treble:**

```
/system  → ONLY Android OS code    (updated by Google)
/vendor  → ONLY vendor/HAL code    (updated by chip vendor)
           ↑
           Clear stable interface between them (HIDL/AIDL)
```

**Result:** Google can update `/system` without touching `/vendor`. The device still works because both sides honor a stable interface contract.

The interface between `/system` and `/vendor` is defined in `hardware/interfaces/` using HIDL/AIDL files.

> **Interview gold:** "Treble introduced the concept of a stable vendor interface (VINTF), so the Android framework can be updated independently of vendor HALs. This is why Pixel phones get updates faster than other Android phones."

</details>

---

**Q17. What AOSP source directories map to which device partitions?**

<details>
<summary>Answer</summary>

```
AOSP Source          →   Image        →   Partition
──────────────────────────────────────────────────────
kernel/              →   boot.img     →   /boot
system/core/init/    →   boot.img     →   /boot

frameworks/          →   system.img   →   /system
packages/apps/       →   system.img   →   /system
system/core/         →   system.img   →   /system
art/                 →   system.img   →   /system
bionic/              →   system.img   →   /system
external/            →   system.img   →   /system

hardware/interfaces/ →   vendor.img   →   /vendor
device/[name]/       →   vendor.img   →   /vendor

packages/ (OEM)      →   product.img  →   /product

(empty — user fills) →   userdata.img →   /data
```

Specific examples:
- `frameworks/base/` → `/system/framework/framework.jar`
- `packages/apps/Settings/` → `/system/priv-app/Settings/Settings.apk`
- `bionic/` → `/system/lib64/libc.so`
- `art/` → `/system/lib64/libart.so`
- `hardware/interfaces/camera/` → `/vendor/lib64/hw/camera.*.so`

</details>

## 5. Manifest & Repo

---

**Q19. What is `manifest.xml` and what are its key elements?**

<details>
<summary>Answer</summary>

`manifest.xml` is the **master list** of all git repositories that make up AOSP. It tells `repo` what to download, from where, at which version, and where to put it locally.

**Key elements:**

**1. `<remote>` — defines a server:**
```xml
<remote name="aosp"
        fetch="https://android.googlesource.com"
        review="https://android-review.googlesource.com" />
```

**2. `<default>` — default settings for all projects:**
```xml
<default revision="refs/tags/android-14.0.0_r1"
         remote="aosp"
         sync-j="4"
         sync-c="true" />
```

**3. `<project>` — one repository to download:**
```xml
<project path="frameworks/base"
         name="platform/frameworks/base" />
<!-- Full URL = remote.fetch + name -->
<!-- = https://android.googlesource.com/platform/frameworks/base -->
```

**4. `<copyfile>` — copy a file after sync:**
```xml
<copyfile src="core/root.mk" dest="Makefile" />
```

**5. `<remove-project>` — exclude a project:**
```xml
<remove-project name="platform/packages/apps/Browser2" />
```

**6. `<include>` — merge another manifest:**
```xml
<include name="default.xml" />
```

> "manifest.xml acts like a shopping list. `repo sync` reads this list and downloads each item (git repository) from its URL into the specified local folder at the specified version."

</details>

---

**Q20. What is a local manifest and when would you use it?**

<details>
<summary>Answer</summary>

A **local manifest** lets you add, remove, or replace projects **without modifying the main manifest**. It lives at `.repo/local_manifests/local.xml`.

**When to use it:**
- Adding a device tree not in AOSP (e.g., building for Xiaomi)
- Replacing a stock AOSP app with your own fork
- Removing projects you don't need (save disk space / build time)
- Adding vendor-specific proprietary blobs

```xml
<?xml version="1.0" encoding="UTF-8"?>
<manifest>

  <!-- ADD project from GitHub -->
  <remote name="github" fetch="https://github.com" />
  <project name="MyCompany/CustomCamera"
           path="packages/apps/CustomCamera"
           remote="github" revision="main" />

  <!-- REMOVE unwanted project -->
  <remove-project name="platform/packages/apps/Browser2" />

  <!-- REPLACE with your fork -->
  <remove-project name="platform/packages/apps/Settings" />
  <project name="MyCompany/MySettings"
           path="packages/apps/Settings"
           remote="github" revision="android-14" />

</manifest>
```

Changes in `.repo/local_manifests/` are automatically picked up by `repo sync`.

</details>

---

**Q21. What is `clone-depth="1"` in a manifest project entry?**

<details>
<summary>Answer</summary>

`clone-depth="1"` tells `repo` to only download the **latest commit**, not the full git history of that repository.

```xml
<project path="build/soong"
         name="platform/build/soong"
         clone-depth="1" />
```

**Benefits:**
- Significantly less disk space used
- Much faster sync time

**Trade-off:** You lose the git history for that repo (can't `git log` deep history, can't `git bisect`).

Commonly used for large repositories like the build system itself, where full history isn't needed for day-to-day development.

</details>

---

**Q22. How does `repo sync` use the manifest to download code? Trace through one project.**

<details>
<summary>Answer</summary>

Given this manifest entry:
```xml
<remote name="aosp" fetch="https://android.googlesource.com"/>
<project name="platform/frameworks/base"
         path="frameworks/base"
         revision="refs/tags/android-14.0.0_r1"/>
```

Repo does:
1. Constructs full URL: `remote.fetch` + `name` = `https://android.googlesource.com/platform/frameworks/base`
2. Runs: `git clone [URL] → .repo/projects/platform/frameworks/base.git`
3. Checks out: `git checkout refs/tags/android-14.0.0_r1`
4. Places files in: `frameworks/base/`
5. After all projects done: runs `<copyfile>` and `<linkfile>` operations

This process repeats for all 800+ `<project>` entries in `manifest.xml`.

</details>

## 6. Branch Interpretation

---

**Q23. How do you decode an AOSP branch name?**

<details>
<summary>Answer</summary>

```
android  -  14  .  0  .  0  _  r  1
   ↑         ↑     ↑     ↑     ↑  ↑
   │         │     │     │     │  └── Release number (higher = more fixes)
   │         │     │     │     └───── 'r' = release
   │         │     │     └─────────── Patch version
   │         │     └───────────────── Minor version
   │         └─────────────────────── Android version number (14 = Android 14)
   └───────────────────────────────── Always "android"
```

| Branch | Meaning |
|---|---|
| `android-14.0.0_r1` | Android 14, first release |
| `android-14.0.0_r25` | Android 14, 25th update (more bugs fixed) |
| `android-13.0.0_r83` | Android 13, very stable (83 updates) |
| `android-12.1.0_r1` | Android 12L (tablet-focused update) |
| `main` | Latest development — **UNSTABLE**, don't use for production |
| `android-security-14.0.0_r1` | Security patches only, no new features |

**Higher release number = more stable.** For production use, prefer a high `r` number. Never use `main` for production.

</details>

---

**Q24. What is the difference between `refs/tags/` and `refs/heads/` in a manifest revision?**

<details>
<summary>Answer</summary>

| | `refs/tags/android-14.0.0_r1` | `refs/heads/main` |
|---|---|---|
| Type | Tag (fixed point) | Branch (moving pointer) |
| Changes? | **Never** — immutable snapshot | **Daily** — gets new commits |
| Stability | Stable, reproducible builds | Unstable, may break |
| Use for | Production, releases | Active Google development |

```xml
<!-- RECOMMENDED — stable, never changes -->
<default revision="refs/tags/android-14.0.0_r1" />

<!-- UNSTABLE — changes daily -->
<default revision="refs/heads/main" />

<!-- Specific commit hash — most precise lock -->
<project name="platform/frameworks/base"
         revision="a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2" />
```

> **Analogy:** Tag = "use exactly page 42 of this book, always." Branch = "use the latest page of this book (keeps changing)."

</details>

---

**Q25. What is a kernel branch name and how does it differ from an AOSP branch?**

<details>
<summary>Answer</summary>

Kernel branches use a **different format** from AOSP branches:

```
android-msm-redbull-4.19-android12
   ↑       ↑      ↑    ↑     ↑
   │       │      │    │     └── Android version it targets
   │       │      │    └──────── Linux kernel version
   │       │      └───────────── Device codename
   │       └──────────────────── Chipset platform (msm = Qualcomm MSM)
   └──────────────────────────── Always "android"
```

- `msm` = Qualcomm MSM chipset family
- `redbull` = device codename (OnePlus 9R / Pixel 5a)
- `4.19` = Linux kernel version
- `android12` = the Android release it supports

Kernel branches can be used in a manifest to override the default revision for the kernel project specifically, since kernels are versioned separately from the rest of AOSP.

</details>

## 7. System Internals

---

**Q26. Explain the Android boot process step by step.**

<details>
<summary>Answer</summary>

```
1. Power On
   → CPU starts executing from ROM (hardcoded bootrom)

2. Bootloader
   → Bootrom loads bootloader from /boot
   → Checks: locked or unlocked?
   → Loads kernel + ramdisk

3. Linux Kernel
   → Initializes CPU, RAM, drivers
   → Mounts root filesystem
   → Starts init (PID 1)

4. init Process (PID 1)
   → Lives in: system/core/init/
   → Reads /init.rc scripts
   → Starts system daemons: adbd, vold, netd, logd

5. Zygote
   → init starts Zygote
   → Pre-loads Android framework classes
   → Pre-loads common Java libraries
   → Waits for app launch requests

6. System Server
   → Zygote forks System Server
   → Starts 80+ system services:
      ActivityManagerService, WindowManagerService,
      PackageManagerService, PowerManagerService...

7. Launcher (Home Screen)
   → ActivityManagerService sends HOME Intent
   → Launcher3 starts
   → Boot complete! 🏠
```

</details>

---

**Q27. What is Zygote? Why is it important?**

<details>
<summary>Answer</summary>

Zygote is the **parent process of all Android apps** — a pre-initialized Java Virtual Machine started by `init` before any app runs.

**Why it exists — the problem:**
Starting a new JVM for every app takes ~600ms (loading Java runtime + Android classes + common libraries). Every app launch would be painfully slow.

**How Zygote solves it:**
1. At boot, Zygote pre-loads all Android framework classes and common libraries (warming up the JVM)
2. Then waits...
3. When you tap an app icon: `ActivityManagerService` tells Zygote to `fork()`
4. `fork()` creates an **exact copy** of Zygote's already-warm process
5. The new copy becomes your app — JVM already ready → starts in ~100ms

**Technical details:**
- Zygote socket: `/dev/socket/zygote`
- Source: `frameworks/base/core/java/com/android/internal/os/ZygoteInit.java`

> **Analogy:** Zygote = cookie cutter. Each app = a cookie made from the same cutter. Making each cookie from scratch is slow; using a template is fast.

</details>

---

**Q28. What is ART? How is it different from Dalvik?**

<details>
<summary>Answer</summary>

| | Dalvik (before Android 5.0) | ART (Android 5.0+) |
|---|---|---|
| Compilation | **JIT** (Just In Time — compiles while running) | **AOT** (Ahead Of Time — compiles at install time) |
| App startup | Slow (compiling at runtime) | Fast (already compiled) |
| Performance | Worse | Better |
| Install time | Fast | Slower |
| Storage | Less | More (stores both `.dex` and `.oat`) |
| Battery | Higher drain | Lower drain |

**Android 7+ (Hybrid):** Mixed AOT + JIT + profile-guided compilation.
- First run: JIT (fast install)
- Background: profiles which code is "hot" (used often)
- Idle time: AOT compiles only the hot code
- Next run: hot code runs as native — fast!

**Location in AOSP:** `art/runtime/`, `art/dex2oat/`, `art/runtime/gc/`

</details>

## 8. HAL, HIDL & AIDL

---

**Q29. What is a HAL and why is it needed?**

<details>
<summary>Answer</summary>

**HAL = Hardware Abstraction Layer** — a translator between Android Framework (high-level) and hardware (low-level).

**Why needed:** Samsung's camera chip ≠ Google's camera chip ≠ Qualcomm's camera chip. Without HAL, the Android framework would need to know about every possible hardware chip in the world. Impossible to maintain.

**With HAL:**
```
Camera App
    ↓ calls takePicture()
Camera2 Framework API
    ↓ calls HAL interface
Camera HAL (hardware/interfaces/camera/)
    ↓ vendor implements this for their hardware
Actual camera sensor
    ↓
Photo captured!
```

The framework calls the standard HAL interface — it doesn't care about Samsung's chip details.

**HAL types (evolution):**

| Type | Era | Mechanism |
|---|---|---|
| Legacy HAL | Before Android 8 | Direct `.so` files, loaded via `dlopen()` |
| HIDL HAL | Android 8–13 | `.hal` files, separate process, hwbinder |
| AIDL HAL | Android 11+ | `.aidl` files, separate process, binder |

**Location:** Interface definitions in `hardware/interfaces/`. Implementations in `/vendor/lib64/hw/*.so`.

</details>

---

**Q30. What is HIDL? What problem does it solve?**

<details>
<summary>Answer</summary>

**HIDL = HAL Interface Definition Language** — introduced in Android 8.0 to define a stable, versioned interface between the Android framework and HAL implementations.

**Problem it solves:** Before HIDL, HALs were loaded directly into the framework process. A HAL crash crashed `system_server`. Also, there was no stable interface — updating Android broke vendor HAL code, requiring months of re-integration.

**With HIDL:**
- HAL runs in its **own separate process** (daemon)
- Communicates via **hwbinder** (`/dev/hwbinder`)
- Interface defined in `.hal` files (versioned: `@1.0`, `@1.1`, `@2.0`)
- If HAL crashes → only HAL process dies, framework keeps running

```hidl
interface IVibrator {
    on(uint32_t timeoutMs) generates (Status status);
    off() generates (Status status);
};
```

HIDL is being replaced by AIDL (Android 11+) and is deprecated as of Android 14.

</details>

---

**Q31. What is the difference between HIDL and AIDL for HAL interfaces?**

<details>
<summary>Answer</summary>

| | HIDL | AIDL (for HALs) |
|---|---|---|
| Introduced | Android 8.0 | Android 11+ for HALs |
| File type | `.hal` | `.aidl` |
| Transport | hwbinder (`/dev/hwbinder`) | binder/vndbinder |
| Code gen tool | `hidl-gen` | `aidl-cpp` / `aidl-java` |
| Return values | `generates()` callback pattern | Direct return values |
| Versioning | Package-level (`@1.0`, `@1.1`) | `@VintfStability` + integer versions |
| Error handling | Status enum return values | `ScopedAStatus` / exceptions |
| Status | Deprecated (Android 14) | Preferred for all new HALs |

**Key AIDL advantage:** `@VintfStability` ensures the interface is stable across system/vendor boundary — framework can be updated without breaking vendor HAL code.

```aidl
@VintfStability
interface IVibrator {
    void on(in int timeoutMs);
    void off();
}
```

</details>

## 9. SELinux & Security

---

**Q32. What is SELinux in Android and why does it matter?**

<details>
<summary>Answer</summary>

**SELinux = Security Enhanced Linux** — a **Mandatory Access Control (MAC)** system that enforces strict rules on what every process can do, even if it has root access.

**Regular Linux (without SELinux):** "You own this file, you can do anything with it" (Discretionary Access Control).

**With SELinux:** "Even if you own the file, you can only do what the policy explicitly allows."

**Why Android needs it:**
- Without SELinux: a hacked app that gains root access can read ALL files, access camera, contacts, SMS — complete compromise.
- With SELinux: even root is limited to what the policy permits. The attack surface is dramatically reduced.

**How it works:**
- Every **process** has a label (e.g., `u:r:system_app:s0`)
- Every **file** has a label (e.g., `u:object_r:system_data_file:s0`)
- **Policy** defines what each label can do to what

**Modes:**

| Mode | Behavior | Used When |
|---|---|---|
| Enforcing | Violations blocked + logged | Production |
| Permissive | Violations logged only | Debugging |
| Disabled | No SELinux | Not recommended |

**Location in AOSP:** `system/sepolicy/` (core policies), `device/[name]/sepolicy/` (device-specific)

</details>

---

**Q33. How do you debug a SELinux violation?**

<details>
<summary>Answer</summary>

SELinux violations appear as `avc: denied` messages in the kernel log.

```bash
# Check for denials:
adb shell dmesg | grep "avc: denied"
adb logcat | grep "avc: denied"

# Example denial:
# avc: denied { write } for
#   path="/sys/class/leds/red/brightness"
#   scontext=u:r:hal_led_default:s0
#   tcontext=u:object_r:sysfs_leds:s0
#   tclass=file

# Fix — add rule to .te file:
allow hal_led_default sysfs_leds:file { write };
```

**Key SELinux file types:**

| File | Purpose |
|---|---|
| `*.te` | Type Enforcement rules (allow/deny) |
| `file_contexts` | Labels assigned to files |
| `property_contexts` | Labels for system properties |
| `service_contexts` | Labels for binder services |
| `hwservice_contexts` | Labels for hwbinder HAL services |

**Common interview scenario:** "App crashes with 'Permission denied' even with root?" → Check for `avc: denied` — it's almost always SELinux.

</details>

## 10. Binder IPC

---

**Q34. What is Binder IPC? Why does Android use it instead of sockets or pipes?**

<details>
<summary>Answer</summary>

**Binder** is Android's primary **Inter-Process Communication (IPC)** mechanism — how separate processes talk to each other.

**The problem:** Android apps run in isolated processes with separate memory. An app process cannot directly access system services' memory. They need a safe, fast way to communicate.

**How Binder works:**
```
Process A (Client)              Process B (Server)
      │                               │
      │── serializes args ──→  /dev/binder (kernel) ──→ │
      │                                                   │── deserializes
      │                                                   │── executes method
      │                                                   │── serializes result
      │◄── receives result ── /dev/binder (kernel) ←── │
```

**Why Binder over sockets/pipes:**

| Feature | Binder | Sockets/Pipes |
|---|---|---|
| Caller identity | ✅ Kernel verifies (cannot be forged) | ❌ Can be spoofed |
| Performance | ✅ Single copy via kernel memory mapping | ❌ Multiple copies |
| Death notification | ✅ Automatic | ❌ Manual |
| Reference counting | ✅ Built-in | ❌ Manual |
| Thread management | ✅ Built-in thread pool | ❌ Manual |

**Three binder domains in Android:**

| Device | Used by |
|---|---|
| `/dev/binder` | Apps ↔ system_server |
| `/dev/hwbinder` | Framework ↔ HIDL HAL |
| `/dev/vndbinder` | Vendor process ↔ vendor process |

**Location in AOSP:** `frameworks/native/libs/binder/` (C++), `frameworks/base/core/java/android/os/` (Java), kernel driver at `drivers/android/binder.c`

</details>

---

**Q35. What is AIDL and how does it relate to Binder?**

<details>
<summary>Answer</summary>

**AIDL = Android Interface Definition Language** — defines the interface for Binder IPC calls between processes. The AIDL compiler auto-generates all the boilerplate serialization/deserialization code.

```aidl
// ILocationManager.aidl
interface ILocationManager {
    Location getLastKnownLocation(String provider);
    void requestLocationUpdates(LocationRequest req);
}
```

AIDL compiler generates:
- `ILocationManager.java` — the interface
- `ILocationManager.Stub` — server side (service implements this)
- `ILocationManager.Stub.Proxy` — client side (app uses this automatically)

**Usage from an app:**
```java
LocationManager lm = getSystemService(LOCATION_SERVICE);
lm.getLastKnownLocation("gps");
// ↑ This is secretly a Binder IPC call to LocationManagerService
//   AIDL hides all the serialization complexity
```

> **Analogy:** AIDL = contract between two parties. "I promise to provide these functions." "I promise to call them this way." Both sides can evolve independently as long as they honor the contract.

</details>

## 11. Practical & Debugging

---

**Q36. How would you add a new built-in app to AOSP?**

<details>
<summary>Answer</summary>

```bash
# Step 1: Create the app directory
mkdir -p packages/apps/MyApp
cd packages/apps/MyApp
```

**Step 2: Create `Android.bp`:**
```bp
android_app {
    name: "MyApp",
    srcs: ["src/**/*.java"],
    resource_dirs: ["res"],
    manifest: "AndroidManifest.xml",
    platform_apis: true,
    certificate: "platform",   // sign with platform key
    privileged: true,          // goes to /system/priv-app
}
```

**Step 3: Create `AndroidManifest.xml`** with package name, activities, etc.

**Step 4: Add to product makefile:**
```makefile
# device/[manufacturer]/[device]/device.mk
PRODUCT_PACKAGES += MyApp
```

**Step 5: Build and verify:**
```bash
m MyApp
ls out/target/product/[device]/system/priv-app/MyApp/
```

**Key points:**
- `certificate: "platform"` → signed with platform key (more permissions)
- `privileged: true` → goes to `/system/priv-app` (privileged permissions)
- Without `privileged`, app goes to `/system/app` (regular permissions)

</details>

---

**Q37. How do you debug a system service crash in AOSP?**

<details>
<summary>Answer</summary>

**Step 1: Check logcat for errors**
```bash
adb logcat -b all | grep -E "crash|fatal|exception|FATAL"
adb logcat *:E    # errors only
```

**Step 2: Check tombstone files** (native crash dumps)
```bash
adb shell ls /data/tombstones/
adb pull /data/tombstones/tombstone_00
# Contains: stack trace, register values, memory maps
```

**Step 3: Check Dropbox** (Java crash logs, ANRs)
```bash
adb shell dumpsys dropbox --print
```

**Step 4: Full bugreport**
```bash
adb bugreport ./bugreport.zip
# Contains everything: all logs, system state, app states
```

**Step 5: Enable verbose logging**
```bash
adb shell setprop log.tag.MyService VERBOSE
adb logcat MyService:V *:S
```

**Step 6: For native crashes — decode addresses**
```bash
arm64-linux-androideabi-addr2line -e symbols/system/lib64/libXYZ.so 0x12345
```

**Common crash causes:** NullPointerException in service, Binder transaction failure, `DeadObjectException`, SELinux violation, `OutOfMemoryError`.

</details>

---

**Q38. How do you check if a HAL service is registered and running?**

<details>
<summary>Answer</summary>

```bash
# Check if the HAL process is running:
adb shell ps -A | grep "android.hardware"

# For AIDL HALs — check servicemanager:
adb shell service list | grep android.hardware

# For HIDL HALs — check hwservicemanager:
adb shell lshal
adb shell lshal | grep vibrator     # filter specific

# Check VINTF compatibility:
adb shell vintf --check-compat

# Check the VINTF manifest:
adb shell cat /vendor/etc/vintf/manifest.xml

# Check for SELinux denials:
adb shell dmesg | grep "avc: denied"

# Verify binary exists:
adb shell ls -la /vendor/bin/hw/ | grep android.hardware

# Call debug() on a specific HIDL HAL:
adb shell lshal debug android.hardware.vibrator@1.0::IVibrator/default
```

**Common reasons a HAL isn't found:**
- SELinux policy missing
- `.rc` file not included in build
- `manifest.xml` version mismatch
- Registration failed in `main()` — check logcat

</details>

**Q39. Explain the incremental build workflow — what happens when you change one file?**

<details>
<summary>Answer</summary>

After changing source code, you **don't need a full rebuild**. The build system tracks dependencies and only recompiles what changed.

```bash
# Changed a file in Settings app:
cd packages/apps/Settings
mm -j$(nproc)          # builds only Settings (~5–10 min)

# Changed a framework class in frameworks/base:
mmm frameworks/base -j$(nproc)   # builds only framework

# Changed frameworks/base AND Settings:
m framework Settings   # builds both
```

**Build time comparison:**
- First full build: 1–6 hours
- Incremental (one module): 5–30 minutes
- Incremental with ccache: 2–5× faster

**Ninja's role:** Ninja tracks which output files depend on which input files. When you change `Button.java`, Ninja knows to recompile only the `.java` files that transitively depend on it — not all 40,000 files.

</details>
