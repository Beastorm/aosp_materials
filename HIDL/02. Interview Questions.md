## 1. Basic / Conceptual

---

**Q1. What is a HAL and why does Android need it?**

<details>
<summary>Answer</summary>

HAL = Hardware Abstraction Layer. It is a standard interface layer between the Android framework and hardware-specific implementations.

**Why Android needs it:**

```
Problem without HAL:

Framework code would need to know about EVERY
specific hardware chip from EVERY manufacturer

Samsung phone  → Exynos camera driver
Pixel phone    → custom ISP driver
OnePlus phone  → Qualcomm camera driver

Impossible to maintain!
```

**Solution:**

```
┌──────────────┐
│  Framework   │  → Only knows ICamera interface
│              │     (defined by HAL)
├──────────────┤
│  HAL         │  → Standard contract/interface
├──────────────┤
│  Vendor impl │  → Samsung implements for Exynos
│              │     Qualcomm implements for Snapdragon
└──────────────┘
```

**Benefits:**

1. Framework doesn't change for different hardware
2. Vendors implement once, works with any Android version
3. OTA updates don't break vendor code (with Treble)
4. Clear separation of responsibility

</details>

---

**Q2. What is HIDL and why was it introduced in AOSP?**

<details>
<summary>Answer</summary>

HIDL (Hardware Interface Definition Language) is an interface description language introduced in Android 8.0 (Treble) to define the interface between the Android framework and HAL implementations.

It was introduced to:
- **Decouple** the Android framework from vendor HAL implementations
- Allow the **framework to be updated independently** of vendor code (Project Treble)
- Enforce **stable, versioned interfaces** between framework and hardware
- Enable **IPC via Binder** (hwbinder) between framework and HAL processes

Before HIDL, HALs were loaded in-process as shared libraries. With HIDL, HALs run in a **separate process**, communicating over Binder.

</details>

---

**Q3. What is Project Treble and how does it relate to HAL?**

<details>
<summary>Answer</summary>

Project Treble (Android 8.0) fundamentally changed HAL architecture.

**Before Treble:**

```
┌────────────────────────────────────┐
│         Android OS Update          │
│                                    │
│  Framework + Vendor Code           │
│  (tightly coupled)                 │
│                                    │
│  To update Android:                │
│  1. Google releases update         │
│  2. Qualcomm/MediaTek must update  │
│  3. Samsung/OnePlus must update    │
│  4. Carrier must approve           │
│  RESULT: 12-18 month delay!        │
└────────────────────────────────────┘
```

**After Treble:**

```
┌─────────────────┐  ┌─────────────────┐
│  /system        │  │  /vendor        │
│  partition      │  │  partition      │
│                 │  │                 │
│  Android OS     │  │  Vendor HALs    │
│  Framework      │  │  Drivers        │
│                 │  │  Firmware       │
│  Updated by     │  │  Updated by     │
│  Google         │  │  Qualcomm etc   │
└────────┬────────┘  └────────┬────────┘
         │                    │
         └──── Stable HIDL ───┘
               Interface
               (contract)
```

> The stable interface means Google can update `/system` without breaking `/vendor` code!

</details>

**Q4. What is the difference between Legacy HAL, HIDL HAL, and AIDL HAL?**

<details>
<summary>Answer</summary>

**Legacy HAL (Before Android 8.0):**
- Just a shared library (`.so` file)
- Loaded via `dlopen()` into framework process
- Same process as caller — no IPC, direct function calls
- No process isolation
- Crash in HAL = crash in `system_server`

```c
struct hw_module_t {
    const char *id;                      // e.g., "camera"
    struct hw_module_methods_t *methods;
};
// Vendor implements this struct
```

**HIDL HAL (Android 8.0 – 13):**
- Interface defined in `.hal` files
- Generates C++ boilerplate (proxies, stubs)
- Runs as separate process (daemon)
- Communicates via `hwbinder` (`/dev/hwbinder`)
- Process isolation — HAL crash doesn't kill framework
- Supports versioning (`@1.0`, `@2.0`, etc.)

```hidl
interface IVibrator {
    on(uint32_t timeoutMs) generates (Status status);
};
```

**AIDL HAL (Android 11+, mandatory from Android 13):**
- Interface defined in `.aidl` files
- Same AIDL as used for app development
- Runs as separate process
- Communicates via `binder`/`vndbinder`
- `@VintfStability` ensures cross-version stability
- Cleaner syntax, better tooling

```aidl
@VintfStability
interface IVibrator {
    void on(in int timeoutMs);
};
```

**Comparison:**

```
Feature        Legacy    HIDL          AIDL
─────────────────────────────────────────────
File type      .c/.cpp   .hal          .aidl
Separate proc  No        Yes           Yes
IPC            No        hwbinder      binder
Versioning     Manual    @major.minor  integer
Status         Gone      Deprecated    Active
```

</details>

## 2. Architecture

---

**Q5. What is the difference between a passthrough HAL and a binderized HAL?**

<details>
<summary>Answer</summary>

**Binderized HAL:**

```
┌──────────────────┐    IPC     ┌──────────────────┐
│  system_server   │◄──────────►│  HAL Process     │
│  (framework)     │ hwbinder   │  (daemon)        │
└──────────────────┘            └──────────────────┘
```

Characteristics:
- HAL runs in completely separate process
- All communication via IPC (binder calls)
- Full process isolation — crash doesn't affect framework
- Slight performance overhead (IPC cost)
- Preferred for all modern HALs

---

**Passthrough HAL:**

```
┌──────────────────────────────────┐
│  Calling Process                 │
│  ┌─────────────┐ dlopen()        │
│  │  Framework  │────────────────►│
│  └─────────────┘ ┌─────────────┐ │
│                  │ HAL .so lib │ │
│                  └─────────────┘ │
└──────────────────────────────────┘
```

Characteristics:
- HAL loaded as shared library — no IPC, direct function calls
- Much faster (no IPC overhead)
- No process isolation
- Used for backward compatibility / migrating legacy HALs

---

In `manifest.xml`, a binderized HAL has `<transport>hwbinder</transport>`, while passthrough has `<transport>passthrough</transport>`.

In passthrough mode, `BsCamera` (the `Bs*` glue file) wraps your implementation and is loaded directly into the client process.

```cpp
// Binderized (contacts hwservicemanager):
sp<IVibrator> v = IVibrator::getService("default");

// Passthrough (loads .so directly via dlopen):
sp<IVibrator> v = IVibrator::getService("default", true);
```

**Same-Process HAL (SP-HAL) — Special Case:**

Must always be passthrough:
- `android.hardware.graphics.mapper`
- EGL / GLES / Vulkan drivers
- RenderScript

Reason: GPU drivers cannot work across process boundaries.

---

**Comparison table:**

| | Passthrough HAL | Binderized HAL |
|---|---|---|
| **Process** | Same process as client | Separate process |
| **IPC** | Direct function call | Binder (hwbinder) |
| **Transport** | `passthrough` | `hwbinder` |
| **Performance** | Faster (no IPC overhead) | Slower (IPC overhead) |
| **Isolation** | None | Full process isolation |
| **Used for** | Legacy/migration path | New HALs (Treble) |

</details>

**Q6. What is hwbinder? How is it different from regular binder?**

<details>
<summary>Answer</summary>

Android has **three** binder domains:

```
/dev/binder    → Apps ↔ system_server
                 Regular Android IPC

/dev/hwbinder  → Framework ↔ HAL (HIDL)
                 Hardware binder
                 Separate domain for HAL communication

/dev/vndbinder → Vendor ↔ Vendor
                 Vendor processes talking to each other
                 Introduced in Android 8.0
```

Both `/dev/binder` and `/dev/hwbinder` run the same kernel driver code — they are just three separate instances with different contexts.

**Why a separate hwbinder?**

| Reason | Detail |
|---|---|
| **Priority** | hwbinder can inherit real-time priorities — important for audio, camera timing |
| **Isolation** | HAL bugs can't corrupt framework binder state |
| **Security** | Different SELinux rules for each domain |
| **Quota** | Separate thread pool — HAL calls don't starve app IPC calls |

| | `/dev/binder` | `/dev/hwbinder` |
|---|---|---|
| **Used by** | Android framework, apps | HAL ↔ framework |
| **Threading** | Default thread pool | Dedicated thread pool |
| **Priority inheritance** | Standard | Real-time capable |
| **Memory** | Standard | Optimized for HAL data |

```bash
# Check binder domains on device:
adb shell ls -la /dev/*binder
# crw-rw-rw- /dev/binder
# crw-rw-rw- /dev/hwbinder
# crw-rw-rw- /dev/vndbinder
```

</details>

**Q7. What is HwServiceManager? How is it different from ServiceManager?**

<details>
<summary>Answer</summary>

`hwservicemanager` is like a **"directory service"** for HIDL HALs — similar to `servicemanager` for regular Android services.

```
Regular Android:
App → servicemanager → finds system_server services

HIDL HAL:
Framework → hwservicemanager → finds HAL services
```

**How it works:**

```
┌─────────────────┐
│  HAL starts up  │
│                 │
│  registers with │──────────────►┌────────────────────┐
│  hwservicemanager               │  hwservicemanager  │
└─────────────────┘               │                    │
                                  │  Registry:         │
┌─────────────────┐               │  vibrator@1.0 →    │
│  Framework      │               │    PID 1234        │
│  wants vibrator │──getService()─►  camera@3.4 →      │
│  HAL            │               │    PID 5678        │
│                 │◄──Binder ref──│  audio@6.0 →       │
└─────────────────┘               │    PID 9012        │
                                  └────────────────────┘
```

When your `service.cpp` calls `cam->registerAsService("default")`, it registers with `HwServiceManager`. When the framework calls `ICamera::getService("default")`, it queries `HwServiceManager` to get the `BpHwCamera` proxy.

| | `ServiceManager` | `HwServiceManager` |
|---|---|---|
| **Manages** | Android services (AMS, WMS) | HIDL HAL services |
| **IPC channel** | `/dev/binder` | `/dev/hwbinder` |
| **Registration** | `addService()` | `registerAsService()` |

```bash
# Check registered HIDL services:
adb shell lshal

# Output:
# android.hardware.vibrator@1.0::IVibrator/default
# android.hardware.camera.provider@2.4::ICameraProvider/legacy/0
# android.hardware.audio@6.0::IDevicesFactory/default
```

</details>

**Q8. What is VINTF and why is it important?**

<details>
<summary>Answer</summary>

VINTF (Vendor Interface) is the compatibility matrix system in AOSP that ensures the framework and vendor HALs are **compatible** with each other.

`manifest.xml` declares **what HAL interfaces the device provides**. The framework has a `compatibility_matrix.xml` that declares **what HAL interfaces it requires**.

```
┌─────────────────────────────────────────────────────┐
│  Device Manifest           Framework Compat Matrix  │
│  /vendor/etc/vintf/        /system/etc/vintf/       │
│  manifest.xml              compatibility_matrix.xml  │
│                                                     │
│  "What vendor             "What framework           │
│   provides"                requires"                │
│                                                     │
│  <hal>vibrator@1.0</hal>  <hal>vibrator@1.0-3</hal>│
│                                                     │
│              VINTF checks: Compatible? ✓            │
└─────────────────────────────────────────────────────┘
```

**manifest.xml (vendor side):**

```xml
<manifest version="1.0" type="device">
    <hal format="aidl">
        <name>android.hardware.vibrator</name>
        <version>1</version>
        <interface>
            <name>IVibrator</name>
            <instance>default</instance>
        </interface>
    </hal>
</manifest>
```

**compatibility_matrix.xml (framework side):**

```xml
<compatibility-matrix version="1.0" type="framework">
    <hal format="aidl" optional="false">
        <name>android.hardware.vibrator</name>
        <version>1-2</version>
    </hal>
</compatibility-matrix>
```

**Why important:**

1. **Prevents boot** if incompatible — device won't boot if a required HAL is missing
2. **OTA safety** — verifies update is compatible before applying
3. **Self-documenting** — explicitly declares what HALs a device supports

Without this entry, even if your HAL service is running, the framework won't find it.

```bash
# Check compatibility:
adb shell vintf --check-compat
# COMPATIBLE   ← good
# INCOMPATIBLE ← device won't boot!

# List device manifest:
adb shell cat /vendor/etc/vintf/manifest.xml

# Check what's running:
adb shell lshal --neat
```

</details>

**Q9. What happens during device boot with respect to HALs?**

<details>
<summary>Answer</summary>

```
1. Bootloader loads kernel
         ↓
2. Kernel starts init (PID 1)
         ↓
3. init reads /init.rc and /vendor/etc/init/*.rc
         ↓
4. init starts servicemanager, hwservicemanager
         ↓
5. init starts HAL daemons (class "hal"):

   for each .rc file in /vendor/etc/init/:
       service vendor.vibrator-hal
           /vendor/bin/hw/android.hardware.vibrator-service
       class hal   ← this class starts early
         ↓
6. Each HAL process starts:

   main() {
       auto hal = ndk::SharedRefBase::make<Vibrator>();

       AServiceManager_addService(hal->asBinder().get(),
           "android.hardware.vibrator.IVibrator/default");

       ABinderProcess_joinThreadPool();
   }
         ↓
7. VINTF check happens:
   - Does manifest match what's actually registered?
   - Are all required HALs present?
   - If not → device may fail to boot
         ↓
8. system_server starts
   - Gets HAL services via servicemanager
   - Framework is now ready
         ↓
9. Device boots to home screen
```

```bash
# See HAL startup in boot logs:
adb logcat -b all | grep "hal"
# I android.hardware.vibrator-service: Vibrator HAL starting
# I android.hardware.camera-provider: Camera HAL ready
```

</details>

## 3. Glue vs Scaffold

---

**Q10. What are glue files in HIDL? Name them and explain each.**

<details>
<summary>Answer</summary>

Glue files are auto-generated C++ files that handle Binder IPC plumbing. For an interface `ICamera`:

| File | Role |
|---|---|
| `ICamera.h` | Pure abstract C++ interface with all methods as pure virtual |
| `BnHwCamera.h` | Binder Native — server-side stub, deserializes Binder parcel and dispatches to your implementation |
| `BpHwCamera.h` | Binder Proxy — client-side proxy, serializes args into Binder parcel and sends over hwbinder |
| `BsCamera.h` | Binder Passthrough adapter — wraps implementation for same-process passthrough mode |
| `ICamera.cpp` | Implements the IPC transaction logic |

You **never edit** these. They are regenerated from `.hal` on every build.

</details>

---

**Q11. What are scaffold files? Why does hidl-gen generate them?**

<details>
<summary>Answer</summary>

Scaffold files are the **starting template** for your HAL implementation. hidl-gen generates them once with `TODO` stubs so you don't have to write boilerplate. They include:

| File | Purpose |
|---|---|
| `Camera.h` | Your implementation class inheriting from `ICamera` |
| `Camera.cpp` | Method bodies with `// TODO implement` stubs |
| `service.cpp` | Main entry point that instantiates your class and registers it |
| `Android.bp` | Build file with correct `shared_libs` pre-filled |

You **own these files** — fill in the TODOs and commit to git. hidl-gen will never overwrite them after the initial generation.

</details>

---

**Q12. If glue files are auto-generated, where do they live? Can you find them in the source repo?**

<details>
<summary>Answer</summary>

Glue files are **not in the source repo**. They exist only in the build output:

```
out/soong/.intermediates/hardware/interfaces/camera/1.0/
    android.hardware.camera@1.0_genc++_headers/gen/
        android/hardware/camera/1.0/
            ICamera.h
            BnHwCamera.h
            BpHwCamera.h
```

What lives in the repo is only:
```
hardware/interfaces/camera/1.0/
    ICamera.hal     ← source of truth
    Android.bp      ← generated by update-makefiles.sh
```

The `.hal` file is the source of truth. Glue files are derived artifacts.

</details>

---

**Q13. What is the `Bs*` file (e.g. `BsCamera.h`) and when is it used?**

<details>
<summary>Answer</summary>

`BsCamera.h` is the **passthrough adapter** (Bs = Binder passthrough). It wraps your implementation class for use in **passthrough mode**, where the HAL is loaded directly into the client process rather than running as a separate process.

In passthrough mode:
- No Binder IPC crossing happens
- `BsCamera` calls your implementation methods directly
- Used during migration from legacy HALs or for performance-critical same-process HALs

The transport mode is declared in `manifest.xml` as `<transport>passthrough</transport>`.

</details>

---

**Q14. A developer edits `BnHwCamera.h` to add custom logic. What happens on the next build?**

<details>
<summary>Answer</summary>

Their changes will be **overwritten**. `BnHwCamera.h` is a generated file in `out/soong/.intermediates/`. It is regenerated from `ICamera.hal` on every build by `hidl-gen`. Any manual edits are lost.

The correct approach is:
- If the interface needs to change → modify `ICamera.hal` and regenerate
- If the implementation needs to change → modify `Camera.cpp` (scaffold file)
- Never edit glue files directly

</details>

## 4. hidl-gen & Build System

---

**Q15. What does `hidl-gen -Lc++-impl` do? What does the `-L` flag mean?**

<details>
<summary>Answer</summary>

The `-L` flag specifies the **output language/format**. `-Lc++-impl` generates the C++ implementation scaffold files (`Camera.h`, `Camera.cpp`, `service.cpp`).

Other common `-L` options:

| Flag | Output |
|---|---|
| `-Lc++` | Generates glue files (ICamera.h, BnHw*, BpHw*) |
| `-Lc++-impl` | Generates implementation scaffold |
| `-Landroidmanifest` | Generates `AndroidManifest.xml` fragment |
| `-Lhash` | Generates interface hash for versioning |
| `-Ljava` | Generates Java bindings |

</details>

---

**Q16. What does `update-makefiles.sh` do? When must you run it?**

<details>
<summary>Answer</summary>

`update-makefiles.sh` scans `hardware/interfaces/` for `.hal` files and regenerates the `Android.bp` files for each interface package (the `hidl_interface` build targets).

You must run it:
- After **adding a new `.hal` file**
- After **adding a new package/version directory**
- After **modifying package structure**

If you skip it, the build system won't know about your new interface and `hidl-gen` won't be invoked to generate the glue library.

</details>

---

**Q17. What is `hidl_interface` in `Android.bp`? What does it do?**

<details>
<summary>Answer</summary>

`hidl_interface` is a Soong build rule that:
1. Runs `hidl-gen` to generate glue C++ files from `.hal`
2. Compiles those generated files
3. Packages them into a shared library named `android.hardware.<name>@<version>`

```json
hidl_interface {
    name: "android.hardware.camera@1.0",
    srcs: ["ICamera.hal"],
    interfaces: ["android.hidl.base@1.0"],
}
```

This produces `android.hardware.camera@1.0.so` which your implementation binary links against via `shared_libs`.

</details>

---

**Q18. What is the `-r` flag in hidl-gen? e.g. `-randroid.hardware:hardware/interfaces`**

<details>
<summary>Answer</summary>

The `-r` flag specifies the **root mapping** — it tells hidl-gen where to find `.hal` files for a given package prefix.

```bash
-randroid.hardware:hardware/interfaces
```

This means: "for any package starting with `android.hardware`, look in `hardware/interfaces/`"

So `android.hardware.camera@1.0` maps to `hardware/interfaces/camera/1.0/`.

You can have multiple `-r` flags for different package roots (e.g., vendor extensions).

</details>

---

**Q19. How does Soong know where the generated glue headers are when compiling `Camera.cpp`?**

<details>
<summary>Answer</summary>

When you declare:
```json
shared_libs: ["android.hardware.camera@1.0"]
```

Soong automatically:
1. Adds `-I out/soong/.intermediates/.../android.hardware.camera@1.0_genc++_headers/gen` to the compiler include path
2. Adds `-landroid.hardware.camera@1.0` to the linker flags

So `Camera.cpp` can `#include <android/hardware/camera/1.0/ICamera.h>` without knowing the full `out/` path. Soong resolves it transparently through the dependency graph.

</details>

## 5. HIDL Type System

---

**Q20. What types are available in HIDL? Give examples.**

<details>
<summary>Answer</summary>

**1. Primitives:**
```hidl
uint8_t, uint16_t, uint32_t, uint64_t
int8_t,  int16_t,  int32_t,  int64_t
float, double, bool, string
```

**2. Enum:**
```hidl
enum Status : uint32_t {
    OK    = 0,
    ERROR = 1,
};
```

**3. Struct:**
```hidl
struct Temperature {
    float value;         // in Celsius
    string name;
    TemperatureType type;
};
```

**4. Union (safe_union):**
```hidl
// Only one field valid at a time — auto-generated discriminator
safe_union SensorValue {
    float floatVal;
    int32_t intVal;
    vec<uint8_t> bytes;
};
```

**5. Vec (dynamic array):**
```hidl
interface IFoo {
    getData()             generates (vec<uint8_t> data);
    setStreams(vec<Stream> streams);
};
```

**6. Array (fixed size):**
```hidl
struct Color {
    uint8_t[4] rgba;   // exactly 4 bytes
};
interface IFoo {
    getUuid() generates (uint8_t[16] uuid);
};
```

**7. Handle (file descriptor):**
```hidl
interface IAllocator {
    allocate(uint32_t size)
        generates (Status s, handle memHandle);
};
// handle wraps native_handle_t
```

**8. FMQ (Fast Message Queue):**
```hidl
interface ISensors {
    initialize(
        fmq_sync<Event> eventQueue,      // blocking
        fmq_unsync<uint32_t> wakeQueue   // non-blocking
    ) generates (Result result);
};
```

**9. Bitfield (OR-able enum):**
```hidl
enum Flags : uint32_t {
    A = 1 << 0,
    B = 1 << 1,
    C = 1 << 2,
};
interface IFoo {
    setFlags(bitfield<Flags> flags);
};
```

**10. Interface type (callback):**
```hidl
interface ICallback {
    onEvent(Event e);
};
interface IFoo {
    register(ICallback cb);  // pass callback to HAL
};
```

</details>

## 6. HIDL Specific

---

**Q21. What is the difference between `generates` in HIDL and return values in AIDL?**

<details>
<summary>Answer</summary>

**HIDL — callback-style returns:**

```hidl
interface IFoo {
    getValue()  generates (int32_t value);
    getInfo()   generates (Status s, string name, int32_t id);
    doSomething();
};
```

```cpp
// Client usage in HIDL:
foo->getValue([](int32_t value) {
    useValue(value);   // lambda callback
});

// Multiple returns:
foo->getInfo([](Status s, const hidl_string& name, int32_t id) {
    if (s == Status::OK) { /* use name and id */ }
});

// Synchronous wrapper (generated):
auto result = foo->getValue();  // Return<int32_t>
int32_t val = result;
```

**AIDL — regular return values:**

```aidl
interface IFoo {
    int getValue();
    InfoResult getInfo();   // use parcelable for multiple
    void doSomething();
}

parcelable InfoResult {
    String name;
    int id;
}
```

```cpp
// Client usage in AIDL:
int value = foo.getValue();  // direct return!

InfoResult info = foo.getInfo();
String name = info.name;
```

**Key differences:**

| | HIDL | AIDL |
|---|---|---|
| Return syntax | `generates (T)` | Returns `T` directly |
| Multiple values | Multiple in lambda | Need `parcelable` |
| Error handling | `Return<T>` wrapper | Throws exception |
| Pattern | `hidl_cb` callback | Simple assignment |

</details>

**Q22. How does HIDL versioning work? What are the rules?**

<details>
<summary>Answer</summary>

HIDL uses `MAJOR.MINOR` versioning:

```
android.hardware.vibrator@1.0  ← major=1, minor=0
android.hardware.vibrator@1.1  ← same major, minor bumped
android.hardware.vibrator@2.0  ← major bump = breaking change
```

**Minor version rules (1.0 → 1.1):**

```
✓ ADD new methods to interface
✓ ADD new types
✓ ADD new enum values (at end)
✓ Extend interface with new methods

✗ CANNOT change existing methods
✗ CANNOT remove methods
✗ CANNOT change existing type fields
✗ CANNOT change enum values
```

```hidl
// IVibrator@1.0
interface IVibrator {
    on(uint32_t timeoutMs) generates (Status status);
    off() generates (Status status);
};

// IVibrator@1.1 — EXTENDS 1.0 (backward compatible)
interface IVibrator extends @1.0::IVibrator {
    perform(Effect_1_1 effect, EffectStrength strength)
        generates (Status status, uint32_t lengthMs);
};
```

**Major version rules (1.x → 2.0):** complete redesign allowed, no backward compatibility required.

**Casting between versions:**

```cpp
sp<V1_0::IVibrator> v1_0 = V1_0::IVibrator::getService();

sp<V1_1::IVibrator> v1_1 = V1_1::IVibrator::castFrom(v1_0);

if (v1_1 != nullptr) {
    v1_1->perform(effect, strength);  // 1.1 feature
} else {
    v1_0->on(500);                    // fall back to 1.0
}
```

**Compatibility matrix range:**

```xml
<!-- Accepts any version from 1.0 to 1.3 -->
<version>1.0-3</version>
<!-- Device provides 1.2 → COMPATIBLE ✓ -->
<!-- Device provides 0.9 → INCOMPATIBLE ✗ -->
```

</details>

## 7. AIDL HAL Specific

**Q23. What is `@VintfStability` and why is it needed?**

<details>
<summary>Answer</summary>

`@VintfStability` is an AIDL annotation that marks an interface as **stable across framework and vendor updates**.

**Without `@VintfStability`:**

Regular AIDL interfaces can change between builds — fine for same-partition code. But HAL interfaces cross the system/vendor boundary:

```
┌──────────────┐    ┌──────────────┐
│  /system     │    │  /vendor     │
│  (Google)    │    │  (Qualcomm)  │
│              │◄──►│              │
│  Framework   │    │  HAL impl    │
└──────────────┘    └──────────────┘

These two can be on DIFFERENT versions!
System updated → /vendor still old
Interface changed → CRASH!
```

**With `@VintfStability`:**

```aidl
@VintfStability        // ← This annotation
interface ILed {
    void setLed(in LedColor color, in int brightness);
}
```

Effects:
1. Interface is **frozen** — cannot change without version bump
2. Build system **enforces** this via `aidl_api/` directory
3. Compatibility checked at build time
4. Safe to use across system/vendor boundary

```
// Android.bp — must declare:
aidl_interface {
    name: "android.hardware.led",
    stability: "vintf",    // ← enables @VintfStability
    ...
}

// Will fail to build if you modify a frozen interface:
// Error: "android.hardware.led-V1 is frozen,
//         cannot be changed. Create V2 instead."
```

</details>

**Q24. How do errors work in AIDL HAL vs HIDL?**

<details>
<summary>Answer</summary>

**HIDL Error Handling — Status enums returned as values:**

```cpp
// HAL defines its own Status enum
enum Status : uint32_t { OK = 0, ERROR = 1, BAD_VALUE = 2 };

// Implementation
Return<Status> Vibrator::on(uint32_t timeoutMs) {
    if (timeoutMs == 0) return Status::BAD_VALUE;
    // do work...
    return Status::OK;
}

// Client checks return value
Status s = vibrator->on(timeoutMs);
if (s != Status::OK) { /* handle error */ }

// Also transport errors:
Return<Status> result = vibrator->on(timeoutMs);
if (!result.isOk()) { /* binder died etc */ }
```

**AIDL Error Handling — exceptions via ScopedAStatus:**

```cpp
// Implementation throws exception
ndk::ScopedAStatus Vibrator::on(int32_t timeoutMs) {
    if (timeoutMs <= 0) {
        return ndk::ScopedAStatus::fromExceptionCodeWithMessage(
            EX_ILLEGAL_ARGUMENT, "timeoutMs must be positive");
    }
    return ndk::ScopedAStatus::ok();
}
```

**Available exception codes:**

| Code | Java Equivalent |
|---|---|
| `EX_ILLEGAL_ARGUMENT` | `IllegalArgumentException` |
| `EX_NULL_POINTER` | `NullPointerException` |
| `EX_ILLEGAL_STATE` | `IllegalStateException` |
| `EX_SECURITY` | `SecurityException` |
| `EX_UNSUPPORTED_OPERATION` | `UnsupportedOperationException` |
| `EX_SERVICE_SPECIFIC` | Custom vendor error code |

```cpp
// Service-specific vendor error:
return ndk::ScopedAStatus::fromServiceSpecificError(
    MY_ERROR_CODE, "Description");

// Client:
auto status = vibrator->on(timeoutMs);
if (!status.isOk()) {
    int exCode = status.getExceptionCode();
    const char* msg = status.getMessage();

    if (exCode == EX_SERVICE_SPECIFIC) {
        int errCode = status.getServiceSpecificError();
    }
}
```

</details>

**Q25. What is the difference between HIDL and AIDL for HAL interfaces? Which is preferred now?**

<details>
<summary>Answer</summary>

| | HIDL | AIDL (for HALs) |
|---|---|---|
| **Introduced** | Android 8.0 | Android 11+ for HALs |
| **Language** | `.hal` files | `.aidl` files |
| **Transport** | hwbinder | binder (unified) |

**Q26. What is the role of `BnXxx` and `BpXxx` classes in HAL implementation?**

<details>
<summary>Answer</summary>

These are auto-generated by the AIDL/HIDL compiler.

```
Bn = Binder Native = SERVER SIDE (HAL implementation)
Bp = Binder Proxy  = CLIENT SIDE (framework caller)
```

```
┌────────────────────────────────────────────────────┐
│                                                    │
│   CLIENT PROCESS         SERVER PROCESS            │
│   (Framework)            (HAL daemon)              │
│                                                    │
│   ┌──────────────┐       ┌──────────────────────┐ │
│   │ BpVibrator   │       │ BnVibrator           │ │
│   │ (Proxy)      │       │ (Native/Stub)        │ │
│   │              │       │                      │ │
│   │ on(500ms)    │──IPC─►│ onTransact()         │ │
│   │              │       │  → calls on(500ms)   │ │
│   └──────────────┘       └──────────────────────┘ │
│                                    │               │
│                           ┌────────▼─────────────┐ │
│                           │ Vibrator              │ │
│                           │ YOUR implementation   │ │
│                           │ extends BnVibrator    │ │
│                           └──────────────────────┘ │
└────────────────────────────────────────────────────┘
```

```cpp
// Auto-generated BnVibrator (you DON'T write this):
class BnVibrator : public IVibrator {
public:
    binder_status_t onTransact(uint32_t code,
                               const AParcel* in,
                               AParcel* out) override;
};

// YOU write this — extends BnVibrator:
class Vibrator : public BnVibrator {
public:
    ndk::ScopedAStatus on(int32_t timeoutMs) override {
        writeSysfs("/sys/class/vibrator/enable", timeoutMs);
        return ndk::ScopedAStatus::ok();
    }
};

// Auto-generated BpVibrator (framework uses this):
class BpVibrator : public BpCInterface<IVibrator> {
public:
    ndk::ScopedAStatus on(int32_t timeoutMs) override {
        // Serializes call, sends over binder to HAL process
    }
};

// Framework gets BpVibrator automatically:
std::shared_ptr<IVibrator> v = IVibrator::fromBinder(...);
v->on(500);  // Goes through binder to HAL process
```

</details>

**Q27. Trace the full call path when a client calls `cam->takePicture()`.**

<details>
<summary>Answer</summary>

```
1. Client calls cam->takePicture()
   └── cam is a BpHwCamera (proxy object)

2. BpHwCamera::takePicture()
   └── Serializes arguments into a Binder parcel
   └── Calls transact() on the hwbinder driver → /dev/hwbinder

3. Kernel hwbinder driver
   └── Wakes up the HAL service process thread pool
   └── Delivers the parcel to the server side

4. BnHwCamera::onTransact()
   └── Receives the parcel
   └── Deserializes arguments
   └── Calls this->takePicture() via virtual dispatch

5. Camera::takePicture()  ← YOUR implementation
   └── Accesses /dev/video0
   └── Does actual hardware work
   └── Returns result

6. Result travels back:
   BnHwCamera → hwbinder kernel → BpHwCamera → client
```

Complete timing view (AIDL example):

```
system_server          kernel(/dev/binder)    HAL process
     │                        │                    │
     │──transact(on, 500)────►│                    │
     │                        │──wake HAL thread──►│
     │   BLOCKED              │                    │──onTransact()
     │                        │                    │──Vibrator::on()
     │                        │                    │──writeSysfs()
     │                        │◄──reply(ok)────────│
     │◄──return(ok)───────────│                    │
     │                        │                    │
   continues                                    waits for next call

Total time: ~0.5ms–5ms (IPC overhead)
vs ~0.01ms for passthrough direct call
```

</details>

**Q28. What is `sp<ICamera>`? Why is it used instead of a raw pointer?**

<details>
<summary>Answer</summary>

`sp<T>` is Android's **strong pointer** (reference-counted smart pointer), similar to `std::shared_ptr`. It is used because:

- HIDL objects cross process boundaries and can be held by multiple clients
- Reference counting ensures the HAL object is alive as long as any client holds a reference
- When the last `sp<>` is released, the object is destroyed safely
- It handles the Binder lifecycle (incrementing/decrementing the Binder reference count)

`wp<T>` (weak pointer) is also available, analogous to `std::weak_ptr`.

</details>

---

**Q29. What is `Return<T>` in HIDL? Why not use plain `T`?**

<details>
<summary>Answer</summary>

`Return<T>` is HIDL's wrapper for return values that handles **transport errors** in addition to the actual return value. It can represent:

- A successful return with value `T`
- A **transport error** (e.g., HAL service crashed, Binder died)

```cpp
Return<bool> result = cam->takePicture();
if (!result.isOk()) {
    // Binder/transport error — HAL may have died
}
bool success = result;  // actual return value
```

Using plain `T` would hide transport errors. `Return<T>` forces callers to handle both the result and potential IPC failures. `Return<void>` is used for methods that return nothing.

</details>

---

**Q30. What happens when a HIDL HAL service crashes? How does the client know?**

<details>
<summary>Answer</summary>

When the HAL process crashes:
1. The Binder kernel driver detects the death
2. It sends a **death notification** to all registered `DeathRecipient` objects on the client side
3. Any pending `Return<T>` calls return with `isOk() == false`

On the client side, you register a death recipient:

```cpp
struct CameraDeathRecipient : hidl_death_recipient {
    void serviceDied(uint64_t cookie, const wp<IBase>& who) override {
        // HAL died — attempt reconnect
        cam = ICamera::getService();
    }
};

cam->linkToDeath(new CameraDeathRecipient(), 0);
```

This is important for robustness — the framework must handle HAL restarts without crashing itself.

</details>

**Q31. What is `hidl_cb` (HIDL callback)? Why are callbacks used instead of direct return values for complex types?**

<details>
<summary>Answer</summary>

In HIDL, methods that return complex types (structs, vectors, strings) use a **synchronous callback** pattern instead of a direct return:

```cpp
// .hal definition
getFrame() generates (bool success, vec<uint8_t> data);

// your implementation
Return<void> Camera::getFrame(getFrameCb _hidl_cb) {
    hidl_vec<uint8_t> frameData = captureFrame();
    _hidl_cb(true, frameData);   // invoke callback with results
    return Void();
}
```

Callbacks are used because:
- Complex types like `vec<T>` or nested structs need special Binder serialization
- The callback is invoked **synchronously before the method returns** — it is not asynchronous
- It avoids multiple round trips for returning multiple values
- Binder has a transaction size limit; callbacks allow zero-copy data passing in some cases

</details>

**Q32. What is the difference between `oneway` methods in HIDL/AIDL?**

<details>
<summary>Answer</summary>

**Regular (synchronous) method:**

```
Client sends request → WAITS → Server processes → Returns

│ Client │──── request ────►│ Server │
│        │                  │        │  (processing...)
│ BLOCKS │◄─── response ────│        │
```

**`oneway` (asynchronous) method:**

```
Client sends request → CONTINUES (doesn't wait)

│ Client │──── request ────►│ Server │
│RETURNS │                  │        │  (processing...)
│immediately                │        │
```

```hidl
// HIDL oneway:
interface IVibrator {
    on(uint32_t timeoutMs) generates (Status status);  // regular
    oneway setAmplitude(uint8_t amplitude);             // async
    // NOTE: oneway cannot have generates()!
};
```

```aidl
// AIDL oneway:
interface ILed {
    void setLed(in LedColor color, in int brightness); // regular
    oneway void logEvent(in String event);              // async
}
```

**Characteristics of oneway:**

```
✓ Lower latency (caller not blocked)
✓ Good for notifications to server

✗ Cannot have return values
✗ No exception propagation to caller
✗ No ordering guarantee with other oneway calls
✗ Cannot know if call was processed
```

**Use cases:**

```
✓ Logging events
✓ Fire-and-forget notifications
✓ Callbacks from HAL to framework
  (HAL doesn't need to wait for framework to process)
```

```hidl
// Typical callback pattern:
interface IVibratorCallback {
    oneway void onComplete();  // HAL notifies framework when done
}
```

</details>

**Q33. Explain FMQ (Fast Message Queue) — when and why to use it?**

<details>
<summary>Answer</summary>

**Problem with regular binder for high-frequency data:**

```
Sensor HAL sends 1000 events/second

Using binder for each event:
1000 binder transactions/sec
= Context switches
= System calls
= HIGH LATENCY, HIGH CPU OVERHEAD!
```

**FMQ Solution — shared memory ring buffer:**

```
┌──────────────────────────────────────────────────┐
│                                                  │
│  HAL Process          Framework Process          │
│  ┌───────────┐        ┌───────────────────────┐ │
│  │ Sensor HAL│        │ SensorService         │ │
│  │  writes   │        │  reads                │ │
│  │  events   │        │  events               │ │
│  └─────┬─────┘        └──────────┬────────────┘ │
│        │                         │              │
│        ▼                         ▼              │
│  ┌─────────────────────────────────────────┐   │
│  │         Shared Memory Ring Buffer       │   │
│  │  [event1][event2][event3][event4]...    │   │
│  │                                         │   │
│  │  • Zero-copy (no data serialization)    │   │
│  │  • Lock-free atomic operations          │   │
│  │  • No binder for data transfer          │   │
│  └─────────────────────────────────────────┘   │
│                                                  │
│  Setup via binder (once):                        │
│  HAL → Framework: "here's the FMQ handle"        │
└──────────────────────────────────────────────────┘
```

```hidl
// In HAL interface:
interface ISensors {
    initialize(
        fmq_sync<Event> eventQueue,      // HAL writes events here
        fmq_sync<uint32_t> wakeLockQueue
    ) generates (Result result);
};
```

```cpp
// HAL writes — NO binder call needed!
mEventQueue->write(events.data(), events.size());

// Framework reads directly from shared memory:
while (mEventQueue->read(&event, 1)) {
    processSensorEvent(event);
}
```

**When to use FMQ:**

```
✓ High-frequency data (sensors, audio)
✓ Low-latency requirements
✓ Large data volumes
✓ Producer-consumer pattern

✗ Infrequent calls
✗ Simple request-response
✗ When simplicity matters more than performance
```

**Types:**

| Type | Behavior |
|---|---|
| `fmq_sync<T>` | One reader, blocks if full/empty |
| `fmq_unsync<T>` | Multiple readers allowed, non-blocking |

</details>

**Q34. What is the difference between `hardware/interfaces/` and `vendor/` for HAL implementation?**

<details>
<summary>Answer</summary>

| | `hardware/interfaces/` | `vendor/<company>/` |
|---|---|---|
| **Contains** | `.hal` interface definitions + default reference implementations | Device/SoC-specific implementations |
| **Owned by** | AOSP / Google | Chip vendor or OEM |
| **In AOSP tree** | ✅ Yes | Typically separate repo (vendor blob) |
| **Versioned** | Strictly versioned (1.0, 1.1, 2.0) | Internal versioning |
| **Shipped** | As source | Often as prebuilt `.so` |

The `.hal` files in `hardware/interfaces/` define the **contract**. The actual hardware implementation goes in `vendor/` since it is device-specific and often proprietary.

</details>

---

**Q35. What is `relative_install_path: "hw"` in `Android.bp`?**

<details>
<summary>Answer</summary>

It specifies the subdirectory under `/vendor/bin/` where the binary is installed.

With `relative_install_path: "hw"`, the binary installs to:
```
/vendor/bin/hw/android.hardware.camera@1.0-service
```

Without it, it would install to:
```
/vendor/bin/android.hardware.camera@1.0-service
```

The `hw/` convention is standard for HAL service binaries and is expected by the `.rc` file and `init`.

</details>

---

**Q36. What is the purpose of the `.rc` file for a HAL service?**

<details>
<summary>Answer</summary>

The `.rc` file is an **Android Init Language** script that tells the `init` process how to start, manage, and restart the HAL service.

```
service vendor.camera-hal-1-0 /vendor/bin/hw/android.hardware.camera@1.0-service
    class hal
    user cameraserver
    group camera
    onrestart restart cameraserver
```

Key directives:
- `class hal` — groups HAL services; started together during boot
- `user/group` — drops privileges (HAL shouldn't run as root)
- `onrestart` — what to do when HAL crashes and restarts

Without the `.rc` file, `init` won't start your service at boot.

</details>

---

**Q37. Where is the HAL binary installed on the device, and why in `/vendor/` not `/system/`?**

<details>
<summary>Answer</summary>

HAL binaries install to `/vendor/bin/hw/`. They are in `/vendor/` and not `/system/` because of **Project Treble**:

- `/system/` is the AOSP framework partition — updated by Google OTA
- `/vendor/` is the vendor partition — updated by the device manufacturer

Treble requires that `/system/` and `/vendor/` can be updated **independently**. If HAL binaries were in `/system/`, a Google OTA might break vendor hardware code. Keeping them in `/vendor/` maintains the separation.

The framework in `/system/` communicates with HALs in `/vendor/` via stable HIDL interfaces over hwbinder — neither side needs to know the other's internals.

</details>

**Q38. You added a new method to `ICamera.hal`. What are all the places you need to update?**

**Q39. How do you extend a HIDL interface without breaking the existing version?**

<details>
<summary>Answer</summary>

Create a new minor version that `extends` the old one:

```hidl
// hardware/interfaces/camera/1.1/ICamera.hal
package android.hardware.camera@1.1;

import android.hardware.camera@1.0;

interface ICamera extends @1.0::ICamera {
    setHDR(bool enable) generates (bool success);  // new method
};
```

Key rules:
- Never modify a released `.hal` version
- New version inherits all methods from the previous version
- Clients coded against `1.0` still work (backward compatible)
- Clients wanting new features use `1.1`

```cpp
sp<V1_1::ICamera> cam11 = V1_1::ICamera::castFrom(cam10);
if (cam11 != nullptr) {
    cam11->setHDR(true);  // 1.1 feature available
}
```

**Q40. How would you handle backward compatibility when updating an AIDL HAL interface?**

<details>
<summary>Answer</summary>

**AIDL Approach (versioned):**

```aidl
// Version 1 (frozen — cannot change)
// aidl_api/android.hardware.led/1/...ILed.aidl
@VintfStability
interface ILed {
    void setLed(in LedColor color, in int brightness);
    void turnOff(in LedColor color);
}

// Version 2 (add features — new version)
// android/hardware/led/ILed.aidl (current)
@VintfStability
interface ILed {
    void setLed(in LedColor color, in int brightness);
    void turnOff(in LedColor color);

    // NEW in V2:
    void blinkLed(in LedColor color, in int onMs, in int offMs);
    int getMaxBrightness(in LedColor color);
}
```

**Framework handles both versions:**

```cpp
void LedController::blink(LedColor color, int onMs, int offMs) {
    if (mLed_v2 != nullptr) {
        // Native V2 blink
        mLed_v2->blinkLed(color, onMs, offMs);
    } else {
        // Emulate using V1
        std::thread([=] {
            while (true) {
                mLed_v1->setLed(color, 255);
                usleep(onMs * 1000);
                mLed_v1->turnOff(color);
                usleep(offMs * 1000);
            }
        }).detach();
    }
}
```

**VINTF manifests:**

```xml
<!-- Old device: -->
<version>1</version>   ← provides V1

<!-- New device: -->
<version>2</version>   ← provides V2

<!-- Framework compatibility matrix: -->
<version>1-2</version> ← accepts V1 OR V2
```

</details>

**Q41. What is `registerAsService()` doing internally?**

<details>
<summary>Answer</summary>

`registerAsService("default")` does the following:

1. Creates a `BnHwCamera` wrapper around your `Camera` object
2. Opens a connection to `HwServiceManager` over hwbinder
3. Registers the `BnHwCamera` Binder object under the name `android.hardware.camera@1.0::ICamera/default`
4. Starts the hwbinder thread pool to handle incoming calls

After this, any client calling `ICamera::getService("default")` will receive a `BpHwCamera` proxy pointing to your `BnHwCamera`, which dispatches to your `Camera` object.

</details>

**Q42. What is `configureRpcThreadpool` and `joinRpcThreadpool` in `service.cpp`?**

<details>
<summary>Answer</summary>

```cpp
// service.cpp
configureRpcThreadpool(1, true /* callerWillJoin */);

Camera* cam = new Camera();
cam->registerAsService("default");

joinRpcThreadpool();
```

- `configureRpcThreadpool(N, ...)` — initializes `N` threads in the hwbinder thread pool to handle concurrent incoming Binder calls
- `joinRpcThreadpool()` — blocks the main thread and adds it to the thread pool, keeping the process alive to serve requests

If you skip `joinRpcThreadpool()`, the `main()` function returns and the HAL process exits immediately after registration.

</details>

**Q45. What is SELinux's role in HIDL HAL? What do you need to add for a new HAL?**

<details>
<summary>Answer</summary>

SELinux enforces mandatory access control on all HIDL HAL communications. For a new HAL you need:

1. **Service type** — declare a type for your HAL service:
```
# vendor/sepolicy/hal_camera.te
type hal_camera, domain;
hal_server_domain(hal_camera, hal_camera)
```

2. **File context** — label your binary:
```
# vendor/sepolicy/file_contexts
/vendor/bin/hw/android\.hardware\.camera@1\.0-service  u:object_r:hal_camera_exec:s0
```

3. **Allow rules** — permit access to hardware devices:
```
# hal_camera.te
allow hal_camera video_device:chr_file rw_file_perms;
```

4. **hwservice context** — label the hwbinder service:
```
# hwservice_contexts
android.hardware.camera@1.0::ICamera  u:object_r:hal_camera_hwservice:s0
```

Without proper SELinux policy, the HAL service will start but all Binder calls will be denied with `avc: denied` errors.

</details>

**Q46. What happens if two different versions (1.0 and 1.1) of the same HAL are registered? How does the client choose?**

<details>
<summary>Answer</summary>

Both can be registered simultaneously under the same instance name. The client uses `getService()` and `castFrom()` to negotiate:

```cpp
// Try to get 1.1 first
sp<V1_1::ICamera> cam11 = V1_1::ICamera::getService("default");
if (cam11 == nullptr) {
    // Fall back to 1.0
    sp<V1_0::ICamera> cam10 = V1_0::ICamera::getService("default");
}
```

Or cast from a known lower version:
```cpp
sp<V1_0::ICamera> cam10 = V1_0::ICamera::getService("default");
sp<V1_1::ICamera> cam11 = V1_1::ICamera::castFrom(cam10);
// cam11 is null if the implementation only supports 1.0
```

`castFrom()` works because `V1_1::ICamera` inherits from `V1_0::ICamera` — it's a real C++ inheritance chain via the glue files.

</details>

**Q47. What is interface hashing in HIDL and why does it exist?**

<details>
<summary>Answer</summary>

HIDL computes a **SHA256 hash** of each `.hal` file and stores it in `current.txt` files. This detects accidental modification of released interfaces.

```bash
# Generate hash for your interface
hidl-gen -Lhash -randroid.hardware:hardware/interfaces android.hardware.camera@1.0

# Verify against stored hashes
android/hardware/interfaces/camera/1.0/ICamera.hal: abc123...
```

If you modify a released `.hal` without bumping the version, the hash check fails at build time with an error like:
```
error: ICamera.hal has changed hash, update current.txt or bump version
```

This enforces the **stable interface contract** — once a version is released, it cannot change. Changes require a new version.

</details>

**Q48. Explain the full build-time dependency chain from `.hal` to the final service binary.**

<details>
<summary>Answer</summary>

```
ICamera.hal
    │
    ▼  hidl_interface rule in Android.bp triggers hidl-gen
ICamera.h, BnHwCamera.h, BpHwCamera.h
ICamera.cpp, ICameraAll.cpp
    │
    ▼  cc_library_shared compiles glue files
android.hardware.camera@1.0.so
    │                                Camera.cpp (your scaffold)
    │                                Camera.h
    │                                service.cpp
    │                                    │
    ▼                                    ▼ cc_binary rule
    └─────── linked together ──────► android.hardware.camera@1.0-service
                                         │
                                    installed to
                                    /vendor/bin/hw/...
                                         │
                                    packaged into
                                    vendor.img
```

Soong resolves the dependency: your `cc_binary` depends on `android.hardware.camera@1.0` (shared lib), which depends on `hidl_interface`, which runs `hidl-gen` on `ICamera.hal`. The entire chain is driven by the `Android.bp` dependency graph.

</details>

**Q49. What is the `IBase` interface that all HIDL interfaces extend? What methods does it provide?**

<details>
<summary>Answer</summary>

`IBase` is the root interface that all HIDL interfaces implicitly extend (like `Object` in Java). It provides:

| Method | Purpose |
|---|---|
| `ping()` | Check if HAL is alive |
| `getHashChain()` | Returns interface hash for compatibility checking |
| `setHALInstrumentation()` | Enable HIDL tracing/instrumentation |
| `linkToDeath()` | Register a death recipient |
| `unlinkToDeath()` | Unregister a death recipient |
| `interfaceDescriptor()` | Returns fully qualified interface name |
| `getDebugInfo()` | Returns debug info (PID, ptr) |
| `debug()` | Dump debug state to a file descriptor |

`BnHwBase` and `BpHwBase` implement these for all interfaces, which is why `Camera` (which extends `ICamera` which extends `IBase`) automatically has all these capabilities without you implementing them.

</details>

**Q50. What are the security considerations when developing a HAL?**

<details>
<summary>Answer</summary>

**1. SELinux (Most Important)**

```
# Only allow what's needed — be specific:
allow hal_led_default sysfs_leds:file rw_file_perms;

# NOT too broad:
allow hal_led_default sysfs:file rw_file_perms;   # BAD

# Never in production:
# permissive hal_led_default;   ← disables SELinux entirely!
```

**2. Input Validation**

```cpp
// ALWAYS validate inputs from framework
ndk::ScopedAStatus Vibrator::on(int32_t timeoutMs) {
    if (timeoutMs <= 0 || timeoutMs > MAX_TIMEOUT) {
        return ndk::ScopedAStatus::fromExceptionCodeWithMessage(
            EX_ILLEGAL_ARGUMENT, "Invalid timeout");
    }
    // Never trust caller, always validate!
}
```

**3. Privilege Separation**

```
service vendor.led-hal /vendor/bin/hw/android.hardware.led-service
    user nobody         # NOT root!
    group nobody
    # Only add capabilities you absolutely need
```

**4. No Sensitive Data in Logs**

```cpp
// BAD:
LOG(DEBUG) << "PIN entered: " << pin;
LOG(DEBUG) << "User data: "   << userData;

// GOOD:
LOG(DEBUG) << "Operation completed";
// Never log credentials, PII, keys!
```

**5. Secure Handle Passing**

```cpp
ndk::ScopedAStatus processBuffer(const ndk::ScopedFileDescriptor& fd) {
    int rawFd = fd.get();
    if (rawFd < 0) {
        return ndk::ScopedAStatus::fromExceptionCode(EX_ILLEGAL_ARGUMENT);
    }
    struct stat st;
    if (fstat(rawFd, &st) != 0) {
        return ndk::ScopedAStatus::fromExceptionCode(EX_ILLEGAL_ARGUMENT);
    }
    if (!S_ISREG(st.st_mode) && !S_ISCHR(st.st_mode)) {
        return ndk::ScopedAStatus::fromExceptionCode(EX_SECURITY);
    }
}
```

**6. Memory Safety**

```cpp
ndk::ScopedAStatus getData(const std::vector<uint8_t>& input) {
    if (input.size() > MAX_BUFFER_SIZE) {
        return ndk::ScopedAStatus::fromExceptionCode(EX_ILLEGAL_ARGUMENT);
    }
    // Use std::string, std::vector
    // Avoid strcpy, sprintf, raw pointer arithmetic
}
```

**7. Fuzzing**

```cpp
// hardware/interfaces/led/aidl/default/fuzzer.cpp
extern "C" int LLVMFuzzerTestOneInput(
        const uint8_t* data, size_t size) {
    FuzzedDataProvider fdp(data, size);
    auto led = ndk::SharedRefBase::make<Led>();

    int color      = fdp.ConsumeIntegral<int>();
    int brightness = fdp.ConsumeIntegral<int>();

    // Call HAL with random inputs — find crashes/issues
    led->setLed(static_cast<LedColor>(color), brightness);
    return 0;
}
```

</details>
