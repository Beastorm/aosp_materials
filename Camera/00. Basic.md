# Android Camera Architecture: A Three-Tier Hierarchy

To understand how the **cameraserver**, **Camera Service**, and **Camera Provider** interact,
it helps to look at them as a three-tier hierarchy: the **application (Client)**,
the **system manager (Service)**, and the **hardware driver (HAL)**.

---

## 1. cameraserver (The System Process)

The `cameraserver` is a **native Linux process** that resides in the System Partition
(`/system/bin/cameraserver`).

- **Lifecycle:** It is started by the Android `init` process during boot via the
  `cameraserver.rc` configuration.

- **Security:** It runs under its own UID/GID (`camera`) and is heavily sandboxed by
  **SELinux**. This ensures that even if the camera service is compromised, it cannot
  easily access other system resources like the microphone or personal files without
  explicit permissions.

- **Source Code:**
  - **Main Entry Point:** `frameworks/av/camera/cameraserver/main_cameraserver.cpp`
  - **Build File:** `frameworks/av/camera/cameraserver/Android.bp`

---

## 2. Camera Service (The Management Logic)

This is the **core C++ logic** that lives inside the `cameraserver` process.
It implements the `ICameraService` Binder interface.

**Role:** It is the "traffic cop." It manages all active camera sessions.

### Key Responsibilities

- **Permissions:** It checks if the calling app (via its package name/UID) has the
  `android.permission.CAMERA` permission.

- **Conflict Resolution:** If you are in a video call and try to open a third-party
  camera app, the Service decides which app should be **evicted** based on priority.

- **API Translation:** It bridges the gap between the modern Camera2 AIDL interfaces
  and the hardware-specific HAL calls.

### Source Code

- **Implementation:** `frameworks/av/services/camera/libcameraservice/CameraService.cpp`
- **API Definitions:** `frameworks/av/camera/aidl/android/hardware/ICameraService.aidl`

---

## 3. Camera Provider (The Hardware Abstraction)

The Camera Provider is the standardized implementation of the
**HAL (Hardware Abstraction Layer)**. It typically runs as a **separate process**
in the Vendor Partition (`/vendor/bin/hw/...`).

**Role:** It abstracts the specific hardware complexities. To the `cameraserver`,
every camera looks like a standard "Camera Device," regardless of whether it's a
Sony, Samsung, or Omnivision sensor.

### The "Provider" Concept

Since **Android 8.0 (Project Treble)**, the Camera Service no longer loads HAL
libraries directly. Instead, it talks to a "Provider" process over **HIDL**
(Hardware Interface Definition Language) or **AIDL**.

### Capabilities

- **Discovery:** It tells the Camera Service how many physical cameras are on the
  device (Front, Back, Wide, Telephoto).
- **Device Versioning:** It manages whether the hardware supports HAL 1.0 (legacy)
  or HAL 3.x (modern).

### Source Code

- **Standard Interface:** `hardware/interfaces/camera/provider/aidl/`
- **Common Library:** `hardware/interfaces/camera/common/`

---

## 4. Detailed Communication Flow (The "Open" Sequence)

1. **App Trigger:** An app calls `CameraManager.openCamera("0")`.
2. **Binder Call:** This goes across the Binder IPC boundary into the
   `cameraserver` process.
3. **Service Validation:** `CameraService::connectDevice()` is called. It verifies
   the app is in the foreground and has permissions.
4. **Provider Interaction:** The Service calls the Camera Provider
   (e.g., `ICameraProvider::getDeviceInterface_3_x`).
5. **HAL Implementation:** The Provider process invokes the vendor-specific code
   (found in `vendor/`) which sets up the Linux kernel **V4L2**
   (Video for Linux 2) drivers.
6. **Stream Setup:** The HAL creates a "Camera Device" instance. The Service then
   coordinates with the **SurfaceFlinger** (Display) or **MediaCodec**
   (Video Recording) to route camera buffers to the right place.

---

## 5. Why the Split? (Process Isolation)

By having three distinct areas:

- **If the App crashes**, the Service cleans up the hardware state.
- **If the Camera Provider (driver) crashes**, the `cameraserver` detects the dead
  Binder link and can restart the provider without rebooting the whole phone.
- **By keeping the Provider in the Vendor partition**, Google can update the Android
  Framework (the Service) while the phone manufacturer doesn't have to touch their
  proprietary sensor code.

# Android Camera Permissions: A Deep Dive

---

## How is Access Denied Without a Manifest Declaration?

Even if an app tries to bypass the Java `CameraManager` and talk directly to the native
`cameraserver` via Binder, it will fail. This is because the check happens on the
**receiving side (the server)**, not just the sending side (the app).

Understanding how permissions are enforced at the AOSP level reveals the
**"Defense in Depth"** strategy Android uses. Access is denied because the Camera Service
acts as a **strict gatekeeper** that validates every caller's identity before talking
to the hardware.

### The Denial Flow

- **Identity via Binder:** When an app makes a Binder call to the camera service, the
  kernel attaches the caller's **UID (User ID)** and **PID (Process ID)** to the
  transaction.

- **The "Gatekeeper" Check:** The `cameraserver` receives the call and immediately asks
  the `PermissionController` or `PackageManager`:
  > *"Does UID 10085 have the `android.permission.CAMERA` permission?"*

- **Manifest Verification:** The `PackageManager` maintains a database of all installed
  apps and their declared permissions. If the app didn't declare the permission in its
  manifest, it was never granted at install/runtime. The `PackageManager` returns
  `FALSE`.

- **Security Exception:** The `cameraserver` then returns a `PERMISSION_DENIED` error
  or throws a `SecurityException` back to the app.

---

## How Permission is Implemented in AOSP (Native Level)

In AOSP, the heavy lifting is done in `CameraService.cpp` using a utility function
called `checkCallingPermission`.

### The Core Logic (Simplified C++)

Inside `frameworks/av/services/camera/libcameraservice/CameraService.cpp`, when an app
tries to connect, the following happens:

```cpp
// 1. Get the identity of the caller from the Binder transaction
int callingPid = Binder::getCallingPid();
int callingUid = Binder::getCallingUid();

// 2. Check if the caller is the system itself (which always has access)
if (callingPid != getpid()) {
    // 3. Perform the actual permission check
    if (!checkCallingPermission(String16("android.permission.CAMERA"))) {
        ALOGE("Permission Denial: can't use camera from pid=%d, uid=%d",
              callingPid, callingUid);
        return PERMISSION_DENIED;
    }
}
```

## Key Components in the Implementation

- **`checkCallingPermission`:** This is a helper function that communicates with the
  `ActivityManagerService (AMS)` or `PermissionManager` to verify if the specific UID
  has been granted the string-based permission `android.permission.CAMERA`.

- **`AppOpsManager`:** For modern Android (6.0+), the service also checks **AppOps**.
  Even if the manifest has the permission, a user might have toggled it **"OFF"** in
  settings. The service calls `mAppOps.checkOp` to ensure the "Camera" operation is
  currently allowed for that app.

---

## Summary of the Enforcement Flow

| Step | Component | Action |
|------|-----------|--------|
| **1** | App | Initiates Binder call to `connectDevice()`. |
| **2** | Kernel | Authenticates the caller's UID and PID. |
| **3** | Camera Service | Receives call and extracts UID. |
| **4** | Permission Service | Checks if UID matches an app with the `CAMERA` permission in its Manifest. |
| **5** | AppOps Service | Checks if the user has manually revoked access in Settings. |
| **6** | Decision | If both pass, Service talks to HAL; otherwise, returns `PERMISSION_DENIED`. |

> **Why This Matters:** This "Server-Side Verification" is why it is impossible to
> "trick" the system by just writing a custom camera driver or library; the central
> service **always** validates who is asking.

---

## Implementing a Custom Permission for Your Own Requirement

Implementing a custom permission in AOSP requires a **"full-stack"** change. You have
to define the permission in the framework, ensure the system recognizes it, and then
manually add the enforcement logic in the native `CameraService`.


### Step 1: Define the Permission (Framework Layer)

First, you must let the Android system know this new permission exists. This is done
in the **framework base**.

- **File:** `frameworks/base/core/res/AndroidManifest.xml`
- **Action:** Add a `<permission>` tag. If you want it to be a system-level permission
  (only for your apps), set the `protectionLevel` to `signature` or `privileged`.

```xml
<permission android:name="com.harman.permission.CUSTOM_CAMERA_CONTROL"
    android:label="Custom Camera Control"
    android:description="@string/perm_desc_custom_camera"
    android:protectionLevel="signatureOrSystem" />

```

### Step 2: Implement Enforcement in CameraService (Native Layer)

Now, you need to modify the C++ code to check for this specific string before allowing
a certain action.

- **File:** `frameworks/av/services/camera/libcameraservice/CameraService.cpp`
- **Action:** Create a helper function to validate your custom permission.

#### The C++ Check Logic

In the native layer, you use the `PermissionChecker` or `ServiceManager` to talk back
to the `PermissionManagerService`.

``` cpp
bool CameraService::checkCustomPermission(int callingPid, int callingUid) {
    // String16 is the standard for binder-based permission strings
    String16 customPermission("com.harman.permission.CUSTOM_CAMERA_CONTROL");

    // Use the internal checkPermission utility
    if (checkPermission(customPermission, callingPid, callingUid)) {
        return true;
    }

    ALOGE("Permission Denial: App (uid: %d) missing Harman Custom Camera Permission",
          callingUid);
    return false;
}
```
### Step 3: Apply the Gatekeeper
Find the function you want to protect (e.g., connectDevice or a custom function
you've added for your specific hardware features) and insert your check.

``` cpp
Status CameraService::connectDevice(const sp<ICameraDeviceCallbacks>& cameraCb, ...) {
    int callingPid = Binder::getCallingPid();
    int callingUid = Binder::getCallingUid();

    // Your new enforcement point
    if (!checkCustomPermission(callingPid, callingUid)) {
        return STATUS_ERROR(ERROR_PERMISSION_DENIED, "Custom permission required");
    }

    // Existing standard camera permission check
    if (!checkCallingPermission(String16("android.permission.CAMERA"))) {
        return STATUS_ERROR(ERROR_PERMISSION_DENIED, "Camera permission required");
    }

    // ... rest of the connection logic
}
```

### Step 4: Update the SELinux Policy

Since you are adding a new permission interaction, the `cameraserver` process needs
permission to talk to the `permission_service` or `package_service` via Binder.

- **File:** `system/sepolicy/vendor/cameraserver.te`
  (or your device-specific `.te` file)
- **Action:** Ensure the `cameraserver` has `allow` rules for `permission_service`.

```plaintext
allow cameraserver permission_service:service_manager find;
```

### Step 5: Usage in the App Manifest
For your application to pass this check, you must now declare this custom permission
in your app's AndroidManifest.xml.
```
<uses-permission android:name="com.harman.permission.CUSTOM_CAMERA_CONTROL" />

```


### Critical Considerations for AOSP Implementation

| Area | Why It Matters |
|------|----------------|
| **Protection Level** | Using `signature` ensures that only apps signed with your platform key can use this feature, preventing 3rd party apps from exploiting your custom logic. |
| **AppOps Integration** | If you want the user to be able to toggle this in "Settings," you would also need to register a new `AppOp` in `frameworks/base/core/java/android/app/AppOpsManager.java`. |
| **Binder Identity** | Always use `Binder::getCallingUid()`. Never trust a UID passed as a function argument, as that can be **spoofed** by a malicious app. |

## How Permissions and SELinux Are Related

In the AOSP world, **Permissions** and **SELinux** represent two different "checkpoints"
that a request must pass.

> Think of **Permissions** as the badge check at the front door *(checking who you are)*,
> and **SELinux** as the structural integrity of the building *(checking what you are
> allowed to touch, regardless of your badge)*.

---

### 1. The Relationship: Defense in Depth

They are **independent layers**. Even if an app has the `CAMERA` permission, it can
still be blocked by SELinux if the `cameraserver` process doesn't have the "permission"
from the kernel to access a specific hardware node.

| Layer | Type | Handled By | Purpose |
|-------|------|------------|---------|
| **Android Permissions** | Discretionary (DAC) | `PermissionManager` (Framework) | Validates if the User/App has permission to use a feature. |
| **SELinux** | Mandatory (MAC) | Kernel (LSM) | Validates if a Process is allowed to perform an action on a Resource. |

---

### 2. How They Interact in the Camera Pipeline

Let's look at what happens when you try to access your custom camera control:

#### Step A: The Permission Check (App to Service)

When your app calls the `cameraserver`, the service checks your UID.

- **Check:** Does the App have `com.harman.permission.CUSTOM_CAMERA_CONTROL`?
- **Result:** If **Yes**, the code execution continues inside `CameraService.cpp`.

#### Step B: The SELinux Check (Service to Hardware)

Now, the `cameraserver` (or the Provider HAL) tries to write to a dev node like
`/dev/video0` or a custom `sysfs` path for your Harman hardware.

- **Check:** Does the process labeled `u:r:cameraserver:s0` have the `write`
  permission on the file labeled `u:object_r:camera_device:s0`?
- **Result:** If the SELinux policy (`.te` file) doesn't explicitly allow this, the
  kernel **blocks** the operation with an `AVC Denial`, even though the C++ code is
  currently running because **Step A passed**.

---

### 3. Coordinating the Two for Your Custom Requirement

If you are implementing a custom feature for a HARMAN project, you usually have to
update **both**.

#### The SELinux Side of Your Custom Permission

If you added a new Binder call to the `cameraserver`, you might see a Logcat error
saying `avc: denied { find } ...`. This is because the `cameraserver` process needs
permission to "talk" to the system service that manages permissions.

In `cameraserver.te`:

``` text
# Allow cameraserver to find the permission service to check your custom permission
allow cameraserver permission_service:service_manager find;

# If your custom control touches a new hardware path
allow cameraserver custom_hw_device:chr_file rw_file_perms;
```

### 4. Key Differences in Enforcement

#### Android Permissions are "Soft"

- They can be **granted or revoked at runtime** by the user.
- They are defined in **XML** (`AndroidManifest.xml`).
- Failure results in a Java `SecurityException`.

#### SELinux is "Hard"

- It is **"Global"** and compiled into the kernel boot image.
- It **cannot be changed** by the user (unless the device is rooted and set to
  permissive).
- Failure results in a **"Silent" failure** in C++ (e.g., `open()` returns `-1` and
  `errno` is `EACCES`) and an `avc: denied` message in `dmesg`.

---

### Summary for Your AOSP Work

> If you write the code to check a permission but **forget the SELinux policy**,
> your service will crash or fail to find the `permission_service`.
>
> If you fix the SELinux policy but **forget the permission check**, any app on the
> phone could potentially trigger your custom hardware logic.
>
> **You need both for a secure, industry-grade implementation.**
