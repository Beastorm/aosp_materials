# How Does an Android App Work?
## A Complete & Updated Guide (2025)

Understanding how an Android app works requires tracing the complete journey — from
source code files in the IDE to a running application on the device. This involves
three major stages:

1. **Building the APK**
2. **Deploying the Application**
3. **Running the Application**

This guide also covers the latest changes and modern improvements introduced in
recent Android versions.

---

## Overview Flow
```
Source Code (Java/Kotlin)
        ↓
  Java Bytecode (.class)
        ↓
  Dalvik Bytecode (.dex)
        ↓
  APK / AAB Packaging
        ↓
  Signing & Alignment
        ↓
  ADB / Play Store Deployment
        ↓
  Zygote Forks New Process
        ↓
  DEX → OAT (Native Code via ART)
        ↓
  App Launches on Screen

```

## Step 1: Building the APK / AAB File

### 1.1 Code Compilation (Source → Java Bytecode)

Android apps are written in **Java** (`*.java`) or **Kotlin** (`*.kt`). Despite having
different syntax, both languages ultimately produce **Java bytecode** that can run on
a **JVM (Java Virtual Machine)**.

| Language | Compiler | Input | Output |
|----------|----------|-------|--------|
| **Java** | `javac` | `.java` files | `.class` files (Java bytecode) |
| **Kotlin** | `kotlinc` | `.kt` files | `.class` files (Java bytecode) |

```
┌─────────────────────┐       ┌─────────────────────┐
│  Source Code         │       │  Java Class Files    │
│  (.java / .kt)      │──────→│  (.class)            │
│                     │ javac/ │  Contains Java       │
│                     │kotlinc │  Bytecode            │
└─────────────────────┘       └─────────────────────┘

```
### 🆕 Latest Change: Kotlin-first Development
> - Google officially declared **Kotlin** as the preferred language for Android
>   development.
> - Kotlin offers features like **null safety**, **coroutines**, **extension functions**,
>   and **data classes**.
> - **Kotlin Multiplatform (KMP)** now allows sharing business logic between Android
>   and iOS.
> - **Kotlin Symbol Processing (KSP)** has replaced **KAPT** (Kotlin Annotation
>   Processing Tool) for faster annotation processing.

```
Old Flow:  Kotlin Code → KAPT → Annotation Processing → .class files
New Flow:  Kotlin Code → KSP  → Faster Processing     → .class files

```

### 1.2 Conversion into Dalvik Bytecodes (.class → .dex)

The `.class` files are not suitable for Android devices. Android uses its own bytecode
format called **Dalvik bytecode**.

The **DEX (Dalvik Executable)** compiler translates Java bytecode into Dalvik bytecode:

- The `dx` command ties up all `.class` files and all `.jar` files together.
- Produces a single `classes.dex` file written in **Dalvik bytecode** format.

```
┌─────────────────────┐       ┌─────────────────────┐
│  .class files        │       │  classes.dex         │
│  + .jar files        │──────→│  (Dalvik Bytecode)   │
│  (Java Bytecode)    │  dx    │  Single unified file │
└─────────────────────┘       └─────────────────────┘
```
#### Example: Seeing the Difference in Bytecodes

**Original Java Code:**
```
public int addTwoNumbers(int a, int b) {
    return a + b;
}
```
**Equivalent Java Bytecode:**
```
public int addTwoNumbers(int, int);
   Code:
      0: iload_1
      1: iload_2
      2: iadd
      3: ireturn
```      
**Equivalent Dalvik Bytecode:**
```
.method public addTwoNumbers(II)I
   .registers 4
   .param p1, "a"    # I
   .param p2, "b"    # I
   .line 6
   add-int v0, p1, p2
   return v0
.end method
```

> **Key Difference:** Java bytecode uses a **stack-based** architecture, while Dalvik
> bytecode uses a **register-based** architecture, making it more efficient for mobile
> devices with limited resources.

### 🆕 Latest Change: D8 and R8 Compiler
The old `dx` compiler has been completely replaced by modern tools:
 | **Tool** | **Purpose** | **Status** |
 |------|---------|--------|
 | **dx** | Old DEX compiler | ❌ Deprecated |
 | **D8** | New DEX compiler | ✅ Default since AGP 3.1 |
 | **R8** | DEX compiler + Shrinker + Optimizer + Obfuscator | ✅ Default since AGP 3.4 |


```
Old Flow:  .class → dx → classes.dex
           .class → ProGuard (shrinking) → dx → classes.dex

New Flow:  .class → R8 (compile + shrink + optimize + obfuscate) → classes.dex
```
**R8 does everything in a single step:**

- ✅ Compiles to DEX format (like D8)
- ✅ Shrinks code (removes unused classes/methods)
- ✅ Optimizes bytecode (inlining, dead code elimination)
- ✅ Obfuscates code (renames classes and methods)
- ✅ Significantly reduces APK size

#### R8 Compilation Modes:
```
Full Mode R8 (Default):
├── More aggressive optimizations
├── Smaller output size
└── Faster runtime performance

Compatibility Mode R8:
├── More conservative
└── For libraries with complex reflection usage
```

### 1.3 Generating the .apk / .aab File

At this stage, two major components are ready to be packaged:

- `classes.dex` — compiled application code
- **Resource files** — images, fonts, XML layouts, etc.

#### Resource Compilation

The **Android Asset Packaging Tool (AAPT2)** handles resources:

- Transforms all resource files into a single compiled resource unit.
- Generates the `R.java` file — a mapping of resource names to integer IDs.

> #### 🆕 Latest Change: AAPT2 Improvements
>
> | Feature | Old AAPT | New AAPT2 |
> |---------|----------|-----------|
> | **Compilation** | Single step | Incremental (compile then link) |
> | **Error detection** | At packaging time | Earlier during compile phase |
> | **Build speed** | Slower | Faster incremental builds |
> | **Resource visibility** | All public | Supports private resources |

The `apkbuilder` tool takes all components and compresses them into an
**Android Package** (`.apk`):

```
├──────────────────┤
│  Compiled         │     apkbuilder
```

### 🆕 1.4 Android App Bundle (AAB) — The Modern Standard

Google introduced **Android App Bundle** (`.aab`) as the new publishing format:

#### APK vs AAB

| Feature | APK | AAB |

- ✅ Support for **Play Feature Delivery** and **Play Asset Delivery**

### 1.5 App Signing & Alignment

The `.apk` or `.aab` must be **digitally signed** for distribution.

#### Signing Process

| Step | Tool | Purpose |
|------|------|---------|
| **1. Sign the APK** | `jarsigner` / `apksigner` | Digitally signs the file |
| **2. Byte Alignment** | `zipalign` | Aligns compressed parts on byte boundaries |

> #### 🆕 Latest Change: Signature Schemes
>
> Android has evolved through multiple APK Signature Schemes:
>
> | Scheme | Introduced | Details |
> |--------|------------|---------|
> | **v1** (JAR Signing) | Android 1.0 | Based on JAR signing; `jarsigner` tool |
> | **v2** (APK Signing) | Android 7.0 | Whole-file signing; faster verification |
> | **v3** (APK Signing) | Android 9.0 | Supports key rotation |
> | **v4** (APK Signing) | Android 11 | Required for Incremental APK Installation |

```
Modern Recommendation:
├── Use v1 + v2 + v3 for broad compatibility
├── v4 for Android 11+ incremental installs
└── Google Play App Signing (Google manages your key)

```
> #### 🆕 Latest Change: Google Play App Signing
>
> - Google now manages your **app signing key** on their secure servers.
> - You upload your AAB signed with an **upload key**.
> - Google **re-signs** the final APKs with the app signing key.
> - Protects against **key loss**.

```
Developer → Signs AAB with Upload Key → Google Play
                                              ↓
                              Google signs with App Signing Key
                                              ↓
                                    Delivered to Users
```

## Step 2: Deploy the Application

### 2.1 Establish the ADB Server

**ADB (Android Debug Bridge)** is a command-line tool for communication between
developer machine and device.

#### ADB Architecture:
```
┌─────────────────────────────────────────────────────┐
│                DEVELOPER'S MACHINE                  │
│                                                     │
│  ┌────────────┐         ┌────────────────┐          │
│  │ ADB Client │────────→│  ADB Server    │          │
│  │ (commands) │         │ (Port 5037)    │          │
│  └────────────┘         └───────┬────────┘          │
└─────────────────────────────────┼────────────────────┘
                                  │ USB / Wi-Fi
                                  ↓
                    ┌──────────────────────────┐
                    │     ANDROID DEVICE       │
                    │                          │
                    │  ┌────────────────────┐  │
                    │  │   ADB Daemon       │  │
                    │  │   (adbd)           │  │
                    │  └────────────────────┘  │
                    └──────────────────────────┘

```

#### How it works:

- **ADB Client** checks if the ADB Server process is already running.
- If not, it **starts the server** process.
- The server binds to local **TCP port 5037**.
- The server scans ports to **detect running devices**.
- When it finds an **ADB daemon** (`adbd`), it establishes a connection.
- The `adbd` enables: **app installation**, **debugging**, and **log collection**.

---

### 2.2 Transfer .apk File to the Device

The ADB command transfers the `.apk` file to the device's local filesystem, based on
the package name:
```
Package Name: com.example.sampleapp
APK Location: /data/app/com.example.sampleapp/
```
#### 🆕 Latest Change: Wireless ADB (Android 11+)
Android 11 introduced native **Wireless ADB** debugging:
```
Old Wireless ADB:
USB connect → adb tcpip 5555 → disconnect USB → adb connect <ip>:5555

New Wireless ADB (Android 11+):
Settings → Developer Options → Wireless Debugging → Pair Device
No USB cable required at all!
```

 | Method | Android Version | Notes |
 |--------|----------------|-------|
 | **USB ADB** | All versions | Most reliable |
 | **Wi-Fi ADB** (manual) | All versions | Requires initial USB |
 | **Wireless ADB** | Android 11+ | Fully wireless, no USB needed |

#### 🆕 Latest Change: Incremental APK Installation (Android 11+)
Large APKs can now be installed **incrementally** on Android 11+:

```
Traditional Install:
Full APK must be transferred → Then the app launches

Incremental Install:
Partial APK transferred → App launches immediately
Remaining data streams in the background
```
- Uses **APK Signature Scheme v4**.
- Dramatically reduces **install time** for large apps (like games).
- Requires: `adb install --incremental`

## Step 3: Run the Application

### 3.1 App Launch Request (Zygote Process)

The **Zygote** process is the parent of **ALL** Android apps.

```
┌──────────────────────────────────────────┐
│              ZYGOTE PROCESS              │
│                                          │
│  Preloaded:                              │
│  ├── Core Android Libraries              │
│  ├── Common Classes                      │
│  ├── Resources Framework                 │
│  └── Runtime Environment                 │
│                                          │
│         fork()        fork()             │
│           ↓             ↓                │
│     ┌─────────┐   ┌─────────┐           │
│     │  App 1  │   │  App 2  │           │
│     │ Process │   │ Process │           │
│     └─────────┘   └─────────┘           │
└──────────────────────────────────────────┘
```

#### 🆕 Latest Change: Zygote64 and Zygote32

Modern Android devices run two Zygote processes:
| Process | Architecture | Purpose |
|---------|-------------|---------|
| **zygote** | 32-bit | Forks 32-bit app processes |
| **zygote64** | 64-bit | Forks 64-bit app processes |

 **Note:** Google mandated 64-bit support for all apps on Google Play. As of
**Aug 2024**, apps must provide 64-bit native libraries.

#### 🆕 Latest Change: App Startup Improvements
```
Traditional Cold Start:
Zygote fork → Load classes → Initialize app → Launch activity

Modern Optimizations:
├── Baseline Profiles (pre-compile hot code paths)
├── Startup Profiles (optimize frequently used classes)
└── App Startup Library (control initialization order)

```

**Launch Sequence:**
```
User taps app icon
        ↓
Launcher sends intent to ActivityManagerService (AMS)
        ↓
AMS checks if process exists
        ↓
AMS requests Zygote to fork (via socket)
        ↓
Zygote fork() creates new process
        ↓
Process inherits preloaded libraries & resources
        ↓
ActivityThread.main() is called
        ↓
Application class is initialized
        ↓
Launcher Activity's onCreate() is called
        ↓
UI rendered via Choreographer (in sync with VSync)
        ↓
App appears on screen

```

### 3.2 Conversion of .dex Code to Native OAT Format

When an app is installed, Android optimizes it by generating an **OAT
(Ahead-Of-Time)** file.

#### The Evolution of Optimization

| Era | Tool | Input | Output | Method |
|-----|------|-------|--------|--------|
| **Old** (Pre-KitKat) | `dexopt` | `.dex` | `.odex` | Optimized bytecode |
| **ART introduced** (Lollipop) | `dex2oat` | `.dex` | `.oat` | AOT compilation |
| **Modern ART** (Nougat+) | `dex2oat` | `.dex` | `.oat` + `.vdex` | Hybrid AOT + JIT |

```
┌───────────────┐     Extract      ┌───────────────┐
│   app.apk     │────────────────→ │  classes.dex  │
└───────────────┘                  └───────┬───────┘
                                           │
                                     dex2oat tool
                                     (AOT Compilation)
                                           │
                                           ↓
                                  ┌───────────────────┐
                                  │    OAT File        │
                                  │  (Native Machine   │
                                  │   Code in ELF      │
                                  │   Format)           │
                                  └───────────────────┘
                                           │
                                           ↓
                                  Mapped into app's
                                  memory space

Storage Location: /data/dalvik-cache/

```

### 🆕 3.3 Modern ART: Hybrid Compilation (AOT + JIT + Profile-Guided)

The biggest evolution in how Android runs code is the shift from pure AOT to a
sophisticated **hybrid model**:

#### The Problem with Pure AOT

- Installing apps took **too long** (entire app compiled on install).
- Compiled code for **rarely-used methods** wasted storage.
- **OTA (Over-The-Air)** updates required full recompilation.

#### The Solution: Hybrid AOT + JIT + Profile-Guided Compilation
```
┌──────────────────────────────────────────────────────────────┐
│              MODERN ART COMPILATION PIPELINE                 │
│                                                              │
│  App Install                                                 │
│      │                                                       │
│      ↓                                                       │
│  ┌─────────────────┐                                         │
│  │ DEX Verification│  → Verify bytecode correctness          │
│  │ (No full AOT)   │  → App installs FAST                    │
│  └────────┬────────┘                                         │
│           │                                                  │
│      First Run                                               │
│           ↓                                                  │
│  ┌─────────────────┐                                         │
│  │   JIT Compiler  │  → Compiles HOT methods at runtime      │
│  │  (Just-in-Time) │  → Records which methods are used       │
│  └────────┬────────┘  → Saves profile data                   │
│           │                                                  │
│      Device Idle / Charging                                  │
│           ↓                                                  │
│  ┌─────────────────┐                                         │
│  │  AOT Compiler   │  → Compiles only HOT methods            │
│  │ (Profile-Guided)│  → Based on collected JIT profile       │
│  └────────┬────────┘  → Stored as .oat file                  │
│           │                                                  │
│      Subsequent Runs                                         │
│           ↓                                                  │
│  ┌─────────────────┐                                         │
│  │ AOT + JIT Mixed │  → Pre-compiled code runs fast          │
│  │   Execution     │  → New/cold code uses JIT               │
│  └─────────────────┘                                         │
└──────────────────────────────────────────────────────────────┘
```

#### Compilation Filter Options

| Filter | Description | When Used |
|--------|-------------|-----------|
| **verify** | Only verify DEX, no compilation | Fresh install |
| **quicken** | Optimize some instructions | Old devices |
| **speed-profile** | AOT compile hot code from profile | After JIT profiling |
| **speed** | Full AOT compile everything | System apps |
| **everything** | Compile all methods | Testing/debugging |

### 🆕 3.4 Baseline Profiles — The Game Changer

Introduced in **Android 9** and popularized via **Jetpack**, Baseline Profiles
revolutionize startup performance:

#### What are Baseline Profiles?

- A list of **critical classes and methods** that should be pre-compiled by ART.
- **Shipped inside the APK/AAB** by the developer.
- Google Play uses them to **pre-compile the app** before the user even launches it.
```
Traditional Flow (without Baseline Profiles):
Install → First Launch (JIT, slow) → Subsequent launches improve gradually

With Baseline Profiles:
Install → Google Play pre-compiles critical paths → First Launch is FAST
```

**How to create a Baseline Profile:**
```
// build.gradle.kts
plugins {
    id("androidx.baselineprofile")
}

// BaselineProfileGenerator.kt
@ExperimentalBaselineProfilesApi
class BaselineProfileGenerator {
    @get:Rule
    val rule = BaselineProfileRule()

    @Test
    fun startup() = rule.collectBaselineProfile(
        packageName = "com.example.app"
    ) {
        pressHome()
        startActivityAndWait()
    }
}
```
```
Generated Profile:
HSPLcom/example/MainActivity;->onCreate(Bundle)V
HSPLcom/example/ui/HomeScreen;->Content(Modifier)V
...

H = Hot method (JIT compiled)
S = Startup method
P = Post startup method
L = Class/method path
```

#### Impact of Baseline Profiles

| Metric | Without | With Baseline Profile |
|--------|---------|-----------------------|
| **Cold startup** | Baseline | Up to **40% faster** |
| **First frame render** | Baseline | Significantly faster |
| **Jank on first use** | Common | Greatly reduced |

### 🆕 3.5 VDEX Files — Verification Optimization

Modern Android also generates `.vdex` (**Verified DEX**) files alongside `.oat` files:
```
/data/app/<package>/
 ├── base.apk
 ├── oat/
 │    ├── arm64/
 │    │    ├── base.odex    → Compiled native code (OAT)
 │    │    └── base.vdex    → Pre-verified DEX bytecode
 │    └── arm/
 │         ├── base.odex
 │         └── base.vdex

 ```

 | File | Purpose | Benefit |
|------|---------|---------|
| **`.oat` / `.odex`** | Native compiled code | Fast execution |
| **`.vdex`** | Pre-verified DEX | Skip re-verification on next launch |

- **VDEX** stores the original DEX data in a verified form.
- On subsequent launches, Android **skips DEX verification** (expensive step).
- After OTA updates, ART can use VDEX to **re-verify faster** without full
  recompilation.

### 🆕 Jetpack Compose — Modern UI Rendering

Traditional Android used **XML-based layouts**. Modern Android uses **Jetpack Compose**:

```
Traditional XML Flow:
XML Layout → LayoutInflater → View objects → rendered on screen

Jetpack Compose Flow:
Composable Functions → Compose Compiler → Optimized UI nodes → rendered on screen
```
```
// Traditional XML-based approach
// activity_main.xml + MainActivity.kt

// Modern Jetpack Compose approach
@Composable
fun HomeScreen() {
    Column(
        modifier = Modifier.fillMaxSize(),
        verticalArrangement = Arrangement.Center
    ) {
        Text(text = "Hello, Android!")
        Button(onClick = { /* action */ }) {
            Text("Click Me")
        }
    }
}
```

**Compose Compilation Pipeline:**
```
@Composable functions (Kotlin)
        ↓
Compose Compiler Plugin (transforms composable code)
        ↓
Generated Kotlin code with $composer parameters
        ↓
Kotlin compiler → .class → D8/R8 → .dex
        ↓
ART executes optimized UI code
```

### 🆕 Modern Garbage Collection in ART

ART uses **Concurrent Copying (CC)** Garbage Collector:

| GC Type | Old (Dalvik) | New ART |
|---------|-------------|---------|
| **Method** | Stop-the-world | Concurrent (app keeps running) |
| **Algorithm** | Mark-and-sweep | Copying GC |
| **Pause time** | Long pauses | Minimal pauses |
| **Impact on app** | Visible jank | Near-invisible |

```
Concurrent Copying GC:
├── App continues running during GC
├── Objects copied to new memory space while app runs
├── Only brief pause at start and end
└── Results in smoother 60fps/90fps/120fps performance
```

|-------|-------------|----------------|--------|
| **Compilation** | Source → Java Bytecode | `javac` / `kotlinc` + KSP | `.class` files |

| **Process Creation** | Fork new process | Zygote64 | New 64-bit app process |
| **DEX Verification** | Verify bytecode | ART verifier | `.vdex` file |
| **JIT Compilation** | Compile hot methods at runtime | ART JIT | Profile data |
| **AOT Compilation** | Pre-compile hot paths | `dex2oat` (Profile-guided) | `.oat` file (ELF) |
| **Baseline Profiles** | Pre-compile before first launch | Jetpack Macrobenchmark | Faster cold start |
| **GC** | Memory management | Concurrent Copying GC | Smooth performance |
| **Launch** | Start Activity lifecycle | Android Runtime + AMS | App visible on screen |

# Hybrid AOT + JIT + Profile-Guided Compilation in Android ART

## Introduction

When Android first launched, it used the **Dalvik Virtual Machine** with a simple
interpreter. Over the years, Android's runtime has evolved dramatically to solve
real-world performance problems. Today, Android uses a sophisticated **three-pronged
compilation strategy** that combines:

1. **AOT (Ahead-Of-Time) Compilation**
2. **JIT (Just-In-Time) Compilation**
3. **Profile-Guided Optimization (PGO)**

Understanding why this hybrid approach exists requires understanding the problems
each technique solves.

---

## The Evolution Timeline

```
Android 1.0 - 4.3 (Dalvik)
        │
        │  Problem: Slow execution (pure interpretation)
        ↓
Android 4.4 KitKat (ART Preview)
        │
        │  Solution: Introduced AOT compilation (dex2oat)
        ↓
Android 5.0 - 6.0 Lollipop/Marshmallow (Pure AOT)
        │
        │  Problem: Slow installs, large storage, slow OTA updates
        ↓
Android 7.0 Nougat (Hybrid JIT + AOT)
        │
        │  Solution: JIT compiler + Profile-guided AOT
        ↓
Android 9.0+ Pie onwards (Refined Hybrid)
        │
        │  Addition: Baseline Profiles, Cloud Profiles
        ↓
Android 12+ (Further Optimizations)
        │
        │  Addition: ART as updatable module via Play Store
        ↓
Android 14-15 (2024-2025)
        │
        │  Addition: More aggressive optimizations, better
        │  profile-guided compilation, improved GC
        ↓
     Today: Sophisticated Hybrid System

```

## Part 1: Understanding Each Compilation Strategy

### 1.1 Pure Interpretation (Dalvik Era — Android 1.0 to 4.3)

Before any compilation strategy, Dalvik simply **interpreted** bytecode:

```
┌─────────────────────────────────────────────────────┐
│                 INTERPRETATION                      │
│                                                     │
│  DEX Bytecode                                       │
│  ┌──────────────┐                                   │
│  │ instruction1 │──→ Interpreter reads instruction  │
│  │ instruction2 │──→ Interpreter executes it        │
│  │ instruction3 │──→ Interpreter reads next         │
│  │ instruction4 │──→ And so on...                   │
│  └──────────────┘                                   │
│                                                     │
│  Every. Single. Instruction.                        │
│  Interpreted at runtime. Every time.                │
│                                                     │
│  ❌ Very slow execution                             │
│  ✅ Fast startup (no compilation needed)            │
│  ✅ Low memory usage                                │
└─────────────────────────────────────────────────────┘
```

> **Real-world analogy:**
> Imagine reading a recipe in French every single time you cook, even if you cook the
> same dish every day — translating word by word, each time.

---

### 1.2 AOT — Ahead-Of-Time Compilation

#### What is AOT?

AOT compilation means translating the **entire DEX bytecode** into native machine
code **BEFORE** the app runs — typically at **install time**.

```
┌─────────────────────────────────────────────────────────┐
│              AOT COMPILATION PROCESS                    │
│                                                         │
│  AT INSTALL TIME:                                       │
│                                                         │
│  DEX Bytecode ──(dex2oat)──→ Native Machine Code        │
│  (classes.dex)               (.oat file / ELF format)  │
│                                                         │
│  AT RUNTIME:                                            │
│                                                         │
│  App launches → Loads pre-compiled .oat file            │
│              → Executes native code directly            │
│              → No translation needed at runtime         │
│                                                         │
└─────────────────────────────────────────────────────────┘

```

> **Real-world analogy:**
> Before cooking, you translate the entire French recipe into English, write it down,
> and then follow the English version every time. Fast cooking, but the translation
> takes time upfront.

#### How dex2oat Works:

```
dex2oat tool takes:
├── Input:  classes.dex (Dalvik bytecode)
├── Target: Device CPU architecture (arm64, x86, etc.)
└── Output: .oat file (native ELF binary)

Inside the .oat file:
┌─────────────────────────────────┐
│           OAT File              │
│                                 │
│  ┌─────────────────────────┐   │
│  │  OAT Header             │   │
│  │  (metadata, version)    │   │
│  ├─────────────────────────┤   │
│  │  DEX Files              │   │
│  │  (original DEX data)    │   │
│  ├─────────────────────────┤   │
│  │  OAT Classes            │   │
│  │  (compiled native code) │   │
│  ├─────────────────────────┤   │
│  │  OAT Methods            │   │
│  │  (method entry points)  │   │
│  └─────────────────────────┘   │
└─────────────────────────────────┘

```

**Pure AOT Advantages & Problems:**
```
✅ ADVANTAGES of Pure AOT:
├── Extremely fast app execution
├── No compilation overhead at runtime
├── Consistent performance from first launch
└── Predictable behavior

❌ PROBLEMS with Pure AOT (Android 5.0-6.0):
├── App install takes VERY long (compiling entire app)
│     Example: Large app could take 2-5 minutes to install
│
├── OTA (Over-The-Air) system updates take forever
│     "Optimizing apps 1 of 150..." (Remember this screen?)
│     This happened because ALL apps needed recompilation
│
├── Compiled code takes significant storage space
│     .oat files are much larger than .dex files
│     Compiling unused methods wastes space
│
└── Compiles EVERYTHING including rarely-used code
      90% of code might be rarely used
      But AOT compiles 100% of it

```      
### 1.3 JIT — Just-In-Time Compilation

#### What is JIT?

JIT compilation means compiling bytecode to native code **AT RUNTIME**, but only
for code that is **actually being used**.

```
┌─────────────────────────────────────────────────────────┐
│              JIT COMPILATION PROCESS                    │
│                                                         │
│  AT INSTALL TIME:                                       │
│  DEX bytecode is only VERIFIED (not compiled)           │
│  App installs instantly! ✅                             │
│                                                         │
│  AT RUNTIME (First execution):                          │
│                                                         │
│  Method called → Interpreter executes it               │
│       ↓ (if called enough times - "HOT")               │
│  JIT Compiler kicks in                                  │
│       ↓                                                 │
│  Compiles the HOT method to native code                 │
│       ↓                                                 │
│  Caches the compiled native code in JIT Code Cache      │
│       ↓                                                 │
│  Next call → Uses cached native code (FAST!)            │
│                                                         │
└─────────────────────────────────────────────────────────┘

```

> **Real-world analogy:**
> You cook using the French recipe. But for dishes you make repeatedly, you eventually
> memorize them in English. First few times are slow (translation), but after that,
> it's fast (from memory).

#### JIT Hot Method Detection:
```
Method Execution Tracking:

methodA() called 1 time    → Interpreted (cold)
methodA() called 5 times   → Still interpreted
methodA() called 10 times  → Getting warmer...
methodA() called 50 times  → JIT THRESHOLD REACHED!
                            → JIT compiles methodA()
                            → Stored in JIT Code Cache
methodA() called 51+ times → Uses compiled native code ⚡

```

**JIT Code Cache:**
```
┌──────────────────────────────────────────┐
│            JIT CODE CACHE               │
│                                          │
│  In-memory cache (not persisted to disk) │
│                                          │
│  ┌─────────────┐  ┌─────────────────┐   │
│  │ methodA()   │  │   methodB()     │   │
│  │ native code │  │   native code   │   │
│  └─────────────┘  └─────────────────┘   │
│                                          │
│  ┌─────────────┐  ┌─────────────────┐   │
│  │ methodC()   │  │   methodD()     │   │
│  │ native code │  │   native code   │   │
│  └─────────────┘  └─────────────────┘   │
│                                          │
│  Default size: 64KB (interpreter code)   │
│               128KB (compiler code)      │
│                                          │
│  ⚠️ Cleared when app process is killed  │
└──────────────────────────────────────────┘
```

**JIT Advantages & Problems:**
```
✅ ADVANTAGES of JIT:
├── Fast app install (no compilation at install time)
├── Fast OTA updates (no "Optimizing apps" wait)
├── Only compiles code that's actually used
├── Smaller storage footprint
└── Adapts to actual usage patterns

❌ PROBLEMS with Pure JIT:
├── Slower execution at first launch (interpretation phase)
├── JIT compilation takes CPU time at runtime
│     Can cause jank/stutter during first use
├── JIT code cache is lost when app is killed
│     Every cold start begins from scratch
├── Higher battery usage (compilation at runtime)
└── Unpredictable performance (depends on warmup)

```
## Part 2: The Hybrid System — How AOT + JIT Work Together

**Android 7.0 (Nougat)** introduced the **Hybrid Compilation Model** that combines
the best of both worlds:

### 2.1 The Three-Phase Approach
```
╔══════════════════════════════════════════════════════════════════╗
║              HYBRID COMPILATION - FULL LIFECYCLE                ║
╠══════════════════════════════════════════════════════════════════╣
║                                                                  ║
║  PHASE 1: INSTALLATION                                          ║
║  ─────────────────────                                          ║
║  app.apk installed                                              ║
║       ↓                                                         ║
║  ART verifies DEX bytecode (correctness check)                  ║
║       ↓                                                         ║
║  Generates .vdex file (pre-verified DEX)                        ║
║       ↓                                                         ║
║  NO full compilation → App installs in seconds ✅               ║
║                                                                  ║
╠══════════════════════════════════════════════════════════════════╣
║                                                                  ║
║  PHASE 2: FIRST RUNS (JIT + Profiling)                          ║
║  ─────────────────────────────────────                          ║
║  App launches → ART uses interpreter + JIT                      ║
║       ↓                                                         ║
║  JIT monitors method call frequency                             ║
║       ↓                                                         ║
║  HOT methods → JIT compiles them → JIT Code Cache              ║
║       ↓                                                         ║
║  Profile Saver records which methods are HOT                    ║
║       ↓                                                         ║
║  Saves profile data to disk:                                    ║
║  /data/misc/profiles/cur/0/<package>/primary.prof               ║
║                                                                  ║
╠══════════════════════════════════════════════════════════════════╣
║                                                                  ║
║  PHASE 3: BACKGROUND OPTIMIZATION (Profile-Guided AOT)          ║
║  ──────────────────────────────────────────────────────         ║
║  Device is idle + charging                                      ║
║       ↓                                                         ║
║  Background dexopt service runs                                 ║
║       ↓                                                         ║
║  Reads profile data (which methods are HOT)                     ║
║       ↓                                                         ║
║  dex2oat compiles ONLY hot methods → .odex/.oat file            ║
║       ↓                                                         ║
║  Subsequent app launches use pre-compiled native code           ║
║       ↓                                                         ║
║  Fast execution with no compilation overhead ✅                 ║
║                                                                  ║
╚══════════════════════════════════════════════════════════════════╝
```

### 2.2 Detailed Runtime Flow
```
App Launch #1 (Cold Start - No Profile):

User opens app
      ↓
ART loads .vdex (pre-verified DEX)
      ↓
Interpreter executes code
      ↓
JIT monitors execution:

  onCreate() called →  [████████░░] 8 calls  → Warming up
  onDraw() called →   [██████████] HOT! → JIT compiles
  onClick() called →  [████░░░░░░] 4 calls  → Still cold
  loadData() called → [██████████] HOT! → JIT compiles

JIT Code Cache now has: onDraw(), loadData() compiled
Profile Saver notes: onDraw(), loadData() are HOT

      ↓
App runs (mix of interpreted + JIT-compiled code)
      ↓
User closes app
      ↓
Profile data saved to disk
```
```
Overnight (Device idle + charging):

Background dexopt service wakes up
      ↓
Reads profile: "onDraw() and loadData() are HOT"
      ↓
dex2oat --compiler-filter=speed-profile
      ↓
Compiles ONLY: onDraw(), loadData() → native code in .odex
      ↓
Stores in: /data/app/<package>/oat/arm64/base.odex
```
```
App Launch #2+ (Optimized):

User opens app
      ↓
ART loads .vdex + .odex
      ↓
Pre-compiled methods (onDraw, loadData) → execute as native code ⚡
Non-compiled methods → JIT as needed
      ↓
Much faster execution, less jank, better battery life
```

## Part 3: Profile-Guided Optimization (PGO) in Detail

### 3.1 What is Profile-Guided Optimization?

**Profile-Guided Optimization** means using **real usage data** to make smarter
compilation decisions:

```
Traditional AOT:                    Profile-Guided AOT:
"Compile everything"                "Compile only what matters"

┌──────────────────┐               ┌──────────────────┐
│ Method A (HOT)   │ ← compiled    │ Method A (HOT)   │ ← compiled ✅
│ Method B (HOT)   │ ← compiled    │ Method B (HOT)   │ ← compiled ✅
│ Method C (COLD)  │ ← compiled    │ Method C (COLD)  │ ← NOT compiled ❌
│ Method D (COLD)  │ ← compiled    │ Method D (COLD)  │ ← NOT compiled ❌
│ Method E (COLD)  │ ← compiled    │ Method E (COLD)  │ ← NOT compiled ❌
│ Method F (HOT)   │ ← compiled    │ Method F (HOT)   │ ← compiled ✅
│ Method G (COLD)  │ ← compiled    │ Method G (COLD)  │ ← NOT compiled ❌
└──────────────────┘               └──────────────────┘

Result: Large .oat file             Result: Small .oat file
        Wasted storage                      Only what's needed
        Slow install                        Fast install

```        
### 3.2 Profile Data Structure
```
Profile File Location:
/data/misc/profiles/cur/0/<package-name>/primary.prof

Profile File Contains:
┌─────────────────────────────────────────────────────┐
│                  PRIMARY.PROF                       │
│                                                     │
│  Format: Binary (not human-readable directly)       │
│                                                     │
│  Contains:                                          │
│  ┌───────────────────────────────────────────────┐ │
│  │  HOT METHODS                                  │ │
│  │  ├── com.example.MainActivity.onCreate()      │ │
│  │  ├── com.example.ui.HomeScreen.render()       │ │
│  │  ├── com.example.data.Repository.loadData()   │ │
│  │  └── ...                                      │ │
│  ├───────────────────────────────────────────────┤ │
│  │  STARTUP CLASSES                              │ │
│  │  ├── com.example.MainActivity                 │ │
│  │  ├── com.example.Application                  │ │
│  │  ├── com.example.di.AppModule                 │ │
│  │  └── ...                                      │ │
│  ├───────────────────────────────────────────────┤ │
│  │  POST-STARTUP CLASSES                         │ │
│  │  ├── com.example.ui.SettingsScreen            │ │
│  │  └── ...                                      │ │
│  └───────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────┘

```

```
Profile Collection Pipeline:

│  └── Saves to primary.prof                                  │
│       ↓                                                     │

│  ├── Reads primary.prof                                     │
```

```
│                 │                                          │
```

## Part 4: Baseline Profiles — Developer-Controlled PGO

### 4.1 The Problem Baseline Profiles Solve

```
WITHOUT Baseline Profiles:

Day 1 (Install):
  App installs → Only DEX verification → No optimization
  First launch: SLOW (cold, interpreted) ❌
  User frustrated, might uninstall

Day 2-3 (JIT Profiling):
  App getting warmer, JIT compiling hot methods

Night (Background AOT):
  dexopt compiles profile → .odex generated

Day 4+:
  App finally runs smoothly ✅
  But user already formed a bad impression

WITH Baseline Profiles:

Day 1 (Install via Google Play):
  AAB installed → Play Store pre-compiles using embedded profile
  First launch: FAST (critical paths pre-compiled) ✅
  User has great first experience


```  

### 4.2 How Baseline Profiles Work
```
DEVELOPER SIDE:
┌─────────────────────────────────────────────────────────┐
│                                                         │
│  Developer writes Baseline Profile Generator test       │
│       ↓                                                 │
│  Test runs on real device via Macrobenchmark library     │
│       ↓                                                 │
│  Captures which classes/methods are used during:        │
│  ├── App startup                                        │
│  ├── Critical user journeys                             │
│  └── Key interactions                                   │
│       ↓                                                 │
│  Generates: baseline-prof.txt                           │
│  Location: src/main/baseline-prof.txt                   │
│       ↓                                                 │
│  File is included in AAB/APK at build time              │
│                                                         │
└─────────────────────────────────────────────────────────┘

GOOGLE PLAY SIDE:
┌─────────────────────────────────────────────────────────┐
│                                                         │
│  Developer uploads AAB (contains baseline-prof.txt)     │
│       ↓                                                 │
│  Google Play reads the Baseline Profile                 │
│       ↓                                                 │
```

# VDEX (Verified DEX) — Complete Detailed Guide

## What is VDEX?

**VDEX (Verified DEX)** is a file format introduced in **Android 8.0 (Oreo)** that
stores **pre-verified DEX bytecode** alongside additional metadata to speed up the
application loading and verification process.

Before VDEX existed, every time an app was updated or the system rebooted, Android
had to **re-verify the DEX bytecode from scratch** — a costly and time-consuming
operation. VDEX was introduced to **eliminate this redundant verification work**.

```
Without VDEX (Before Android 8.0):

App Install/Update
      ↓
DEX Verification (expensive)
      ↓
App Runs
      ↓
App Update / OTA Update
      ↓
DEX Verification AGAIN (from scratch) ❌ wasteful
      ↓
App Runs


With VDEX (Android 8.0+):

App Install/Update
      ↓
DEX Verification (expensive) — done ONCE
      ↓
Results saved to .vdex file ✅
      ↓
App Runs
      ↓
App Update / OTA Update
      ↓
ART reads .vdex → Skips re-verification ✅ fast!
      ↓
App Runs
```

### Why Was VDEX Introduced?
#### The Core Problem
```
DEX Bytecode Verification is EXPENSIVE:

What verification checks:
├── Type safety (correct types used everywhere)
├── Control flow integrity (no illegal jumps)
├── Register usage (correct register allocation)
├── Method signatures (correct method calls)
├── Access rules (private/public/protected respected)
├── Null safety checks
└── Array bounds validity

Cost of verification:
├── CPU intensive
├── Time consuming (hundreds of milliseconds for large apps)
├── Had to be repeated unnecessarily
└── Caused slow app installs and OTA updates
```

### Problems VDEX Solves:
```
┌───────────────────────────────────────────────────────────┐
│              PROBLEMS VDEX SOLVES                        │
│                                                           │
│  Problem 1: Redundant Verification                        │
│  ─────────────────────────────────                        │
│  Before: Verify DEX every time anything changes           │
│  After:  Verify once, store result, reuse later           │
│                                                           │
│  Problem 2: Slow OTA Updates                              │
│  ──────────────────────────                               │
│  Before: "Optimizing app 1 of 150..." (long wait)         │
│  After:  Use VDEX to speed up re-verification             │
│                                                           │
│  Problem 3: App Update Re-verification                    │
│  ────────────────────────────────────                     │
│  Before: Full re-verification after every update          │
│  After:  Incremental re-verification using VDEX           │
│                                                           │
│  Problem 4: Storage of Original DEX                       │
│  ────────────────────────────────────                     │
│  Before: Original DEX stored inside .oat file             │
│  After:  DEX stored in .vdex, .oat references it          │
│          Cleaner separation of concerns                   │
└───────────────────────────────────────────────────────────┘
```
### VDEX File Location on Device
```

/data/
 └── app/
      └── ~~randomstring==/

                ├── base.apk                    ← The APK
                └── oat/
```


## VDEX vs ODEX vs OAT — Understanding the Difference
```
┌─────────────────────────────────────────────────────────────────┐
│                  FILE FORMAT COMPARISON                         │
├──────────────┬──────────────────────────────────────────────────┤
│              │                                                  │
│   .dex       │  • Original Dalvik bytecode                      │
│              │  • Inside the APK (classes.dex)                  │
│              │  • Not executable directly by ART                │
│              │  • Platform-independent                          │
│              │                                                  │
├──────────────┼──────────────────────────────────────────────────┤
│              │                                                  │
│   .vdex      │  • Contains original DEX data                    │
│              │  • Pre-verification results                      │
│              │  • Verifier dependency information               │
│              │  • Quickening info (Android 8-11)               │
│              │  • Platform-independent (mostly)                 │
│              │  • Enables skipping re-verification             │
│              │                                                  │
├──────────────┼──────────────────────────────────────────────────┤
│              │                                                  │
│   .odex      │  • "Optimized DEX"                               │
│   (modern)   │  • Actually an OAT file in modern Android        │
│              │  • Contains AOT-compiled native machine code     │
│              │  • Platform-specific (arm64, x86, etc.)          │
│              │  • References DEX data in .vdex file             │
│              │  • ELF format                                    │
│              │                                                  │
├──────────────┼──────────────────────────────────────────────────┤
│              │                                                  │
│   .oat       │  • Same as modern .odex essentially              │
│              │  • Used for boot image and system apps           │
│              │  • Contains native compiled code                 │
│              │  • ELF binary format                             │
│              │  • Platform-specific                             │
│              │                                                  │
└──────────────┴──────────────────────────────────────────────────┘
```

### Relationship Between Files:
```
┌─────────────────────────────────────────────────────────────┐
│              HOW THE FILES RELATE TO EACH OTHER             │
│                                                             │
```

### Compact DEX (CDEX) Inside VDEX
#### Android 10 introduced Compact DEX format stored inside VDEX to reduce size:
```
Regular DEX vs Compact DEX:

Regular DEX (inside APK):
┌─────────────────────────────────────┐
│  Full DEX file                      │
│  ├── String table (full strings)    │
│  ├── Type table                     │
│  ├── Proto table                    │
│  ├── Field table                    │
│  ├── Method table                   │
│  └── Code items (full bytecode)     │
│  Size: 100% (baseline)              │
└─────────────────────────────────────┘

Compact DEX (inside VDEX):
┌─────────────────────────────────────┐
│  Compact DEX file                   │
│  ├── Shared data section            │
│  │   (shared between multiple DEX) │
│  ├── Deduplicated strings           │
│  ├── Deduplicated code items        │
│  └── Optimized data layout          │
│  Size: ~5-15% smaller than DEX     │
└─────────────────────────────────────┘

Multiple DEX files (MultiDex apps):
Without Compact DEX:
  classes.dex  → own string table
  classes2.dex → own string table (DUPLICATES!)
  classes3.dex → own string table (DUPLICATES!)

With Compact DEX in VDEX:
  Shared data section → strings shared among all DEX files
  classes.cdex  → references shared data
  classes2.cdex → references shared data (no duplication!)
  classes3.cdex → references shared data (no duplication!)
```  

## VDEX and Boot Image
#### VDEX is not just for user apps — it's also used for the Android boot image (core framework classes):
```
Boot Image VDEX:

/apex/com.android.art/javalib/
 ├── boot.art          ← Heap snapshot of pre-initialized classes
 ├── boot.oat          ← Compiled native code for boot classes
 └── boot.vdex         ← Verified DEX for boot classes

Boot VDEX contains:
├── java.lang.*        (String, Object, Thread, etc.)
├── java.util.*        (ArrayList, HashMap, etc.)
├── android.app.*      (Activity, Service, etc.)
├── android.view.*     (View, ViewGroup, etc.)
└── ... all core framework classes

Why this matters:
• All app verification can reference boot VDEX
• Boot classes considered pre-verified
• Apps don't need to re-verify framework classes
• Massive speedup for all app verification

```

## VDEX Validation Process
When ART loads a VDEX file, it performs **validation checks**:
```
VDEX Validation Checks:

┌─────────────────────────────────────────────────────────┐
│                 VDEX VALIDATION                         │
│                                                         │
│  Check 1: Magic Number                                  │
│  ─────────────────────                                  │
│  First 4 bytes must be: {'v', 'd', 'e', 'x'}           │
│  If wrong → VDEX is corrupt or wrong format             │
│                                                         │
│  Check 2: Version Compatibility                         │
│  ──────────────────────────────                         │
│  VDEX version must match current ART version            │
│  If mismatch → Re-generate VDEX                         │
│                                                         │
│  Check 3: DEX Checksum Validation                       │
│  ─────────────────────────────────                      │
│  Checksum in VDEX header == Checksum of APK's DEX?     │
│  If match → DEX unchanged, skip verification ✅         │
│  If mismatch → DEX changed, re-verify ⚠️               │
│                                                         │
│  Check 4: Verifier Dependency Validation                │
│  ────────────────────────────────────────               │
│  Are all recorded dependencies still valid?             │
│  ├── Is the boot classpath the same?                    │
│  ├── Do framework classes still have same checksums?    │
│  └── Are all referenced classes still accessible?       │
│  If all valid → Use cached results ✅                   │
│  If any invalid → Re-verify affected methods ⚠️         │
│                                                         │
│  Check 5: File Integrity                                │
│  ───────────────────────                                │
│  VDEX file not truncated or corrupted                   │
│  If corrupt → Delete and re-generate                    │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

## Key Takeaways
```
✅ VDEX = Verified DEX — stores pre-verified DEX bytecode
           and verification metadata

✅ Introduced in Android 8.0 (Oreo) to solve redundant
   re-verification problem

✅ Contains three main sections:
   ├── DEX Section      (original DEX data)
   ├── Verifier Deps    (what was verified & dependencies)
   └── Quickening Info  (optimized opcodes, removed in Android 12)

✅ Enables SKIPPING full DEX verification on subsequent launches
   → Faster app startup

✅ Tracks verifier DEPENDENCIES on framework classes
   → Smart incremental re-verification after OTA updates

✅ Works alongside .odex files:
   ├── .vdex = DEX data + verification info
   └── .odex = native compiled code (references .vdex)

✅ Compact DEX (Android 10+) reduces VDEX size by
   deduplicating shared data in MultiDex apps

✅ Also used for the Android boot image (framework classes)
   → All app verification can benefit from pre-verified
     framework classes

✅ Continuously improved across Android versions
   up to latest Android 14/15

```

# Complete Android App Flow with NDK (C/C++ Native Code)

## Introduction

When an Android app includes C/C++ native code via the **NDK (Native Development Kit)**,
the build, packaging, deployment, and runtime flow becomes significantly more complex.
The app now has **two parallel compilation pipelines** — one for Java/Kotlin code and
one for C/C++ code — that eventually merge together.

### 1.2 Pipeline 2 — C/C++ Native Compilation (NEW)

This is the entirely new pipeline that runs in **parallel** with the Java/Kotlin
pipeline:
```
┌──────────────────────────────────────────────────────────────┐
│           PIPELINE 2: C/C++ Native Compilation               │
│                                                              │
│  Step 1: CMake Configuration                                 │
│  ───────────────────────────                                 │
│  CMakeLists.txt read by CMake                                │
│       │                                                      │
│       ↓                                                      │
│  CMake generates Makefiles for each target ABI               │
│  ┌──────────────┐                                           │
│  │  arm64-v8a   │ ← 64-bit ARM (most modern phones)        │
│  │  armeabi-v7a │ ← 32-bit ARM (older phones)              │
│  │  x86_64      │ ← 64-bit Intel (emulators)               │
│  │  x86         │ ← 32-bit Intel (old emulators)           │
│  └──────────────┘                                           │
│                                                              │
│  Step 2: Compilation (per ABI)                               │
│  ─────────────────────────────                               │
│  For EACH target ABI:                                        │
│       │                                                      │
│       ↓                                                      │
│  ┌────────────────────────────────────────────────────────┐ │
│  │  NDK Clang/LLVM Cross-Compiler                        │ │
│  │                                                        │ │
│  │  .cpp/.c files                                         │ │
│  │       │                                                │ │
│  │  Preprocessor (#include, #define)                      │ │
│  │       │                                                │ │
│  │  Compiler (Clang frontend)                             │ │
│  │       │                                                │ │
│  │  LLVM Intermediate Representation (IR)                 │ │
│  │       │                                                │ │
│  │  LLVM Optimizer (optimization passes)                  │ │
│  │       │                                                │ │
│  │  LLVM Backend (target-specific code generation)        │ │
│  │       │                                                │ │
│  │  .o files (object files — native machine code)         │ │
│  └────────────────────────────────────────────────────────┘ │
│       │                                                      │
│  Step 3: Linking                                             │
│  ────────────────                                            │
│       │                                                      │
│  ┌────────────────────────────────────────────────────────┐ │
│  │  NDK Linker (lld)                                      │ │
│  │                                                        │ │
│  │  .o files (compiled objects)                            │ │
│  │  + NDK system libraries (libc, libm, liblog, etc.)    │ │
│  │  + Third-party libraries (if any)                      │ │
│  │       │                                                │ │
│  │  Links everything together                             │ │
│  │       │                                                │ │
│  │  Output: .so file (Shared Object / Dynamic Library)    │ │
│  │  Format: ELF (Executable and Linkable Format)          │ │
│  └────────────────────────────────────────────────────────┘ │
│       │                                                      │
│  Result: One .so file PER ABI                                │
│  ├── lib/arm64-v8a/libnative-lib.so                         │
│  ├── lib/armeabi-v7a/libnative-lib.so                       │
│  ├── lib/x86_64/libnative-lib.so                            │
```
