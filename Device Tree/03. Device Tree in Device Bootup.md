# Device Tree in Device Bootup — Complete Deep Dive

## Overview Flow

```
┌─────────────────────────────────────────────────────────────────────┐
│                    COMPLETE DEVICE BOOTUP FLOW                      │
│                                                                     │
│  Power ON                                                           │
│     │                                                               │
│     ▼                                                               │
│  ROM Code (Built-in, no DT)                                        │
│     │                                                               │
│     ▼                                                               │
│  SPL/IBL (Secondary Program Loader, minimal DT use)                │
│     │                                                               │
│     ▼                                                               │
│  Bootloader (LOADS & MERGES DT + DTBO)          ← DT starts here  │
│     │                                                               │
│     ▼                                                               │
│  Kernel Boot (READS DT, probes devices)         ← DT heavy use    │
│     │                                                               │
│     ▼                                                               │
│  Init Process (reads /proc/device-tree)         ← DT reference    │
│     │                                                               │
│     ▼                                                               │
│  HAL Layer (uses drivers probed via DT)         ← DT indirect use │
│     │                                                               │
│     ▼                                                               │
│  Android Framework (hardware abstraction)       ← DT transparent  │
│     │                                                               │
│     ▼                                                               │
│  Apps (no DT knowledge at all)                  ← DT invisible    │
└─────────────────────────────────────────────────────────────────────┘
```

## Phase 1: ROM Code (No Device Tree)

```
┌─────────────────────────────────────────────────────────────────────┐
│                         ROM CODE                                    │
│                  (Burned into SoC chip)                             │
│                                                                     │
│  Hardcoded in silicon:                                              │
│  • Basic CPU initialization                                         │
│  • SRAM setup (tiny amount)                                         │
│  • Boot device selection (eMMC/SD/USB/NAND)                        │
│  • Loads SPL from boot device                                       │
│                                                                     │
│  DT Usage: ❌ NONE - Everything hardcoded                           │
│                                                                     │
│  Why no DT?                                                         │
│  • No filesystem access yet                                         │
│  • No DRAM available (DRAM not initialized)                         │
│  • Code burned in ROM cannot be changed                             │
└─────────────────────────────────────────────────────────────────────┘
```

## Phase 2: SPL / First Stage Bootloader (Minimal DT)

```
┌─────────────────────────────────────────────────────────────────────┐
│              SPL (Secondary Program Loader)                         │
│              Also called: MLO, IBL, First Stage BL                  │
│                                                                     │
│  Runs from: SRAM (small, fast on-chip memory)                      │
│  Size limit: Usually 64KB – 256KB                                  │
│                                                                     │
│  Tasks:                                                             │
│  1. Initialize DRAM/DDR controller                                  │
│     (hardcoded register writes or MINIMAL DT)                       │
│  2. Setup basic clocks                                              │
│  3. Initialize storage (eMMC/SD)                                    │
│  4. Load main bootloader (U-Boot/ABL/LK) to DRAM                  │
│                                                                     │
│  DT Usage: ⚠️ MINIMAL                                               │
│  • Some SPLs use a tiny DT for DRAM init params                    │
│  • Most use hardcoded values                                        │
└─────────────────────────────────────────────────────────────────────┘
```

```dts
/* Minimal DT used by some SPLs for DRAM configuration */
/ {
    memory-controller@ff400000 {
        compatible = "example,dram-ctrl";
        reg = <0xff400000 0x1000>;

        ddr-speed-bin  = "DDR4-3200";
        ddr-size-mb    = <4096>;        // 4GB
        ddr-bus-width  = <32>;

        /* Timing in picoseconds */
        timing-trcd = <13750>;
        timing-trp  = <13750>;
        timing-tras = <32000>;
        timing-trc  = <45750>;
        timing-tcl  = <14>;
    };
};
```

## Phase 3: Bootloader (Main DT Processing)

```
┌─────────────────────────────────────────────────────────────────────┐
│           MAIN BOOTLOADER (U-Boot / ABL / LK2ND)                   │
│           This is where MOST DT work happens before kernel          │
│                                                                     │
│  STEP 1: Load Base DTB                                              │
│  dtb_partition → read → DRAM buffer                                │
│  OR vendor_boot → extract DTB section → DRAM buffer                │
│          │                                                          │
│          ▼                                                          │
│  STEP 2: Load DTBO Image                                            │
│  dtbo_partition → read all overlay entries → DRAM                  │
│          │                                                          │
│          ▼                                                          │
│  STEP 3: AVB Verification                                           │
│  • Verify dtbo.img signature against vbmeta                        │
│  • Verify vendor_boot DTB section                                  │
│  • If verification fails → HALT or warn                            │
│          │                                                          │
│          ▼                                                          │
│  STEP 4: Hardware Detection                                         │
│  • Read board_id from:                                              │
│    - GPIO strapping pins                                            │
│    - eFuse/OTP registers                                            │
│    - I2C EEPROM                                                     │
│    - SMEM (Shared Memory) on Qualcomm                              │
│  • Read board_revision, hardware variant info                      │
│          │                                                          │
│          ▼                                                          │
│  STEP 5: Overlay Selection & Application                            │
│  For each DTBO entry:                                               │
│    if (entry.board_id == detected_board_id &&                       │
│        entry.rev     == detected_rev) {                             │
│        apply_overlay(base_dtb, overlay);                            │
│    }                                                                │
│          │                                                          │
│          ▼                                                          │
│  STEP 6: Bootloader Modifies DT (DYNAMICALLY)                       │
│  • Memory size (detected at runtime)                                │
│  • Serial number                                                    │
│  • Boot command line (bootargs)                                     │
│  • KASLR seed (random for security)                                 │
│  • Initrd location & size                                           │
│  • Verified boot state                                              │
│  • Android boot properties                                          │
│          │                                                          │
│          ▼                                                          │
│  STEP 7: Pass DT to Kernel                                          │
│  ARM64: x0 = 0 (unused)                                             │
│         x1 = 0 (unused)                                             │
│         x2 = 0 (unused)                                             │
│         x3 = physical address of DTB in DRAM  ← KEY               │
│  Kernel reads DTB from x3 register at startup                      │
└─────────────────────────────────────────────────────────────────────┘
```

### Bootloader DT Modification Example

```c
/* Actual bootloader code (simplified U-Boot style) */
#include <libfdt.h>

void prepare_device_tree(void *fdt) {
    int node;

    /* ===== 1. Update Memory Size ===== */
    uint64_t dram_size = detect_dram_size();
    uint64_t dram_base = 0x80000000ULL;

    node = fdt_path_offset(fdt, "/memory@80000000");
    uint64_t mem_reg[2] = { cpu_to_fdt64(dram_base), cpu_to_fdt64(dram_size) };
    fdt_setprop(fdt, node, "reg", mem_reg, sizeof(mem_reg));

    /* ===== 2. Update bootargs ===== */
    node = fdt_path_offset(fdt, "/chosen");
    char bootargs[512];
    snprintf(bootargs, sizeof(bootargs),
        "console=ttyMSM0,115200 "
        "androidboot.hardware=mydevice "
        "androidboot.serialno=%s "
        "androidboot.verifiedbootstate=%s "
        "androidboot.slot_suffix=%s "
        "mem=%lluM",
        get_serial_number(),
        get_verified_boot_state(),  // "green"/"yellow"/"orange"/"red"
        get_ab_slot(),              // "_a" or "_b"
        dram_size / (1024 * 1024)
    );
    fdt_setprop_string(fdt, node, "bootargs", bootargs);

    /* ===== 3. Set initrd location ===== */
    fdt_setprop_u32(fdt, node, "linux,initrd-start", RAMDISK_LOAD_ADDR);
    fdt_setprop_u32(fdt, node, "linux,initrd-end",   RAMDISK_LOAD_ADDR + ramdisk_size);

    /* ===== 4. Set KASLR seed ===== */
    fdt_setprop_u64(fdt, node, "kaslr-seed", generate_random_seed());

    /* ===== 5. Add board info ===== */
    node = fdt_path_offset(fdt, "/");
    fdt_setprop_string(fdt, node, "android,board-id", get_board_id_string());

    /* ===== 6. Update display framebuffer ===== */
    node = fdt_path_offset(fdt, "/reserved-memory/framebuffer");
    uint32_t fb_reg[2] = { cpu_to_fdt32(framebuffer_base), cpu_to_fdt32(framebuffer_size) };
    fdt_setprop(fdt, node, "reg", fb_reg, sizeof(fb_reg));
}

void boot_kernel(void) {
    void *fdt = load_dtb_from_partition();
    apply_dtbo_overlays(fdt);
    prepare_device_tree(fdt);

    /* ARM64 calling convention: x3 = DT physical address */
    void (*kernel_entry)(void*, void*, void*, void*) = kernel_addr;
    kernel_entry(0, 0, 0, fdt);
    /* Never returns */
}
```

## Phase 4: Kernel Boot — DT Processing (Most Critical Phase)

```
┌─────────────────────────────────────────────────────────────────────┐
│                    KERNEL DT PROCESSING                             │
│                                                                     │
│  Kernel Entry (arch/arm64/kernel/head.S)                           │
│  x3 register holds DTB physical address                            │
│        │                                                            │
│        ▼                                                            │
│  early_init_dt_scan()                                               │
│  • Scans /chosen for bootargs                                       │
│  • Gets memory layout                                               │
│  • Sets up early console (earlycon)                                 │
│        │                                                            │
│        ▼                                                            │
│  setup_machine_fdt()                                                │
│  • Validates DTB magic number (0xd00dfeed)                         │
│  • Copies DTB to permanent location                                 │
│  • Unflatten FDT (flat → tree structure in memory)                 │
│        │                                                            │
│        ▼                                                            │
│  unflatten_device_tree()                                            │
│                                                                     │
│  Flat DTB (binary):         Tree in Memory:                         │
│  [raw bytes]          →     device_node {                           │
│                               name, full_name                       │
│                               properties linked list                │
│                               parent / child / sibling pointers     │
│                             }                                       │
│        │                                                            │
│        ▼                                                            │
│  irqchip_init()    → finds GIC node in DT                          │
│  (Interrupt controller must come first — everything needs IRQs)    │
│        │                                                            │
│        ▼                                                            │
│  of_clk_init()     → finds all clock providers in DT               │
│  → registers clock tree                                             │
│        │                                                            │
│        ▼                                                            │
│  of_platform_populate()  → walks DT tree                           │
│  → creates platform_device for each node                            │
│  → adds to platform bus                                             │
│        │                                                            │
│        ▼                                                            │
│  Driver Matching & Probing                                          │
│  For each platform_device:                                          │
│    1. Look at device's compatible string                            │
│    2. Search registered drivers' of_match_table                     │
│    3. If match found → call driver's probe()                        │
│    4. Driver reads its properties from DT                           │
└─────────────────────────────────────────────────────────────────────┘
```

### Kernel DT Parsing — Internal Code Flow

```c
/* arch/arm64/kernel/setup.c */
void __init setup_arch(char **cmdline_p) {
    void *dt_virt = fixmap_remap_fdt(__fdt_pointer);

    if (!early_init_dt_scan(dt_virt))
        panic("No DTB found!\n");

    *cmdline_p = boot_command_line;
}

/* drivers/of/fdt.c */
void __init unflatten_device_tree(void) {
    __unflatten_device_tree(initial_boot_params, NULL, &of_root,
                            early_init_dt_alloc_memory_arch, false);
    of_alias_scan(early_init_dt_alloc_memory_arch);
}

/* drivers/of/platform.c */
int __init of_platform_populate(struct device_node *root, ...) {
    struct device_node *child;

    for_each_child_of_node(root, child) {
        if (!of_find_property(child, "compatible", NULL))  continue;
        if (!of_device_is_available(child))                continue;

        of_platform_device_create(child, NULL, parent);
        of_platform_populate(child, matches, ...);
    }
}

/* drivers/base/platform.c */
static int platform_match(struct device *dev, struct device_driver *drv) {
    struct platform_device *pdev = to_platform_device(dev);

    if (pdev->dev.of_node)
        return of_driver_match_device(dev, drv);

    return (strcmp(pdev->name, drv->name) == 0);
}

bool of_driver_match_device(struct device *dev, const struct device_driver *drv) {
    const char *compat;
    of_property_read_string(dev->of_node, "compatible", &compat);

    const struct of_device_id *id;
    for (id = drv->of_match_table; id->compatible[0]; id++) {
        if (of_compat_cmp(compat, id->compatible, ...) == 0)
            return true;    // MATCH FOUND → probe() will be called
    }
    return false;
}
```

## Phase 5: Init Process — DT Usage

```
┌─────────────────────────────────────────────────────────────────────┐
│  /proc/device-tree/  (Kernel exposes live DT here)                 │
│  ├── model           → "Example Device"                             │
│  ├── compatible      → "vendor,device\0vendor,soc"                 │
│  ├── chosen/                                                        │
│  │   └── bootargs   → "console=ttyS0 androidboot.hw=..."           │
│  └── firmware/                                                      │
│      └── android/                                                   │
│          ├── compatible → "android,firmware"                        │
│          └── fstab/    → filesystem mount info                      │
│                                                                     │
│  Init reads DT to:                                                  │
│  1. Get hardware name → set ro.hardware property                   │
│  2. Read fstab → know what partitions to mount                     │
│  3. Read androidboot.* from bootargs → set system properties       │
│  4. Detect hardware features → start appropriate services          │
└─────────────────────────────────────────────────────────────────────┘
```

```cpp
/* system/core/init/property_service.cpp (simplified) */

void PropertyService::LoadPropertiesFromDT() {
    std::string model;
    if (ReadFileToString("/proc/device-tree/model", &model))
        SetProperty("ro.product.model", Trim(model));

    std::string bootargs;
    ReadFileToString("/proc/device-tree/chosen/bootargs", &bootargs);

    for (const auto& entry : Split(bootargs, " ")) {
        if (StartsWith(entry, "androidboot.")) {
            auto [key, value] = Split(entry, "=");
            // androidboot.hardware → ro.boot.hardware
            SetProperty("ro.boot." + key.substr(strlen("androidboot.")), value);
        }
    }
}

Fstab ReadFstabFromDt() {
    auto fstab_node_path = "/proc/device-tree/firmware/android/fstab";

    for (const auto& entry : GetDtChildren(fstab_node_path)) {
        std::string blk_device, fs_type, mnt_flags, fsmgr_flags;

        ReadFileToString(entry + "/dev",         &blk_device);
        ReadFileToString(entry + "/type",        &fs_type);
        ReadFileToString(entry + "/mnt_flags",   &mnt_flags);
        ReadFileToString(entry + "/fsmgr_flags", &fsmgr_flags);

        fstab.emplace_back(blk_device, mount_point, fs_type, ...);
    }
    return fstab;
}
```

## Which Drivers USE Device Tree?

### ✅ Platform / SoC Drivers (Always use DT)

```
1.  GPIO Controllers           reg base, interrupt, pin count
2.  I2C Bus Controllers        base addr, clock, speed, child devices
3.  SPI Bus Controllers        base addr, clock, chip-selects
4.  UART / Serial Controllers  base addr, interrupt, clock rate
5.  Clock Controllers / PLLs   register base, parent clocks, rates
6.  Pin Controllers (pinctrl)  pin mux settings per peripheral
7.  Power Management (PMIC)    regulator names, voltages, GPIO
8.  Interrupt Controllers      base addr, IRQ count (mandatory)
9.  DMA Controllers            base addr, channel count
10. Watchdog Timers            register base, timeout values
```

## Which Drivers Do NOT Use Device Tree?

### ❌ PCI / PCIe Devices

```
PCI uses its OWN discovery mechanism:

PCI Bus
├── Device 0:0 → GPU  (self-identifies via Vendor:Device ID)
├── Device 0:1 → WiFi card
└── Device 0:2 → USB controller

How PCI works:
• OS scans PCI config space
• Each device reports: Vendor ID + Device ID + Class Code
• Driver matches on Vendor:Device ID → NO DT needed

BUT: PCI Root Complex (the controller itself) IS in DT:
  pcie@fc000000 {
      compatible = "example,pcie-controller";
      /* controller in DT, devices behind it NOT */
  }
```

```c
/* PCI driver — no DT */
static const struct pci_device_id my_pci_ids[] = {
    { PCI_DEVICE(0x168C, 0x003E) }, // Qualcomm WiFi
    { PCI_DEVICE(0x10DE, 0x1234) }, // NVIDIA GPU
    { 0 }
};
```

### ❌ USB Devices

```
USB uses hot-plug discovery:

USB Host Controller (in DT)
└── USB Hub (self-enumerates)
    ├── USB Keyboard  → matched by Vendor:Product ID
    ├── USB Mouse     → matched by Vendor:Product ID
    ├── USB Storage   → matched by class code
    └── USB Camera    → matched by class code

Device responds with: Vendor ID, Product ID, Class → DT not involved.
BUT: USB Controller (xHCI/EHCI) itself IS in DT.
```

```c
/* USB driver — no DT */
static const struct usb_device_id my_usb_ids[] = {
    { USB_DEVICE(0x046D, 0xC52B) },              // Logitech receiver
    { USB_DEVICE_CLASS(USB_CLASS_HID, 0, 0) },   // Any HID
    { }
};
```

### ❌ Virtual / Software Drivers

```
No physical hardware → No DT needed:

• /dev/null, /dev/zero, /dev/random   → No hardware
• loopback interface (lo)             → Virtual
• dm-crypt, dm-verity                 → Software layers
• OverlayFS, SquashFS, Ext4          → Filesystems
• Netfilter / iptables                → Software firewall
• VLAN, bridge, bonding               → Network virtual devices
• /dev/binder                         → Android IPC (software)
```

### ❌ Bluetooth Peripherals

```
BT Controller (UART-connected) → MAY be in DT
BT Peripherals                 → Use BT discovery protocol

BT mouse, headphones, speakers:
→ Identified by BT device class + UUID profiles
→ No DT involvement
```

### ❌ Purely Software Kernel Subsystems

```
• Scheduler (CFS, EAS)        → sysfs/procfs configuration
• Memory management (SLUB)    → Compile-time config
• Crypto subsystem (SW)       → No hardware for SW crypto
• SELinux / AppArmor          → Policy files
• Cgroups / Namespaces        → OS-level isolation
• futex, epoll, inotify       → System call mechanisms
```

## The Golden Rule for DT Usage

```
┌─────────────────────────────────────────────────────────────────────┐
│                                                                     │
│  USE Device Tree WHEN:                                              │
│                                                                     │
│  ✅ Device is MEMORY-MAPPED                                          │
│     Hardware accessed via fixed register addresses                  │
│     Kernel cannot discover it automatically                         │
│                                                                     │
│  ✅ Device is permanently SOLDERED to board                          │
│     Not hot-pluggable                                               │
│     Address/connection fixed at manufacturing time                 │
│                                                                     │
│  ✅ Device requires MANUAL CONFIGURATION                             │
│     Needs specific clock, voltage, GPIO settings                    │
│     Settings vary per board/product                                 │
│                                                                     │
│  ─────────────────────────────────────────────────────────────────  │
│                                                                     │
│  DO NOT USE Device Tree WHEN:                                       │
│                                                                     │
│  ❌ Device has its OWN DISCOVERY PROTOCOL                            │
│     USB → enumerate via USB protocol                                │
│     PCI → scan config space                                         │
│     Bluetooth → BT pairing and discovery                            │
│                                                                     │
│  ❌ Device is PURELY SOFTWARE                                         │
│     No physical hardware registers                                  │
│     Virtual devices, protocol layers, filesystems                   │
│                                                                     │
│  ❌ Device is HOT-PLUGGABLE via standard bus                         │
│     Can be added/removed while system runs                          │
│     Bus protocol handles discovery                                  │
└─────────────────────────────────────────────────────────────────────┘
```

## Complete Phase Summary

```
┌───────────────────┬──────────────────────────────────────────────────────┐
│  Boot Phase       │  DT Activity                                         │
├───────────────────┼──────────────────────────────────────────────────────┤
│  ROM Code         │  ❌ No DT — hardcoded in silicon                      │
├───────────────────┼──────────────────────────────────────────────────────┤
│  SPL              │  ⚠️ Minimal/None — DRAM init only                     │
├───────────────────┼──────────────────────────────────────────────────────┤
│  Bootloader       │  ✅ Loads DTB, applies DTBO overlays                  │
│                   │  ✅ Detects hardware, selects correct overlays        │
│                   │  ✅ Modifies DT (memory, bootargs, serial number)     │
│                   │  ✅ Verifies DT (AVB signature check)                 │
│                   │  ✅ Passes DT pointer to kernel (x3 register)         │
├───────────────────┼──────────────────────────────────────────────────────┤
│  Kernel Boot      │  ✅ Reads DT from x3 pointer                          │
│                   │  ✅ Unflatten FDT → in-memory tree                    │
│                   │  ✅ Inits memory, interrupt controller, clock tree    │
│                   │  ✅ Creates platform devices from DT nodes            │
│                   │  ✅ Probes matched drivers, reads DT properties       │
│                   │  ✅ Exposes DT via /proc/device-tree/                 │
├───────────────────┼──────────────────────────────────────────────────────┤
│  Init Process     │  ✅ Reads /proc/device-tree/ for hw config            │
│                   │  ✅ Derives system properties from DT                 │
│                   │  ✅ Reads fstab from DT firmware/android node         │
│                   │  ✅ Starts services conditionally based on DT         │
├───────────────────┼──────────────────────────────────────────────────────┤
│  HAL Layer        │  ✅ Uses DT-probed drivers via /dev/* nodes           │
│                   │  ✅ May read /proc/device-tree/ for extra config      │
├───────────────────┼──────────────────────────────────────────────────────┤
│  Framework        │  ⚠️ Transparent — uses HAL abstraction                │
│                   │  DT is invisible at this level                        │
├───────────────────┼──────────────────────────────────────────────────────┤
│  Apps             │  ❌ No DT knowledge                                    │
│                   │  Use Android APIs (camera, sensors, audio, etc.)      │
└───────────────────┴──────────────────────────────────────────────────────┘
```

> **Key Insight:** Device Tree is heaviest during the **Bootloader** and **Kernel Boot** phases. After boot, it becomes a read-only reference — Init reads it for configuration, HALs occasionally query it for hardware specifics, and the Framework/Apps are completely abstracted from it.
