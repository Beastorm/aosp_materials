## 1. What is VNDK?

**VNDK = Vendor Native Development Kit**

Introduced in Android 8 (Oreo) to cleanly separate:

- 📱 Android system framework code (`/system`)
- 🏭 Vendor (device manufacturer) code — Qualcomm, MediaTek, Samsung hardware libraries (`/vendor`)

---

## 2. Why Was VNDK Needed?

### Before Android 8 — The Problem

Vendor code directly used internal system libraries. When Google updated Android, those internal libraries changed, and vendor binaries broke. Device makers had to redo a lot of work for every Android upgrade.

> **Result:** Slow Android updates, fragmented ecosystem.

### Simple Analogy

```
Android system = 🏢 Building foundation
Vendor code    = 🏠 Furniture inside

Before VNDK:
  Furniture was attached directly to the walls.
  If walls changed → furniture broke.

With VNDK:
  Google created a stable interface layer.
  Furniture connects only to fixed hooks.
  If walls change, hooks stay the same.
  Furniture keeps working.
```

### The Solution: Partition Separation

```
/system     → Android framework libraries
/vendor     → Device manufacturer code
/vendor/lib → Vendor's own libraries
```

VNDK provided a **stable set of libraries** vendors were allowed to use, enforcing strict rules so vendor code could not call private system APIs.

## 3. Library Categories

```
┌────────────────────────────────────────────────────────┐
│  LL-NDK (Low Level NDK)                                │
│  Example: libc.so, libm.so, liblog.so                  │
│  Vendor can ALWAYS use these                           │
├────────────────────────────────────────────────────────┤
│  VNDK                                                  │
│  Example: libcutils.so, libutils.so                    │
│  Vendor can use — stable copy provided at             │
│  /system/lib/vndk/                                     │
├────────────────────────────────────────────────────────┤
│  VNDK-SP (Same Process)                                │
│  Example: libRScpp.so                                  │
│  Used when system and vendor run in the same process   │
├────────────────────────────────────────────────────────┤
│  Framework Private                                     │
│  Example: libandroid_runtime.so                        │
│  Vendor CANNOT use ❌                                  │
└────────────────────────────────────────────────────────┘
```

### How the VNDK Copy Works

```
/system/lib/libcutils.so          ← Used by system
/system/lib/vndk/libcutils.so     ← Used by vendor (stable copy)
```

Even if the system's `libcutils` changes, the VNDK copy stays stable and the vendor HAL keeps working.

## 4. How Vendor Code Uses VNDK

### Step 1 — Write the HAL Code

```cpp
// camera_hal.cpp — Vendor camera HAL code

#include <cutils/properties.h>   // from libcutils (VNDK)
#include <utils/Log.h>           // from libutils (VNDK)

int main() {
    char value[100];
    property_get("ro.build.version.sdk", value, "0");
    ALOGI("SDK Version: %s", value);
    return 0;
}
```

### Step 2 — Android.bp Build File

```bp
cc_binary {
    name: "camera_hal",
    srcs: ["camera_hal.cpp"],

    vendor: true,       // ← Tell build system this is VENDOR code

    shared_libs: [
        "libcutils",    // VNDK library
        "libutils",     // VNDK library
        "liblog",       // LL-NDK library
    ],
}
```

### Step 3 — Build System Handles It Automatically

```
Build system sees vendor: true
        ↓
Automatically links to VNDK version
        ↓
/system/lib/vndk/libcutils.so  ← used ✅
NOT /system/lib/libcutils.so   ← skipped
```

No extra work needed — setting `vendor: true` is sufficient.

---

### How to Check if a Library is VNDK

Look for `vndk: { enabled: true }` in the library's `Android.bp`:

```bp
// In libcutils Android.bp
cc_library {
    name: "libcutils",

    vndk: {
        enabled: true,    // ← This makes it VNDK!
    },
    ...
}
```

---

### What Happens if Vendor Uses a Private Library?

```cpp
// BAD — Vendor trying to use a private library ❌
#include <android_runtime/something.h>
```

```
Build error:
  error: libandroid_runtime is not available
  for the vendor partition.
  Use a VNDK library instead.
```

### Quick Usage Reference

| What | How |
|---|---|
| Mark library as VNDK | `vndk: { enabled: true }` in `Android.bp` |
| Mark code as vendor | `vendor: true` in `Android.bp` |
| Use a VNDK library | Just include the header — build handles the rest |
| Check if a library is allowed | Look for `vndk: enabled` in its source |
| VNDK libraries location | `/system/lib/vndk/` |

## 6. Why Was VNDK Deprecated?

**Short answer:** Android's architecture improved and VNDK was no longer needed in the same way. It solved an old problem; now Android uses better mechanisms.

### What Changed After VNDK Was Introduced

**Project Treble matured** — The system/vendor separation became standard and stable across all Android devices.

**Stable AIDL replaced HIDL** — Communication between system and vendor became version-controlled and stable without needing a VNDK copy of every library.

**Mainline modules (APEX) introduced** — Parts of Android can now be updated independently via Google Play, bypassing the need for full system images.

**Stronger partition rules enforced** — System and vendor are strictly isolated by design, not just by library copy conventions.

### Simple Analogy

```
VNDK = 🛠 Temporary scaffolding used while constructing a building.

At first:
  The building needed scaffolding for support.

Later:
  The structure became strong and self-supported.
  Scaffolding was removed.

VNDK     = scaffolding
Modern modular Android = strong finished building
```

### Technical Reason

- Vendor interface is now **frozen per Android release**
- System libraries are no longer meant to be accessed directly
- Stable AIDL + VINTF manifests manage compatibility
- Kernel and vendor freeze models handle version compatibility
- Maintaining separate VNDK versions became unnecessary complexity

### Important Note

VNDK was not suddenly deleted. It is:
- No longer evolving
- No longer the main mechanism for compatibility
- Gradually replaced by better modular design

---

## 7. Summary

### Before vs After VNDK

| Before VNDK | With VNDK |
|---|---|
| Vendor tightly coupled to system | Vendor separated |
| Updates broke devices | Easier upgrades |
| Slow Android updates | Faster updates |

### Why VNDK Was Deprecated

| Reason | Detail |
|---|---|
| Treble matured | System/vendor separation is now standard |
| Stable AIDL | Replaced many unstable interfaces |
| Mainline modules | Improved modular updates via APEX |
| Android compatibility model matured | Stricter partitioning enforced by design |
| VNDK became redundant | Maintaining separate copies added complexity with less benefit |

---

> **As a vendor developer (while VNDK was active):**
> 1. Set `vendor: true` in `Android.bp`
> 2. Use only VNDK / LL-NDK libraries
> 3. Build system handles the rest
> 4. Your code stays compatible across Android updates
