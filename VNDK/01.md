## 1. What is VNDK?

**VNDK = Vendor Native Development Kit**

Introduced in Android 8 (Oreo) to cleanly separate:

- 📱 Android system framework code (`/system`)
- 🏭 Vendor (device manufacturer) code — Qualcomm, MediaTek, Samsung hardware libraries (`/vendor`)

---

## 2. Why Was VNDK Needed?

### Before Android 8 — The Problem

Vendor code directly used internal system libraries. When Google updated Android, those internal libraries changed, and vendor binaries broke. Device makers had to redo a lot of work for every Android upgrade.

> **Result:** Slow Android updates, fragmented ecosystem.

### Simple Analogy

```
Android system = 🏢 Building foundation
Vendor code    = 🏠 Furniture inside

Before VNDK:
  Furniture was attached directly to the walls.
  If walls changed → furniture broke.

With VNDK:
  Google created a stable interface layer.
  Furniture connects only to fixed hooks.
  If walls change, hooks stay the same.
  Furniture keeps working.
```

### The Solution: Partition Separation

```
/system     → Android framework libraries
/vendor     → Device manufacturer code
/vendor/lib → Vendor's own libraries
```

VNDK provided a **stable set of libraries** vendors were allowed to use, enforcing strict rules so vendor code could not call private system APIs.

---

## 3. Library Categories

```
┌────────────────────────────────────────────────────────┐
│  LL-NDK (Low Level NDK)                                │
│  Example: libc.so, libm.so, liblog.so                  │
│  Vendor can ALWAYS use these                           │
├────────────────────────────────────────────────────────┤
│  VNDK                                                  │
│  Example: libcutils.so, libutils.so                    │
│  Vendor can use — stable copy provided at             │
│  /system/lib/vndk/                                     │
├────────────────────────────────────────────────────────┤
│  VNDK-SP (Same Process)                                │
│  Example: libRScpp.so                                  │
│  Used when system and vendor run in the same process   │
├────────────────────────────────────────────────────────┤
│  Framework Private                                     │
│  Example: libandroid_runtime.so                        │
│  Vendor CANNOT use ❌                                  │
└────────────────────────────────────────────────────────┘
```

### How the VNDK Copy Works

```
/system/lib/libcutils.so          ← Used by system
/system/lib/vndk/libcutils.so     ← Used by vendor (stable copy)
```

Even if the system's `libcutils` changes, the VNDK copy stays stable and the vendor HAL keeps working.

## 4. How Vendor Code Uses VNDK

### Step 1 — Write the HAL Code

```cpp
// camera_hal.cpp — Vendor camera HAL code

#include <cutils/properties.h>   // from libcutils (VNDK)
#include <utils/Log.h>           // from libutils (VNDK)

int main() {
    char value[100];
    property_get("ro.build.version.sdk", value, "0");
    ALOGI("SDK Version: %s", value);
    return 0;
}
```

### Step 2 — Android.bp Build File

```bp
cc_binary {
    name: "camera_hal",
    srcs: ["camera_hal.cpp"],

    vendor: true,       // ← Tell build system this is VENDOR code

    shared_libs: [
        "libcutils",    // VNDK library
        "libutils",     // VNDK library
        "liblog",       // LL-NDK library
    ],
}
```

### Step 3 — Build System Handles It Automatically

```
Build system sees vendor: true
        ↓
Automatically links to VNDK version
        ↓
/system/lib/vndk/libcutils.so  ← used ✅
NOT /system/lib/libcutils.so   ← skipped
```

No extra work needed — setting `vendor: true` is sufficient.

---

### How to Check if a Library is VNDK

Look for `vndk: { enabled: true }` in the library's `Android.bp`:

```bp
// In libcutils Android.bp
cc_library {
    name: "libcutils",

    vndk: {
        enabled: true,    // ← This makes it VNDK!
    },
    ...
}
```

---

### What Happens if Vendor Uses a Private Library?

```cpp
// BAD — Vendor trying to use a private library ❌
#include <android_runtime/something.h>
```

```
Build error:
  error: libandroid_runtime is not available
  for the vendor partition.
  Use a VNDK library instead.
```

## 6. Why Was VNDK Deprecated?

**Short answer:** Android's architecture improved and VNDK was no longer needed in the same way. It solved an old problem; now Android uses better mechanisms.

### What Changed After VNDK Was Introduced

**Project Treble matured** — The system/vendor separation became standard and stable across all Android devices.

**Stable AIDL replaced HIDL** — Communication between system and vendor became version-controlled and stable without needing a VNDK copy of every library.

**Mainline modules (APEX) introduced** — Parts of Android can now be updated independently via Google Play, bypassing the need for full system images.

**Stronger partition rules enforced** — System and vendor are strictly isolated by design, not just by library copy conventions.

### Simple Analogy

```
VNDK = 🛠 Temporary scaffolding used while constructing a building.

At first:
  The building needed scaffolding for support.

Later:
  The structure became strong and self-supported.
  Scaffolding was removed.

VNDK     = scaffolding
Modern modular Android = strong finished building
```

### Technical Reason

- Vendor interface is now **frozen per Android release**
- System libraries are no longer meant to be accessed directly
- Stable AIDL + VINTF manifests manage compatibility
- Kernel and vendor freeze models handle version compatibility
- Maintaining separate VNDK versions became unnecessary complexity

### Important Note

VNDK was not suddenly deleted. It is:
- No longer evolving
- No longer the main mechanism for compatibility
- Gradually replaced by better modular design

---

## 7. Summary

### Before vs After VNDK

| Before VNDK | With VNDK |
|---|---|
| Vendor tightly coupled to system | Vendor separated |
| Updates broke devices | Easier upgrades |
| Slow Android updates | Faster updates |

### Why VNDK Was Deprecated

| Reason | Detail |
|---|---|
| Treble matured | System/vendor separation is now standard |
| Stable AIDL | Replaced many unstable interfaces |
| Mainline modules | Improved modular updates via APEX |
| Android compatibility model matured | Stricter partitioning enforced by design |
| VNDK became redundant | Maintaining separate copies added complexity with less benefit |

---

> **As a vendor developer (while VNDK was active):**
> 1. Set `vendor: true` in `Android.bp`
> 2. Use only VNDK / LL-NDK libraries
> 3. Build system handles the rest
> 4. Your code stays compatible across Android updates

## 1. Core Concept

VNDK is a set of system libraries that Google allows vendors to use safely.

```
/system     → Android framework libraries
/vendor     → Device manufacturer code
/vendor/lib → Vendor's own libraries
```

There are three access levels:

```
┌─────────────────────────────────────────────┐
│  LL-NDK   → Vendor CAN use (stable APIs)    │
│  VNDK     → Vendor can use (selected ones)  │
│  Private  → Vendor CANNOT use               │
└─────────────────────────────────────────────┘
```

### The Problem VNDK Solved

**Before VNDK:**

```
Camera HAL (vendor code)
    ↓
Directly links to /system/lib/libcutils.so
    ↓
Android updates libcutils internally
    ↓
Camera HAL breaks 💥
```

**With VNDK:**

Google marks `libcutils` as a VNDK library and creates a stable copy:

```
/system/lib/libcutils.so          ← Used by system
/system/lib/vndk/libcutils.so     ← Used by vendor (stable copy)
```

Even if the system's `libcutils` changes, the VNDK copy stays stable and the vendor HAL keeps working.

## 5. VNDK-SP — Same Process Libraries

### The Problem

In Android, system and vendor code normally run in **separate processes** and talk via IPC (Binder/HIDL). But sometimes they must run in the **same process** — and this creates a conflict.

```
┌─────────────────────────────────────┐
│         ONE SINGLE PROCESS          │
│                                     │
│  System code uses → libcutils v2    │
│  Vendor code uses → libcutils v1    │
│                                     │
│  TWO VERSIONS IN SAME PROCESS 💥    │
│  CRASH!                             │
└─────────────────────────────────────┘
```

### Simple Analogy

```
Shared kitchen:

Chef A (System) uses → Gas Stove
Chef B (Vendor) uses → Gas Stove

Both need the SAME stove in the SAME kitchen at the SAME time.
If they use different stoves → kitchen gets crowded → conflicts 💥

VNDK-SP = Agreed set of shared tools both chefs can safely use together.
```

### What is VNDK-SP?

**VNDK-SP = VNDK Same Process** — a smaller, stricter subset of VNDK libraries that are:

- ✅ Safe to load in the same process
- ✅ Used by both system and vendor simultaneously
- ✅ Always exactly ONE version loaded
- ✅ Strictly stable and controlled

---

### Real Example: RenderScript

```
┌─────────────────────────────────────────┐
│            App Process                  │
│                                         │
│  Android Framework (system code)        │
│       +                                 │
│  GPU Driver / Vendor RenderScript code  │
│                                         │
│  BOTH run in SAME process               │
└─────────────────────────────────────────┘
```

System's RenderScript runtime and the vendor GPU driver both need the same libraries, in the same process. Those shared libraries must be VNDK-SP.

**VNDK-SP library examples:**

```
libRScpp.so       → RenderScript C++ API
libRS_internal.so → RenderScript internal
libcutils.so      → (subset allowed in SP)
libutils.so       → (subset allowed in SP)
liblog.so         → logging
libc++.so         → C++ standard library
```

---

### How VNDK-SP is Defined in Code

```bp
cc_library {
    name: "libRScpp",

    vndk: {
        enabled: true,
        support_system_process: true,  // ← This makes it VNDK-SP!
    },

    srcs: ["RenderScript.cpp"],
}
```

`support_system_process: true` = VNDK-SP ✅

---

### Where VNDK-SP Libraries Live

```
Normal VNDK:
  /system/lib/vndk/libcutils.so

VNDK-SP:
  /system/lib/vndk-sp/libRScpp.so
                   ↑
                Different folder!
```

---

### Full VNDK-SP Flow — App Using RenderScript

```
┌─────────────────────────────────────────────────┐
│                 App Process                     │
│                                                 │
│  Step 1: App calls RenderScript API             │
│          ↓                                      │
│  Step 2: Android Framework loads                │
│          libRScpp.so (VNDK-SP)                  │
│          ↓                                      │
│  Step 3: Vendor GPU driver also loads           │
│          libRScpp.so (same VNDK-SP copy)        │
│          ↓                                      │
│  Step 4: BOTH use SAME library                  │
│          No conflict ✅  No crash ✅             │
└─────────────────────────────────────────────────┘
```

---

### What if VNDK-SP Rules Are Broken?

```
┌─────────────────────────────────────────────────┐
│                 App Process                     │
│                                                 │
│  System loads → libcutils v2.0                  │
│  Vendor loads → libcutils v1.5 (not SP!)        │
│                                                 │
│  Same library, two versions, one process        │
│                 ↓                               │
│          SYMBOL CONFLICTS                       │
│          MEMORY CORRUPTION                      │
│          RANDOM CRASHES 💥                      │
└─────────────────────────────────────────────────┘
```

---

### VNDK-SP Rules

1. Library must be marked `support_system_process: true`
2. VNDK-SP libraries can only depend on other VNDK-SP libraries (no mixing)
3. Stored in `/system/lib/vndk-sp/`
4. Only ONE version loaded in a process
5. Very small approved list of libraries

## 1. Why VNDK-SP Exists

### Two Ways Code Can Talk

**Way 1 — Different Processes (Normal):**

```
Process A (System)  →  IPC/Binder  →  Process B (Vendor)

Like calling someone on a phone.
Separate rooms, communicate via phone.
```

**Way 2 — Same Process (Special Cases):**

```
System code + Vendor code inside ONE process.

Like two people working in the SAME room together.
```

### Why Would They Ever Be in the Same Process? — Performance

```
Different process communication:
  App → Binder IPC → Vendor Code
         ↑
    Takes TIME
    Extra memory copies
    Context switching
    Latency added

Same process communication:
  App → Direct function call → Vendor Code
         ↑
    Super FAST ⚡
    No IPC overhead
    No extra copies
    Zero latency
```

When both system and vendor code are in the same process, they may both try to load the same library — but different versions:

```
┌─────────────────────────────────────┐
│         ONE SINGLE PROCESS          │
│                                     │
│  System code uses → libcutils v2    │
│  Vendor code uses → libcutils v1    │
│                                     │
│  TWO VERSIONS IN SAME PROCESS 💥    │
│  CRASH!                             │
└─────────────────────────────────────┘
```

**VNDK-SP solves this** by providing one agreed-upon version of each library that both sides must use when sharing a process.

## 2. Real Cases Where VNDK-SP is Needed

### Case 1 — GPU Rendering

Every app that draws UI needs the GPU. At 60–120 FPS, IPC is far too slow.

```
Option 1: Different Process (BAD ❌)

  App draws one frame
  → sends to another process via IPC
  → GPU driver renders
  → sends result back via IPC
  → App shows frame

  For 120 FPS = IPC overhead × 120 = HUGE LAG 🐢
  Phone becomes unusable!

Option 2: Same Process (GOOD ✅)

  App draws one frame
  → directly calls GPU driver
  → renders instantly
  → shows frame

  For 120 FPS = smooth as butter 🧈⚡
```

```
┌─────────────────────────────────────────┐
│              App Process                │
│                                         │
│  Android Skia / Vulkan (system)         │
│          +                              │
│  Qualcomm / Mali GPU Driver (vendor)    │
│          +                              │
│  Shared VNDK-SP libraries               │
│  (libcutils, libutils, libc++)          │
│                                         │
│  All in ONE process working together ✅ │
└─────────────────────────────────────────┘
```

---

### Case 2 — RenderScript (Image Processing)

Apps use RenderScript for camera effects, image blur, filters. System's RenderScript runtime and the vendor GPU driver both need the same libraries in the same process.

```
Without VNDK-SP:
  RenderScript (system) loads → libRScpp v2.0
  GPU Driver (vendor) loads   → libRScpp v1.5
  Same process, two versions → CRASH! 💥

With VNDK-SP:
  RenderScript (system) loads → libRScpp VNDK-SP ✅
  GPU Driver (vendor) loads   → libRScpp VNDK-SP ✅
  Same version, no conflict ✅
```

---

### Case 3 — Camera Processing

Camera HAL processes 30+ frames per second, each with millions of pixels. IPC for every frame is impossible.

```
┌─────────────────────────────────────────┐
│           Camera App Process            │
│                                         │
│  Android Camera Framework (system)      │
│          +                              │
│  Camera ISP Driver (vendor)             │
│  (Image Signal Processor)               │
│                                         │
│  IPC for every frame = impossible ❌    │
│  Same process = fast enough ✅          │
└─────────────────────────────────────────┘
```

---

### Case 4 — Audio Processing

Audio must be processed in milliseconds. Any IPC delay causes audible glitches.

```
┌─────────────────────────────────────────┐
│           AudioServer Process           │
│                                         │
│  Android AudioFlinger (system)          │
│          +                              │
│  Audio HAL / DSP Driver (vendor)        │
│                                         │
│  Any IPC delay = audio glitch ❌        │
│  Same process = no glitch ✅            │
└─────────────────────────────────────────┘
```

## 6. Stable AIDL

**AIDL = Android Interface Definition Language** — defines how system and vendor talk to each other.

### Old Way (HIDL + VNDK)

```hidl
// vendor/hardware/camera/1.0/ICameraDevice.hal
interface ICameraDevice {
    open() generates (Status status);
    close();
};
```

Problem: Camera HAL needed VNDK libraries to implement this interface. Every Android update meant rechecking VNDK.

### New Way (Stable AIDL)

```aidl
// hardware/interfaces/camera/device/aidl/ICameraDevice.aidl

@VintfStability   // ← Makes this interface STABLE
interface ICameraDevice {
    void open();
    void close();
}
```

`@VintfStability` means:
- Interface is **frozen**
- Works across Android versions
- Vendor implements once, works forever ✅
- No VNDK needed

### Vendor Implementation

```cpp
#include <aidl/hardware/camera/device/BnCameraDevice.h>

class CameraDevice : public BnCameraDevice {
public:
    ndk::ScopedAStatus open() override {
        // Open camera hardware
        return ndk::ScopedAStatus::ok();
    }

    ndk::ScopedAStatus close() override {
        // Close camera hardware
        return ndk::ScopedAStatus::ok();
    }
};
```

```bp
cc_library {
    name: "camera.vendor",
    vendor: true,
    srcs: ["CameraDevice.cpp"],
    shared_libs: [
        "libbinder_ndk",   // ← Stable, no VNDK needed
    ],
}
```

### HIDL vs Stable AIDL

```
┌─────────────────────────────────────────────┐
│  HIDL (Old — used with VNDK)                │
│  ├── Complex syntax                         │
│  ├── Needed VNDK libraries                  │
│  ├── Hard to version                        │
│  └── Being phased out                       │
├─────────────────────────────────────────────┤
│  Stable AIDL (New — replaces VNDK need)     │
│  ├── Simple syntax                          │
│  ├── No VNDK libraries needed               │
│  ├── Easy versioning with @VintfStability   │
│  └── Works across Android versions ✅       │
└─────────────────────────────────────────────┘
```

## 7. APEX (Mainline Modules)

**APEX = Android Pony EXpress** — like APK but for system libraries.

```
APK  = Updates for Apps
APEX = Updates for System Libraries
```

### Old Way (With VNDK)

```
Android System Library needs update:
├── Google releases new Android version
├── OEM gets update, tests everything
├── OEM releases to users
└── Takes 1–2 YEARS! 😱

Meanwhile:
├── VNDK libraries are outdated
├── Security issues unfixed
└── Users suffer
```

### New Way (With APEX)

```
Android System Library needs update:
├── Google updates the APEX module
├── Pushes via Google Play Store
├── Users get update in DAYS! ✅
└── No OEM involvement needed!
```

### Example

```
Before APEX:
  /system/lib/libcrypto.so
  → Part of Android system
  → Needs VNDK to share with vendor
  → OEM must update whole Android to fix security bug
  → Takes months!

After APEX:
  /apex/com.android.conscrypt/lib/libcrypto.so
  → Separate module, updated via Play Store
  → Vendor doesn't need to touch it
  → Fixed in DAYS! ✅
```

### APEX Structure

```
APEX Module:
┌─────────────────────────────┐
│  com.android.media.apex     │
│                             │
│  /lib/libmedia.so           │
│  /lib/libstagefright.so     │
│  /bin/mediaserver           │
│  /etc/config.xml            │
│                             │
│  Self-contained!            │
│  Updated independently! ✅  │
└─────────────────────────────┘
```

### Current APEX Modules

```
/apex/com.android.conscrypt        → Security/SSL
/apex/com.android.media            → Media framework
/apex/com.android.neuralnetworks   → AI/ML
/apex/com.android.wifi             → WiFi stack
/apex/com.android.bluetooth        → Bluetooth
/apex/com.android.art              → ART runtime (Java)
```

All updated via Google Play Store directly, independently of full Android releases.

## 8. Vendor Freeze

**Simple concept:** vendor code is frozen at a specific Android version, and Google guarantees it still works on future versions.

```
Android 13 (2022):
├── Vendor writes Camera HAL
├── Uses Android 13 interfaces
└── Ships to customers

Android 14 (2023):
├── Google guarantees Android 13 HALs still work
├── Vendor doesn't need to update
└── Customers still get Android 14 ✅

Android 15 (2024):
├── Still works!
└── Vendor HAL from 2022 still running ✅
```

### Old vs New

```
OLD (with VNDK):
  Every Android version:
  ├── VNDK libraries might change
  ├── Vendor must check all libraries
  ├── Rebuild and test everything
  └── Lots of work for OEM 😓

NEW (Vendor Freeze):
  ├── Write HAL once
  ├── Interfaces are frozen
  ├── Works for multiple Android versions
  └── OEM can focus on new features ✅
```

## 4. Era 2 — VNDK (Android 8–13)

VNDK works by keeping a **frozen copy** of libraries specifically for vendor use:

```
/system/lib/libutils.so         ← System uses this (can change)
/system/lib/vndk/libutils.so    ← Vendor uses this (FROZEN)
```

### Scenario 1 — Both Updated ✅

```
Both on Android 15.
VNDK copy is also updated alongside system.

System libutils → openCamera(id, mode)  [2 args]
VNDK libutils   → openCamera(id, mode)  [2 args]
Qualcomm HAL    → calls openCamera(id, mode)  [2 args]

MATCH! ✅
```

### Scenario 2 — Neither Updated ✅

```
Both still on Android 14.

VNDK libutils → openCamera(id)  [1 arg]
Qualcomm HAL  → calls openCamera(id)  [1 arg]

MATCH! ✅
```

### Scenario 3 — Only System Updated ✅ (VNDK saves it)

```
Google updates to Android 15. Qualcomm does NOT update.

System libutils → openCamera(id, mode)  ← CHANGED
VNDK libutils   → openCamera(id)        ← FROZEN — stays same
Qualcomm HAL    → calls openCamera(id)  ← uses VNDK copy

MATCH with VNDK copy! ✅  Camera still works!
```

```
┌─────────────────────────────────────────┐
│           Android 15 System             │
│                                         │
│  libutils v15  ← system uses            │
│  openCamera(id, mode)                   │
│                                         │
│  ┌───────────────────────────────────┐  │
│  │  VNDK FROZEN COPY                 │  │
│  │  libutils v13                     │  │
│  │  openCamera(id) ← vendor uses    │  │
│  └───────────────────────────────────┘  │
│                ↑                        │
│    Qualcomm HAL links here              │
│    Still works! ✅                      │
└─────────────────────────────────────────┘
```

### Scenario 4 — Only Vendor Updated ❌ (VNDK cannot help)

```
Qualcomm releases new HAL expecting v15 features.
System still on Android 14.

Qualcomm new HAL → calls openCamera(id, mode)  [2 args]
VNDK libutils    → openCamera(id)              [1 arg only]

MISMATCH! 💥
```

VNDK only protects an **old vendor from a new system**. It cannot protect a new vendor from an old system — the frozen copy is old by definition.

### Era 2 Summary

```
Scenario 1: Both Updated      → ✅ Works
Scenario 2: Neither Updated   → ✅ Works
```

## 5. Era 3 — Stable AIDL (Android 13+)

The key difference: vendor code **never touches system libraries directly**. It only calls a stable **interface**. The system internally handles library versions.

```
VNDK approach:
  Vendor → directly calls library function → openCamera()

Stable AIDL approach:
  Vendor → calls interface → system handles library internally
```

The interface is a **contract** that never removes old things — only adds new ones.

### Scenario 1 — Both Updated ✅

```
Both on Android 15. Interface now has both versions.

interface.openCamera()    ← v1 (original, still here)
interface.openCameraV2()  ← v2 (new in v15)

Qualcomm new HAL uses openCameraV2()
System supports openCameraV2()

MATCH! ✅  Works and uses new features.
```

### Scenario 2 — Neither Updated ✅

```
Both on Android 14.

interface.openCamera()   ← v1 only

Qualcomm HAL calls openCamera()
System has openCamera()

MATCH! ✅
```

### Scenario 3 — Only System Updated ✅ (Better than VNDK)

```
Google updates to Android 15. Qualcomm does NOT update.

Android 15 interface:
  openCamera()     ← v1 STILL EXISTS (never removed!)
  openCameraV2()   ← v2 added

Old Qualcomm HAL calls openCamera() v1
System still has openCamera() v1

MATCH! ✅  No frozen library copies. No wasted storage.
```

```
┌─────────────────────────────────────────────┐
│  Stable AIDL Interface (Contract)            │
│                                             │
│  Android 14:  openCamera()                  │
│                                             │
│  Android 15:  openCamera()    ← STILL HERE  │
│               openCameraV2()  ← ADDED       │
│                                             │
│  Old Qualcomm HAL calls openCamera()        │
│  System still has it → Works! ✅            │
└─────────────────────────────────────────────┘
```

### Scenario 4 — Only Vendor Updated ✅ (Fixed — VNDK could not do this)

```
Qualcomm releases new HAL. System still on Android 14.
New HAL wants openCameraV2() but system only has v1.
```

Vendor writes **defensive code** with a version check:

```cpp
// Qualcomm NEW HAL — written with fallback
void startCamera() {
    if (interface.getVersion() >= 2) {
        interface.openCameraV2(id, MODE_HDR);  // new system ✅
    } else {
        interface.openCamera(id);               // old system fallback ✅
    }
}
```

```
Qualcomm new HAL
     ↓
checks interface version
     ↓
System is v14 → interface version = 1
     ↓
HAL takes fallback path
     ↓
calls openCamera(id)  [old way]
     ↓
Works! ✅
```

### Era 3 Summary

```
Scenario 1: Both Updated      → ✅ Works
Scenario 2: Neither Updated   → ✅ Works
Scenario 3: Only System       → ✅ Works (no frozen copies needed)
Scenario 4: Only Vendor       → ✅ Works now too!

ALL scenarios handled! 🎉
```

```
HAL calls:     getMemory(99999999999L)  ← long (8 bytes)

Wrong memory size allocated. Buffer overflow possible! 💥
```

```
HAL calls:  newFeature()
```

```
VNDK cannot help Scenario 4!
```

## 2. LL-NDK Libraries

**LL-NDK = Low Level NDK** — fundamental libraries that almost never change their ABI. Google guarantees these are always stable for vendor use. No VNDK needed.

### Full LL-NDK Library List

```
├── libc.so           ← C standard library
├── libm.so           ← Math library
```

### APEX Stability Rules (Why Scenarios Work)

```
Google APEX Rules:

│  RULE 1: Never remove existing functions    │

│  RULE 4: ABI must stay backward compatible  │

SSL_CTX_new() in v14  ← same signature
SSL_CTX_new() in v15  ← same signature
```

### Scenario 4 — Only Vendor Updated, APEX/System NOT


```cpp
    quantum_encrypt(data);              // v15 — wants new function
    SSL_connect(ssl);                   // v14 — old function
}
```

But APEX is still v14:

```
APEX v14 symbol table:
  SSL_CTX_new      ✅
  SSL_connect      ✅
  SSL_CTX_new_v2   MISSING ❌
  quantum_encrypt  MISSING ❌
```

**Without defensive code — linker fails:**

```
ERROR:
cannot locate symbol "SSL_CTX_new_v2"
referenced by vendor.wifi.hal.so

HAL fails to load! WiFi broken 💥
```

**With defensive code — works gracefully:**

```cpp
// SMART New Vendor WiFi HAL
#include <dlfcn.h>

void secureWifiConnect() {

    void* lib = dlopen("libcrypto.so", RTLD_NOW);
    auto* newFunc = dlsym(lib, "SSL_CTX_new_v2");

    if (newFunc != nullptr) {
        ALOGI("Using new SSL v2!");
        SSL_CTX* ctx = SSL_CTX_new_v2();   // new APEX available ✅
    } else {
        ALOGI("Falling back to SSL v1!");
        SSL_CTX* ctx = SSL_CTX_new();       // old fallback ✅
    }

    SSL_connect(ssl);   // always works ✅
}
```

```
New Vendor HAL
    ↓
checks if SSL_CTX_new_v2 exists
    ↓
APEX v14 → NOT found
    ↓
Takes fallback path
    ↓
calls SSL_CTX_new()  ← old function
    ↓
APEX v14 has this ✅
    ↓
WiFi works ✅
```

## 9. Final Summary

### How Vendor Uses Libraries Without VNDK

```
1. LL-NDK (liblog, libc, libm, libdl)
   → Always stable, ABI never changes
   → Use directly, no worries

2. APEX Libraries (libcrypto, libssl)
   → Stable inside APEX module
   → Google guarantees backward compatibility
   → No frozen copies needed

3. Replace with stable alternatives
   → libcutils → LL-NDK subset / sysprop
   → libutils  → std:: library
   → libbase   → standard POSIX

4. For everything else
   → Use Stable AIDL
   → System handles libs internally
   → Vendor never touches them directly
```

| | VNDK | APEX |
|---|---|---|
| Library copies | Frozen copy per version | One copy for everyone |

| Security fixes | Slow | Fast ✅ |

| Old vendor safety | ✅ Frozen copy | ✅ Functions never removed |
